## 2. GAP — requirement ที่ไม่มี design รองรับ

เรียงตามความรุนแรง

### G-1 🔴 US-45 (เลขคิว A01) — ไม่มีใน screen / API / data model เลยแม้แต่จุดเดียว

- `orders` ไม่มีคอลัมน์เลขคิว และไม่มีตัวนับที่รีเซ็ตรายวัน ทั้งที่ **BR ข้อ 25 สั่งไว้เป็นลายลักษณ์อักษร**
- ไม่มี endpoint ใดคืนเลขคิว · `GET /staff/orders` คืนแค่ `placed_at` / `status_changed_at` / ป้าย channel-origin
- ไม่มีหน้าจอไหนใน 23 หน้าจอที่แสดงเลขคิว ทั้งที่ AC ของ US-45 สั่งว่าต้อง **เด่นที่สุด**บนจอลูกค้าหลังยืนยันออเดอร์
- **ลูกโซ่:** ทำให้ AC ของ US-28 (ข้อ 5), US-29 (ข้อ 2), US-30 (ข้อ 6) ไม่มีทางผ่าน — จึงเป็นเหตุผลที่ US-28/29/30 ถูกมาร์ก ⚠️ PARTIAL ในตารางข้อ 1.1
- **ลูกโซ่ต่อ:** ขัด exit criteria ของ Phase 0 ในโรดแมปโดยตรง (*"ลูกค้าซื้อกลับต้องอ้างอิงออเดอร์ของตัวเองกับพนักงานได้ด้วยเลขคิว"*)
- **ลูกโซ่ต่อ PDPA:** ถ้าไม่มีเลขคิว ทางเดียวที่พนักงานจับคู่ออเดอร์กับคนได้คือถามชื่อ → เปิดจุดเก็บข้อมูลส่วนบุคคลจุดแรกของ Phase 0 → ขัด BR ข้อ 14
- **ค่าใช้จ่ายในการแก้:** วันนี้ = เพิ่ม 1 คอลัมน์ + 1 ตัวนับ + แสดงผล 3 จุด · หลังเริ่ม build = migration + แก้ทุกจอที่แสดงคิว

### G-2 🔴 US-44 (ป้าย/สติกเกอร์ QR) — ไม่มีแบบป้าย ไม่มีไฟล์พร้อมพิมพ์

- ไม่มีหน้าจอ ไม่มี endpoint ไม่มี entity · endpoint เดียวที่ใกล้เคียงคือ `GET /admin/tables/{id}/qr.png` ซึ่งคืน **รูป QR เปล่า**
- แต่ AC ของ **US-24 เอง** (เพิ่ม 2026-08-12) สั่งไว้ชัดว่าไฟล์ที่ดาวน์โหลดต้องเป็น *"ป้ายพร้อมพิมพ์ที่มี QR + เลขโต๊ะ + ข้อความบอกวิธีใช้และกฎการจ่ายเงินอยู่ในไฟล์เดียว **ไม่ใช่รูป QR เปล่า**"* — API ปัจจุบันจึงขัดกับ AC ของ US-24 ตรง ๆ ด้วย (นี่คือเหตุผลที่ US-24 ถูกมาร์ก ⚠️)
- ต้องมี **2 แบบ** (ป้ายโต๊ะ / ป้ายเคาน์เตอร์) เพราะกฎจ่ายเงินตรงข้ามกัน (BR ข้อ 12, 24) — ไม่มีที่ไหนออกแบบไว้
- US-44 คือ **MoSCoW = Must ที่ backlog เองระบุว่า "ไม่มี workaround จริง"** และเป็นจุดสัมผัสแรกของทุก journey (J1/J2/J3)

### G-3 🟠 BR ข้อ 26 + 27 (พนักงาน 2–4 คน หลายอุปกรณ์) — ไม่มีเจ้าภาพทั้งฝั่ง requirement และฝั่ง design

## 4. Finding — เอกสารขัดกันเอง / ID ไม่เป็นระบบ

> ตามคำสั่ง: บันทึกไว้เฉย ๆ ไม่แก้ ไม่เดา

### F-1 🔴 ไม่มีระบบ ID แบบ FR-xx / NFR-xx ในโปรเจกต์นี้เลย

ตรวจทุกไฟล์ใน `docs/` แล้ว **ไม่พบ `FR-` หรือ `NFR-` แม้แต่ตัวเดียว** — ระบบ ID ที่ใช้จริงมี 4 ชุด ซึ่ง **ไม่มีชุดไหนแยก functional ออกจาก non-functional**:

| ชุด ID | จำนวน | ใช้ที่ไหน | ปัญหา |
|---|---|---|---|
| `US-01…US-45` | 45 | backlog (ต้นทาง) + ทุกเอกสารปลายทาง | ✅ สม่ำเสมอ ไม่มีเลขซ้ำ ไม่มีเลขข้าม · เรียงตามลำดับที่สร้าง ไม่ใช่ลำดับในเอกสาร (US-42 อยู่ก่อน US-31 ในไฟล์) — จงใจและมีคำอธิบายกำกับไว้ |
| `UX-01…UX-12` | 12 | ux-requirements + design | ⚠️ มี `UX-13` ที่ถูกอ้างแต่ไม่มีอยู่จริง (ดู G-5) |
| `BR ข้อ 1…27` | 27 | backlog §3 | ⚠️ **ไม่มี prefix ตัวอักษร** — อ้างเป็นภาษาไทย "Business Rule ข้อ 11" ทำให้ grep/link ย้อนกลับยาก · feature-list เขียนเป็น `BR-09`, `BR-11`, `BR-25` ซึ่ง **ไม่ตรงกับรูปแบบในเอกสารต้นทาง** |
| `F-01…F-09` + `F-xx.y` | 9 + sub | feature-list เท่านั้น | ⚠️ **ไม่มีเอกสาร design ฉบับไหนอ้าง F-xx เลย** — feature tree จึงเป็น layer ที่ไม่มีใครใช้ต่อ |
| `C-xx` / `S-xx` / `A-xx` | 23 | screen-inventory | ✅ สม่ำเสมอ · ⚠️ แต่ไม่มีใครอ้างกลับมาที่ backlog |

### F-2 ✅ **ปิดแล้ว 2026-08-16** — "ร้อน/เย็น" เป็นหมวดหมู่ หรือเป็น option

> **คำตอบ (Touch ยืนยัน 2026-08-15, sync เข้า `01-requirements` เมื่อ 2026-08-16 ในรอบ T-010):** *"ร้อนเย็นแยกกันดีกว่า กดง่ายกว่าในหน้างานจริง"* → **ร้อน/เย็น = หมวดหมู่ · สินค้า 1 ตัว 1 อุณหภูมิ = 1 การ์ด**
> **หลักฐาน:** [[../../02-design/01-prototypes/design-system-adoption-v1|design-system-adoption-v1]] §8 ข้อ 1 บันทึกคำพูดของ Touch ไว้ตรง ๆ พร้อมทำเครื่องหมาย "ปิดแล้ว"
> **แก้อะไรไป:** [[initial-menu-data-v1|Initial Menu Data v1]] เพิ่มหัวข้อ **"รายการสินค้าจริงที่ต้องนำเข้าระบบ"** = **32 SKU** (ร้อน 16 · เย็น 16) พร้อมกฎการแตกรายการและรหัส `-H`/`-C` ที่สืบกลับไปหาที่มาของราคาได้ · [[product-backlog-v1|Product Backlog v1]] เพิ่ม AC ใน **US-02** และ **US-23** พร้อมบล็อกบันทึกที่มาของคำตัดสิน

## 5. AC ที่ขาด — US ที่ยังไม่มี acceptance criteria ที่เทสต์ได้จริง

**ทั้ง 45 US มี AC ครบทุกตัว ไม่มีตัวไหนว่างเปล่า** — ปัญหาไม่ใช่ "ไม่มี AC" แต่คือ **AC ที่เขียนไว้แล้ววัดผลไม่ได้** เรียงตามลำดับความสำคัญของ backlog (P0 ก่อน แล้วตามด้วย MoSCoW = Must ก่อน Should)

| ลำดับ | US | Priority / MoSCoW | AC ที่มีปัญหา | ทำไมเทสต์ไม่ได้ | มี UX-xx มาปักหมุดตัวเลขให้ไหม |
|---|---|---|---|---|---|
| 1 | **US-15** แจ้งเตือนออเดอร์ใหม่ | **P0 / Must** | มี AC ข้อเดียว: *"มีเสียงแจ้งเตือน **และ/หรือ** popup/badge ทุกครั้งที่มีออเดอร์ใหม่"* | **"และ/หรือ" ทำให้เทสต์ไม่ได้** — ผ่านด้วย badge เงียบ ๆ ก็ได้ ซึ่งขัดกับเจตนาของ story เอง (*"ไม่พลาดออเดอร์แม้ไม่ได้จ้องหน้าจอ"*) · ไม่มีเกณฑ์เวลา ไม่มีเกณฑ์ระดับเสียง ไม่มีเงื่อนไขว่าต้องดังแม้จอดับ | ⚠️ UX-09 ครอบแค่ขนาดปุ่ม/มือเปียก ไม่ครอบการแจ้งเตือน — **ไม่มีตัวเลขปักหมุด** |
| 2 | **US-13** เห็นออเดอร์ใหม่เรียลไทม์ | **P0 / Must** | *"แสดงออเดอร์ใหม่โดยไม่ต้องกดรีเฟรชเอง"* | ไม่มีเกณฑ์เวลา — "ไม่ต้องรีเฟรช" กับ "เห็นภายในกี่วินาที" คนละเรื่อง | ⚠️ UX-04 ปักหมุด ≤5 วินาที แต่**เขียนไว้สำหรับฝั่งลูกค้า (US-05/US-14)** ไม่ได้เขียนคลุมจอสถานี |
| 3 | **US-44** ป้าย/สติกเกอร์ QR | **P0 / Must** | *"QR มีขนาดที่สแกนติดจากท่านั่งปกติ"* · *"เลขโต๊ะอ่านออกได้จากระยะยืน (~1 เมตร)"* | ไม่มีขนาดจริง (มม.), ไม่มี error-correction level, ไม่มีขนาดฟอนต์ขั้นต่ำ — **ทดสอบซ้ำได้ยาก** และเป็น deliverable ที่ต้องส่งโรงพิมพ์ | ❌ ไม่มี UX-xx ตัวไหนผูกกับ US-44 เลย |
| 4 | **US-16** มาร์กสินค้าหมด | **P0 / Should** | *"ภายในไม่กี่คลิก"* · *"เมนูฝั่งลูกค้าอัปเดต**ทันที**"* | "ไม่กี่คลิก" และ "ทันที" ไม่มีตัวเลข · เป็น AC ที่ผูกกับ race condition ที่ api-design §5.2 ออกแบบไว้อย่างละเอียดแล้ว แต่ AC ไม่ได้สะท้อนความละเอียดนั้นกลับมา | ⚠️ UX-09 ครอบแค่ขนาดปุ่ม |
| 5 | **US-23** จัดการเมนู | **P0 / Must** | *"มีผลกับเมนูฝั่งลูกค้าทันที (หรือภายในเวลาสั้น ๆ)"* | *"ทันที (หรือภายในเวลาสั้น ๆ)"* — วงเล็บทำให้เกณฑ์หายไปทั้งข้อ | ✅ UX-11 ปักหมุด ≤5 นาที/success ≥90% แต่วัด **ความง่ายของแอดมิน** ไม่ได้วัด **ความเร็วในการ propagate** |
| 6 | **US-42** จัดผังโต๊ะ | **P0 / Should** | *"ทำให้เสร็จได้ภายใน**ไม่กี่คลิก**จากหน้าจอเดียว"* (AC ข้อ 8) | ไม่มีตัวเลข · เป็น story ที่ screen-inventory เตือนเองว่า **"เพิ่มสโคปจริงให้ Phase 0 มากที่สุด"** และ persona เจ้าของคือ P5 คุณแอน (ไม่สายเทค) — จุดที่ควรมีเกณฑ์ที่สุดกลับไม่มี | ⚠️ UX-11 มีเกณฑ์แบบนี้อยู่แล้ว แต่**ผูกไว้กับ US-23/US-24 เท่านั้น ไม่ครอบ US-42** ทั้งที่ persona และลักษณะงานเหมือนกันเป๊ะ |
| 7 | **US-02** ดูเมนูสินค้า | **P0 / Must** | *"หน้าจอใช้งานได้ดีบนมือถือ"* | *"ใช้งานได้ดี"* ไม่ใช่เกณฑ์ | ✅ **ครอบแล้ว** ด้วย UX-01 (≤3 วิ / ≤5 วิ Slow 3G), UX-02 (≤6 tap) และ BR ข้อ 23 (≥16px, 4.5:1, ≥44px) — ข้อนี้จึงเป็นปัญหาเชิงถ้อยคำมากกว่าเชิงเนื้อหา |

**ข้อสังเกตข้ามตาราง:** Phase 0 มี 25 US แต่ UX requirement ครอบคลุมแค่ 16 ตัว — **9 ตัวที่ไม่มี UX-xx ปักหมุดตัวเลขให้เลย** คือ US-18, US-19, US-20, US-35, US-36, US-42, US-43, US-44, US-45 · ในกลุ่มนี้ US-19/US-20/US-35/US-36/US-43/US-45 มี AC ที่เป็น **state-based** (ตรวจได้ว่าจริง/เท็จ) จึงยังเทสต์ได้ · ที่เหลือ (**US-42, US-44**) เป็น AC เชิงคุณภาพที่ต้องมีตัวเลข

## 6. สรุปสิ่งที่ควรทำต่อ (ข้อเสนอ ไม่ใช่การตัดสินใจ)

เรียงตามลำดับที่ควรทำ — **ทุกข้อรอ Touch/god อนุมัติก่อน XAVIER จะแก้เอกสารใด ๆ**

1. **ปิด G-1 (US-45 เลขคิว) ก่อนอย่างอื่น** — เป็น schema change ที่ราคาถูกที่สุดวันนี้ · แจ้ง COULSON เพิ่มคอลัมน์เลขคิว + ตัวนับรายวันใน `orders` และเพิ่มการแสดงผล 3 จุด (จอลูกค้าหลังยืนยัน · คิวรอยืนยันชำระเงิน · คิวเตรียมของ)
2. **ปิด G-2 (US-44 ป้าย QR)** — งานออกแบบป้าย 2 แบบเป็นของ SHURI · การผลิตไฟล์พร้อมพิมพ์ผูกกับ endpoint ของ US-24 ที่ต้องแก้จาก `qr.png` เป็นไฟล์ป้ายเต็มใบ
3. **ปิด G-3 (BR ข้อ 26/27)** — ตัดสินก่อนว่าจะให้เป็น NFR ที่ architecture รับไปเลย หรือเปิด US ใหม่เป็นเจ้าภาพ (กระทบเรื่อง ID ตาม F-1)
4. **ให้ COULSON แก้คำประกาศความครบถ้วนใน screen-inventory §1 จาก 23 เป็น 25** (G-4) — ไม่ใช่เรื่องตัวเลข แต่เพื่อไม่ให้เอกสารนี้ถูกใช้เป็นหลักฐานว่า Phase 0 ครบแล้ว
5. **ตอบ 18 ข้อของ F-3** — โดยเฉพาะ 3 ข้อที่กระทบ schema (รอเสิร์ฟ / ร้อน-เย็น / นมโอ๊ต) เพราะ COULSON ระบุเองว่าต้องได้คำตอบ **ก่อน finalize schema**
6. **ตัดสิน O-8 (US-46…US-49)** — อนุมัติหรือปฏิเสธ เพื่อปลดล็อกเลข US สำหรับ story ใหม่ที่ข้อ 1–3 อาจต้องเปิด
7. **เริ่ม `03-testing/01-test-plan`** — ของที่แปลงเป็น test case ได้ทันทีโดยไม่ต้องรอ requirement ใหม่: UX-01…UX-12 (12 เกณฑ์ที่มีตัวเลขครบ), ux-requirements §7, invariant 10 ข้อ, error contract 16 กรณี, race condition 6 จุด = **ประมาณ 50 test case ที่เขียนได้ตั้งแต่วันนี้**
8. **เติมตัวเลขให้ AC ทั้ง 7 ข้อในหัวข้อ 5** — เริ่มที่ US-15 (Must, มี AC ข้อเดียวและ "และ/หรือ") และ US-42/US-44 (ไม่มี UX-xx ครอบเลย)
