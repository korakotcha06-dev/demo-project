## 0. จุดประสงค์ของเอกสาร

เอกสารนี้แปลง actor 3 กลุ่มใน [[product-backlog-v1|Product Backlog v1]] (ลูกค้า / พนักงานแคชเชียร์-หน้าร้าน / เจ้าของร้าน-แอดมิน) ให้เป็น **persona ที่มีตัวตนและบริบทการใช้งานที่ชัดเจนขึ้น** เพื่อให้ COULSON และทีมออกแบบ (SHURI) ใช้ตัดสินใจเรื่อง UI/UX ได้อย่างมีหลักอ้างอิง แทนที่จะออกแบบจาก actor ที่เป็นแค่ label บทบาท

Persona ทั้ง 5 ตัวนี้เป็น **roster คงที่** — ห้ามเปลี่ยนชื่อ/บทบาท เพราะเอกสาร Journey Map (จะตามมาในสัปดาห์เดียวกัน) จะอ้างอิง persona ชุดนี้โดยตรง

## 1. Persona Roster

### P1 — "ฟ้า" (พนักงานออฟฟิศ, ลูกค้า dine-in ประจำ)

| หัวข้อ | รายละเอียด |
|---|---|
| ข้อมูลพื้นฐาน | อายุ ~28 ปี พนักงานออฟฟิศบริษัทเอกชนแถวที่ตั้งร้าน มาร้านเกือบทุกวันช่วงพักเที่ยงหรือก่อนเข้างานตอนเช้า มักมาคนเดียวหรือมากับเพื่อนร่วมงาน 1-2 คน |
| เป้าหมาย (Goals) | สั่งเครื่องดื่ม/ของว่างให้เร็วที่สุด กลับไปทำงานหรือกลับโต๊ะทันเวลาพัก ไม่อยากรอเรียกพนักงานหรือต่อคิว |
| พฤติกรรมและบริบทการใช้งาน | นั่งที่โต๊ะ สแกน QR ด้วยมือถือตัวเอง สั่งระหว่างพัก 15-20 นาที บางวันสั่งเพิ่มรอบสองระหว่างนั่งคุยงาน ใช้มือถือเก่งอยู่แล้ว คุ้นเคยกับแอปสั่งอาหารเดลิเวอรี่/QR ร้านอื่นมาก่อน |
| Pain Points | เกลียดการรอพนักงานมารับออเดอร์ตอนร้านคนเยอะ ไม่มีเวลาต่อคิวจ่ายเงินถ้าไม่จำเป็น อยากรู้สถานะออเดอร์แบบไม่ต้องเดินไปถาม |
| ความคาดหวังจากระบบ | สแกนแล้วเจอเมนูทันที ไม่มีหน้ากลางให้เสียเวลา สั่งเสร็จรู้สถานะแบบเรียลไทม์ สั่งเพิ่มรอบสองได้โดยไม่ต้องสแกนซ้ำ |
| ระดับทักษะดิจิทัล / อุปกรณ์ | สูง — ใช้สมาร์ตโฟนเป็นหลัก คุ้นเคย QR/mobile web ทั่วไปดี ไม่ต้องมีคำแนะนำการใช้งานละเอียด |
| Quote | "สแกนปุ๊บขอให้เจอเมนูปั๊บ ไม่ต้องมีหน้าอะไรมาคั่นก่อน เดี๋ยวเวลาพักหมดพอดี" |
| User Story ที่เกี่ยวข้อง | เจ้าของ: US-01, US-02, US-03, US-04, US-05, US-06, US-07 · ได้ประโยชน์: US-08, US-09, US-11, US-35 |

### P2 — "ต้น" (ลูกค้า takeaway/สั่งกลับ ผ่าน QR เคาน์เตอร์)

| หัวข้อ | รายละเอียด |
|---|---|
| ข้อมูลพื้นฐาน | อายุ ~32 ปี ทำงานหรือเดินทางผ่านย่านที่ตั้งร้าน แวะซื้อกาแฟกลับระหว่างเดินทาง ไม่ได้นั่งในร้าน |
| เป้าหมาย (Goals) | สั่ง จ่ายเงิน รับของ แล้วออกจากร้านให้เร็วที่สุด ไม่อยากยืนรอคิวพูดสั่งด้วยปาก |
| พฤติกรรมและบริบทการใช้งาน | สแกน QR ที่ติดหน้าเคาน์เตอร์ (ไม่ใช่ QR โต๊ะ) เลือกเมนู-จ่ายเงินก่อนออเดอร์เข้าครัวตาม Business Rule ข้อ 12 แล้วยืนรอที่ "ปลายเคาน์เตอร์" ระยะเวลาที่ยอมรับได้ทั้งกระบวนการคือไม่กี่นาที |
| Pain Points | รีบมาก ไม่ต้องการขั้นตอนซ้ำซ้อน กลัวสับสนว่าต้องจ่ายเงินตรงไหน/เมื่อไหร่ ไม่อยากถูกจัดคิวปนกับลูกค้านั่งทาน |
| ความคาดหวังจากระบบ | รู้ชัดเจนว่าต้องจ่ายเงินก่อนออเดอร์จะเดินหน้า มีจุดรับของที่ชัดเจนแยกจากจุดสั่ง/จ่ายเงิน รู้ว่าออเดอร์ของตัวเองเสร็จเมื่อไหร่โดยไม่ต้องถาม |
| ระดับทักษะดิจิทัล / อุปกรณ์ | ปานกลาง-สูง — ใช้สมาร์ตโฟนคล่อง แต่ไม่มีเวลาอ่านคำอธิบายยาว ต้องการ flow ที่ตรงไปตรงมาไม่ต้องตัดสินใจเยอะ |
| Quote | "รีบมากจริง ๆ ขอจ่ายแล้วรับของแล้วไปเลย อย่าเพิ่งมีขั้นตอนพิเศษ" |
| User Story ที่เกี่ยวข้อง | เจ้าของ: US-28 (ใช้กลไก US-02/US-03 ร่วม) · ได้ประโยชน์: US-08, US-09, US-35 · เกี่ยวข้องทางอ้อม: US-29 (ฝั่งพนักงานยืนยันจ่ายเงินของออเดอร์เขา), Business Rule ข้อ 12 |

### P3 — "ป้าน้อย" (ลูกค้าสูงวัย, ตัวแทน accessibility / worst-case usability)

| หัวข้อ | รายละเอียด |
|---|---|
| ข้อมูลพื้นฐาน | อายุ ~58 ปี มาร้านเป็นครั้งคราวกับเพื่อนหรือลูกหลาน ไม่ได้ใช้แอปสั่งอาหารเป็นกิจวัตร สายตาเริ่มมีปัญหาเวลาอ่านตัวหนังสือเล็ก |
| เป้าหมาย (Goals) | สั่งเครื่องดื่มที่ต้องการได้โดยไม่รู้สึกเคอะเขิน/กังวลว่าจะกดผิด ไม่อยากรบกวนคนอื่นให้มาช่วยสั่งแทน แต่ก็ไม่ปฏิเสธถ้าพนักงานช่วยได้ |
| พฤติกรรมและบริบทการใช้งาน | เห็น QR code ที่โต๊ะแต่ไม่แน่ใจว่าต้องสแกนยังไง บางครั้งไม่มีแอปกล้องที่อ่าน QR ในตัว หรือลืมวิธีเปิดกล้องสแกน ตัวอักษร/ปุ่มขนาดเล็กบนจอมือถือทำให้กดพลาดง่าย มักถามพนักงานตรง ๆ แทนการงมเอง |
| Pain Points | ตัวหนังสือเล็กเกินไปอ่านไม่ออก ไม่รู้ต้องกดตรงไหนหลังสแกน QR กังวลว่ากดผิดแล้วเสียเงิน/สั่งผิด ไม่มั่นใจเทคโนโลยีจนรู้สึกเสียเวลาคนอื่นที่ต่อคิวอยู่ข้างหลัง |
| ความคาดหวังจากระบบ | ถ้าจะใช้ระบบ QR ต้องมีตัวอักษร/ปุ่มขนาดใหญ่พอ ขั้นตอนน้อยที่สุด และ **ต้องมีทางเลือกสั่งด้วยปากเปล่ากับพนักงานได้เสมอโดยไม่ถูกปฏิเสธหรือทำให้รู้สึกแปลก** |
| ระดับทักษะดิจิทัล / อุปกรณ์ | ต่ำ — มีสมาร์ตโฟนแต่ใช้เฉพาะแอปพื้นฐาน (โทร/LINE) ไม่คุ้นการสแกน QR ด้วยตัวเอง ไม่คุ้นภาษา UI แบบ "ตะกร้า/เพิ่มรายการ" |
| Quote | "หนูสแกนไม่เป็นหรอก ขอสั่งกับน้องที่เคาน์เตอร์แบบเดิมได้ไหมจ๊ะ" |
| User Story ที่เกี่ยวข้อง | ตัวแทนกรณีเสี่ยง (usability risk) ของ: US-01, US-02, US-03, US-04, US-05 · เจ้าของ/ผู้ได้ประโยชน์จากทางเลือกสำรอง: US-30 (พนักงานคีย์ออเดอร์แทนลูกค้าที่สั่งด้วยวาจา) |

### P4 — "เบียร์" (บาริสต้า/พนักงานหน้าร้าน — internal persona)

| หัวข้อ | รายละเอียด |
|---|---|
| ข้อมูลพื้นฐาน | อายุ ~24 ปี พนักงานประจำร้าน ทำหน้าที่รวม (ตาม Business Rule ข้อ 13) — ทั้งชงเครื่องดื่ม/ทำของ และรับเงิน/ปิดบิลในสถานีเดียวกัน เพราะจุดเตรียมของอยู่ติดเคาน์เตอร์ |
| เป้าหมาย (Goals) | ทำออเดอร์ให้ครบถูกต้องไม่ตกหล่น ไม่พลาดออเดอร์ใหม่ที่เข้ามาระหว่างมือไม่ว่าง จบแต่ละออเดอร์ให้ไวที่สุดช่วง peak โดยไม่สับสนว่าออเดอร์ไหนเป็นของโต๊ะไหน/ใครจ่ายแล้วหรือยัง |
| พฤติกรรมและบริบทการใช้งาน | ยืนอยู่หน้าเครื่องชงกาแฟ/เคาน์เตอร์ตลอดกะ มือมักเปียก/เปื้อนระหว่างทำงาน ต้องดูจอออเดอร์สลับกับการชงเครื่องดื่มและรับเงินไปพร้อมกัน ช่วง peak (เช้า/พักเที่ยง) มีออเดอร์เข้าพร้อมกันจากทั้งโต๊ะ (dine-in) และเคาน์เตอร์ (takeaway ทั้งที่ลูกค้าสั่งเองผ่าน QR และที่ตัวเองคีย์แทนลูกค้าที่สั่งปากเปล่า) |
| Pain Points | มือเปียก/เปื้อนทำให้กดหน้าจอเล็ก ๆ ผิดพลาดง่าย เสียงแจ้งเตือนอาจไม่ได้ยินตอนเครื่องชงกำลังทำงานเสียงดัง ถ้าไม่มีระบบแยกคิว dine-in vs takeaway ชัดเจนอาจสับสนว่าออเดอร์ไหนต้องทำก่อน/ออเดอร์ไหนยังไม่ได้จ่ายเงิน |
| ความคาดหวังจากระบบ | ปุ่ม/พื้นที่กดต้องใหญ่พอสำหรับสถานการณ์มือเปียก แจ้งเตือนต้องเห็นชัดแม้ไม่ได้ยินเสียง แยกคิว/ป้ายที่มาของออเดอร์ (โต๊ะ vs เคาน์เตอร์, ลูกค้าสั่งเอง vs พนักงานคีย์แทน) ให้ดูออกในพริบตาเดียว |
| ระดับทักษะดิจิทัล / อุปกรณ์ | ปานกลาง — ใช้จอแท็บเล็ต/หน้าจอสถานีที่ร้านติดตั้งให้เป็นหลัก ไม่ใช่มือถือส่วนตัว ต้องได้รับการสอนวิธีใช้ระบบครั้งแรก แต่ไม่จำเป็นต้องเก่งเทคโนโลยีมาก่อน |
| Quote | "มือเปียกอยู่ ขอปุ่มใหญ่ ๆ กดง่าย ๆ อย่าให้ต้องมาคอยเช็ดจอบ่อย ๆ" |
| User Story ที่เกี่ยวข้อง | เจ้าของ: US-13, US-14, US-15, US-16, US-17, US-18, US-19, US-20, US-21, US-22, US-29, US-30 |

| Pain Points | กลัวกดอะไรผิดแล้วกระทบเมนูที่ลูกค้าเห็นอยู่ตอนนั้น ไม่มีเวลาเรียนรู้ระบบซับซ้อน ต้องพึ่งพนักงานหรือลูกเรียกโปรแกรมเมอร์ถ้า UI ไม่ตรงไปตรงมา |
| ความคาดหวังจากระบบ | หน้าจัดการเมนู/QR ต้องเข้าใจง่ายแบบไม่ต้องมีคู่มือ การแก้ไขมีผลทันทีโดยไม่ต้องรอ deploy รายงานอ่านง่ายเป็นภาพรวม ไม่ต้องตีความตัวเลขซับซ้อน |
| ระดับทักษะดิจิทัล / อุปกรณ์ | ต่ำ-ปานกลาง — ใช้ Facebook/LINE/Excel พื้นฐานได้ แต่ไม่คุ้นระบบจัดการหลังบ้าน (admin panel) ที่ซับซ้อน ต้องการ UI ที่เดาทางได้ (self-explanatory) |
| Quote | "ขอให้แก้เมนูเองได้แบบไม่ต้องโทรหาโปรแกรมเมอร์ทุกครั้งที่ราคากาแฟขึ้น" |
| User Story ที่เกี่ยวข้อง | เจ้าของ: US-23, US-24, US-25, US-26, US-27, US-31, US-34, US-36 |

## 2. ตารางสรุปเปรียบเทียบ Persona

| Persona | บทบาท | Primary/Secondary (สำหรับ MVP) | ช่องทาง | ความสำคัญต่อ MVP |
|---|---|---|---|---|
| P1 ฟ้า | ลูกค้า dine-in ประจำ | **Primary** | Dine-in (QR โต๊ะ) | สูงสุด — คือภาพของโจทย์ตั้งต้นตรง ๆ ("ลูกค้าสแกน QR ที่โต๊ะสั่งเอง") การออกแบบ flow หลัก (US-01 ถึง US-07) ต้องผ่านมาตรฐานของ ฟ้า ก่อนใคร |
| P2 ต้น | ลูกค้า takeaway | Secondary (แต่ P0 ตาม Business Rule) | Takeaway (QR เคาน์เตอร์) | สูง — ช่องทางเคาน์เตอร์เป็น P0/Phase 0 เต็มตัว (US-28/29/30) ไม่ใช่ nice-to-have แต่เป็น flow รองจาก dine-in ในแง่ที่ไม่ใช่ภาพหลักของโจทย์ตั้งต้น |
| P3 ป้าน้อย | ลูกค้าสูงวัย/accessibility | Secondary — ใช้เป็น **validation persona** | ทั้งสองช่องทาง (มักหลบไปใช้ US-30 แทน self-scan) | ปานกลาง-สูง — ไม่ใช่ target หลักของ flow QR เอง แต่ถ้า flow ทำให้เธอใช้ไม่ได้เลย = ความเสี่ยงต่อภาพลักษณ์ร้านและยอดขายจากกลุ่มลูกค้าสูงวัย ต้อง design ผ่าน worst-case ของเธอ ไม่ใช่แค่ optimize สำหรับ ฟ้า |
| P4 เบียร์ | พนักงานหน้าร้าน (internal) | **Primary (ฝั่ง internal)** | Internal — รับออเดอร์ทุกช่องทาง | สูงสุด — ทุก user story ฝั่งเตรียมของ/การเงิน (หมวด 2.2-2.3, US-29, US-30) เป็น P0 ทั้งหมด ถ้าหน้าจอของเบียร์ใช้งานไม่ได้จริงช่วง peak ระบบทั้งระบบก็ล้มเหลวในทางปฏิบัติ |
| P5 คุณแอน | เจ้าของร้าน/แอดมิน (internal) | Secondary (แต่มี P0 บางส่วน) | Internal — จัดการระบบ | ปานกลาง-สูง — US-23 (จัดการเมนู) และ US-24 (สร้าง QR) เป็น P0 จำเป็นต่อการเปิดร้านวันแรก ส่วน US-25/26/27/31/34/36 กระจายอยู่ P1/P2 |

## 3. Persona ไหนคือ Primary สำหรับ MVP และเหตุผล

**Primary สำหรับ MVP มี 2 ตัว คนละมิติกัน ไม่ใช่ตัวเดียว:**

1. **ฟ้า (P1)** เป็น primary ฝั่งลูกค้า เพราะเธอคือภาพตรงของโจทย์ตั้งต้นในไฟล์ [[../../../CLAUDE.md|CLAUDE.md]] — "ลูกค้าสแกน QR ที่โต๊ะแล้วสั่งเอง" — ทุกการตัดสินใจ UX ของ flow หลัก (US-01 ถึง US-07) ควร optimize ให้เธอเร็วและลื่นที่สุดก่อน เพราะเป็น use case ที่เกิดบ่อยที่สุดและตรงกับเหตุผลที่ร้านลงทุนสร้างระบบนี้ตั้งแต่แรก

2. **เบียร์ (P4)** เป็น primary ฝั่ง internal เพราะทุก use case ของลูกค้า (ทั้ง ฟ้า, ต้น, และแม้แต่ ป้าน้อยที่ใช้ US-30) จบลงที่หน้าจอของเบียร์เสมอ ถ้าหน้าจอนี้ใช้งานไม่ได้จริงในสภาพมือเปียก/เสียงดัง/ช่วง peak ระบบทั้งหมดก็ล้มเหลวไม่ว่าฝั่งลูกค้าจะออกแบบมาดีแค่ไหน — เบียร์คือ single point of failure ของระบบทั้งระบบภายใต้ station model แบบรวมเดียว (Business Rule ข้อ 13)

**ต้น (P2) และ คุณแอน (P5) เป็น secondary ที่ยังคงมีงาน P0 ต้องทำ** ไม่ใช่ persona ที่ตัดทิ้งได้ เพียงแต่ไม่ใช่ตัวที่กำหนดทิศทางการออกแบบ flow หลัก — ออกแบบ flow หลักให้ ฟ้า/เบียร์ ผ่านก่อน แล้วค่อยตรวจว่า flow เดียวกัน (ที่ใช้กลไกร่วมกับ US-02/US-03) ยังใช้ได้กับต้นและคุณแอนหรือไม่

**ป้าน้อย (P3) มีบทบาทพิเศษ: เป็น validation gate ไม่ใช่ design target** — ไม่ได้ออกแบบ flow ใหม่แยกสำหรับเธอ แต่ทุก flow ที่ทำเสร็จสำหรับ ฟ้า ต้องถูกทดสอบซ้ำผ่านสายตาของป้าน้อยก่อนถือว่า "เสร็จจริง" ถ้าเธอใช้ไม่ได้เลย ระบบต้องมีทางออก (US-30) ที่ไม่ทำให้เธอรู้สึกถูกทิ้งไว้ข้างหลัง

## 4. สมมติฐานและข้อจำกัด (Assumptions & Limitations)

**ข้อจำกัดสำคัญที่ต้องบอกให้ชัด: persona ทั้ง 5 ตัวนี้เป็น proto-persona** — สร้างขึ้นจากการตีความ backlog + โจทย์ตั้งต้นของ Touch เท่านั้น **ยังไม่ผ่านการสัมภาษณ์ผู้ใช้จริง (user interview) แม้แต่คนเดียว** จึงมีความเสี่ยงที่รายละเอียดบางจุดจะไม่ตรงกับลูกค้า/พนักงานจริงของร้าน

สิ่งที่เป็น **สมมติฐานที่ควร validate** ก่อนใช้ persona เหล่านี้ตัดสินใจ design ที่ลงทุนสูง (เช่น ก่อนเริ่ม build จริงใน 02-design):

1. **สัดส่วนของแต่ละ persona ในลูกค้าจริง** — สมมติว่า ฟ้า (ออฟฟิศ) เป็นกลุ่มใหญ่สุด แต่ยังไม่รู้ทำเลร้านจริงว่าอยู่ย่านออฟฟิศ ย่านที่พักอาศัย หรือแหล่งท่องเที่ยว ซึ่งจะเปลี่ยนสัดส่วนนี้มาก
2. **ป้าน้อยเป็น edge case จริงหรือกลุ่มลูกค้าขนาดใหญ่** — ถ้าทำเลร้านอยู่ใกล้ชุมชนผู้สูงวัย ป้าน้อยอาจไม่ใช่ worst-case เล็ก ๆ แต่เป็นกลุ่มลูกค้าหลักกลุ่มหนึ่งที่ต้องออกแบบให้จริงจังกว่านี้
3. **จำนวนพนักงานจริงตอนเปิดร้าน** — เบียร์ถูกสมมติเป็นคนเดียวทำทุกอย่าง (ตาม Business Rule ข้อ 13) ถ้าร้านมีพนักงานมากกว่า 1 คนหมุนเวียนกันตั้งแต่วันแรก บางเงื่อนไข pain point (มือเปียก, ทำหลายอย่างพร้อมกัน) อาจไม่ตรงเป๊ะ
4. **คุณแอนจะเข้าระบบแอดมินบ่อยแค่ไหนจริง** — สมมติว่าเข้านอกเวลาขายเป็นหลัก ถ้าจริง ๆ ต้องเช็ครายงานระหว่างวันบ่อย ๆ ต้องออกแบบให้เข้าถึงง่ายกว่านี้บนมือถือ ไม่ใช่แค่จอคอมพิวเตอร์
5. **ต้น (takeaway) รีบขนาดไหนจริง** — สมมติว่าอดทนรอได้ "ไม่กี่นาที" แต่ยังไม่มีข้อมูลจริงว่าลูกค้าซื้อกลับของร้านนี้ยอมรอนานแค่ไหนก่อนหงุดหงิด

**Persona เหล่านี้ควรถูกทบทวนอีกครั้งหลังร้านเปิดจริงและมีข้อมูลลูกค้าจริง** (หรือถ้าเป็นไปได้ ทำ user interview สั้น ๆ กับกลุ่มตัวอย่างก่อน 02-design เริ่ม build ของจริง) ไม่ควรถือเป็นความจริงสมบูรณ์เพียงเพราะเขียนไว้เป็นเอกสารแล้ว

## 5. NEED-INPUT / คำถามถึง Touch

ประเด็นต่อไปนี้เป็นสิ่งที่ Touch ในฐานะ CEO/เจ้าของร้านเป็นผู้รู้ดีที่สุด ไม่ใช่สิ่งที่ XAVIER ควรเดาแทน กรุณาตอบเท่าที่ทราบ ข้อไหนยังไม่แน่ใจก็บอกได้ว่า "ยังไม่รู้ รอดูตอนเปิดร้านจริง" — ไม่บล็อกการทำ Journey Map ต่อ เพราะจะใช้สมมติฐานข้อ 4 แทนไปก่อน

1. **ทำเลร้านตั้งอยู่ย่านแบบไหน?** (ย่านออฟฟิศ / ที่พักอาศัย/ชุมชน / แหล่งท่องเที่ยว / ริมถนนคนเดินผ่าน) — มีผลโดยตรงต่อสัดส่วนลูกค้าแบบ ฟ้า vs ป้าน้อย vs ต้น
2. **คาดว่าสัดส่วนลูกค้า dine-in (นั่งในร้าน) กับ takeaway (ซื้อกลับ) จะเป็นเท่าไหร่โดยประมาณ?** (เช่น 70:30 หรือ 50:50) — มีผลต่อว่าควรลงทุนออกแบบ/ทดสอบช่องทางไหนหนักกว่ากัน
3. **กลุ่มลูกค้าสูงวัย (แบบป้าน้อย) เป็นกลุ่มที่คาดว่าจะเจอบ่อยไหม?** หรือเป็นแค่กรณีนาน ๆ ครั้ง — มีผลต่อว่าต้องลงทุนกับทางเลือก "สั่งด้วยปากเปล่า" (US-30) มากแค่ไหน
4. **ตอนเปิดร้านวันแรก จะมีพนักงานกี่คนหมุนเวียนกันทำงาน?** (คนเดียวตลอดกะ หรือมีมากกว่า 1 คนช่วยกัน) — มีผลต่อ pain point ของเบียร์ (คนเดียวทำทุกอย่างจริงไหม)
5. **Touch (หรือคุณแอนตัวจริงถ้าไม่ใช่คนเดียวกัน) จะเข้าดูรายงาน/จัดการเมนูบ่อยแค่ไหนและจากอุปกรณ์อะไร?** (คอมพิวเตอร์ที่ร้าน / มือถือระหว่างวัน) — มีผลต่อว่าหน้าแอดมินควร mobile-first หรือไม่
6. **มีข้อมูลลูกค้าจริงจากการสำรวจหรือประสบการณ์ร้านกาแฟที่เคยทำมาก่อนบ้างไหม** ที่ช่วยยืนยัน/แก้ไข persona เหล่านี้ได้ก่อนเริ่ม 02-design จริง

## 6. หมายเหตุการส่งต่อ (Handoff)

เอกสารนี้เป็น proto-persona ระดับ DRAFT — ยังไม่ต้องรอคำตอบข้อ NEED-INPUT ด้านบนก่อนเริ่มทำ Journey Map เพราะ Journey Map จะใช้ persona roster นี้ตามที่มีอยู่ (พร้อมระบุ assumption เดิมกำกับไว้) แต่**ห้ามให้ COULSON/SHURI ใช้เอกสารนี้เป็นข้อเท็จจริงที่ยืนยันแล้วเวลาออกแบบ UI จริง** — ควรอ้างอิงพร้อมข้อความเตือนว่าเป็น draft ที่ยังไม่ validate จนกว่า Touch จะตอบคำถามในหัวข้อ 5 หรือมีข้อมูลลูกค้าจริงหลังเปิดร้าน

---

ส่งงาน — XAVIER → ทัช (งาน / ผลลัพธ์ / ค้าง-เสี่ยง / skill ที่ใช้)

**งาน:** ร่างเอกสาร UX Persona (DRAFT) สำหรับระบบสั่งอาหารด้วย QR code ตาม persona roster ที่กำหนด 5 ตัว (ฟ้า/ต้น/ป้าน้อย/เบียร์/คุณแอน) แปลงจาก actor 3 กลุ่มใน [[product-backlog-v1|Product Backlog v1]] ให้มีบริบท เป้าหมาย pain point และแม็ปกับ US-xx ครบทุกตัว พร้อมระบุ primary/secondary สำหรับ MVP

**ผลลัพธ์:** ไฟล์ `docs/01-requirements/01-spec/ux-persona-v1.md` — persona ครบ 5 ตัวพร้อมตารางเปรียบเทียบ, primary = ฟ้า (ลูกค้า) + เบียร์ (internal), ป้าน้อยเป็น validation gate ไม่ใช่ design target, หัวข้อสมมติฐาน/ข้อจำกัด และ NEED-INPUT 6 ข้อถึง Touch

**ค้าง/เสี่ยง:** persona ทั้งหมดยังไม่ผ่าน user interview จริง เป็น proto-persona ล้วน ๆ — ความเสี่ยงหลักคือสัดส่วนลูกค้าจริง (ทำเลร้าน, dine-in vs takeaway, สัดส่วนผู้สูงวัย) อาจต่างจากสมมติฐานมาก ต้องรอคำตอบ NEED-INPUT หรือข้อมูลหลังเปิดร้านจริงก่อนใช้ตัดสินใจ design ที่ลงทุนสูง — ไม่บล็อกการทำ Journey Map ต่อในตอนนี้

**skill ที่ใช้:** scrutinize (ตรวจสอบว่า persona ไม่ได้ผูกติดกับ role label ตรง ๆ จาก backlog เฉย ๆ แต่มี insight เพิ่มที่ช่วยการออกแบบจริง และตรวจว่า ป้าน้อยไม่ได้ถูกจัดเป็น primary ทั้งที่ไม่ตรงกับ MVP scope จริง), management-talk (สรุป primary/secondary และ NEED-INPUT ให้ตัดสินใจง่าย ไม่ทิ้งเป็น raw list)
