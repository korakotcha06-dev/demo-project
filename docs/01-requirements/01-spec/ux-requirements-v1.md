## 0. จุดประสงค์ของเอกสาร

- **COULSON/SHURI** ใช้เป็นเกณฑ์ตัดสินว่า wireframe/design system ที่ออกแบบ "ผ่าน" หรือ "ไม่ผ่าน" ก่อนเริ่ม build
- **OKOYE** ใช้แปลงเป็น usability test case ใน `03-testing` โดยไม่ต้องตีความเอง

เอกสารนี้ไม่ทำหน้าที่แทน `02-design` — ไม่มีการเลือกสี ฟอนต์ หรือ layout ในนี้ มีแต่ *เกณฑ์ที่การเลือกเหล่านั้นต้องทำให้ผ่าน*

## 1. UX Principles

หลักการต่อไปนี้ derive ตรงจากโจทย์ตั้งต้น + persona แต่ละคน แต่ละข้อผูกกับเหตุผลที่มาชัดเจน เพื่อไม่ให้ทีมออกแบบตีความหลักการลอย ๆ เอง

1. **สแกนแล้วถึงเมนูทันที ไม่มีหน้ากลาง** — มาจาก US-01 (ยืนยันแล้วโดย Touช รอบ feedback ที่ 3) และ persona ฟ้า (P1) ที่มีเวลาพักเที่ยงจำกัด 15-20 นาที ทุกวินาทีที่เสียไปกับหน้า splash คือเวลาที่หักออกจากเวลาที่เธอจะได้นั่งพัก
2. **ไม่ต้องติดตั้งแอป ไม่ต้องสมัครสมาชิกก่อนสั่ง** — มาจาก Business Rule ข้อ 8 (guest ordering) และ US-01/US-02 เหตุผลคู่: ลดแรงเสียดทานให้ฟ้า/ต้น (P1/P2) ที่รีบ และไม่เพิ่มอุปสรรคให้ป้าน้อย (P3) ที่ไม่คุ้นการสมัครสมาชิกออนไลน์
3. **ทุกจอต้องมีทางออกที่ไม่ใช่ "งมเอง"** — มาจาก persona ป้าน้อย (P3) และ US-30 (พนักงานคีย์แทน) ทุกจุดที่ลูกค้าอาจติดขัด (สแกนไม่เป็น, กดผิด, ไม่มั่นใจ) ต้องมีทางเรียกพนักงานหรือสั่งด้วยปากเปล่าได้เสมอ โดยไม่ทำให้รู้สึกถูกปฏิเสธ
4. **สถานะของออเดอร์ต้องสื่อสารได้โดยไม่ต้องถาม** — มาจาก US-05/US-14 และ pain point ของฟ้า ("อยากรู้สถานะแบบไม่ต้องเดินไปถาม") การออกแบบต้องลดการพึ่งพา "เดินไปถามพนักงาน" ให้เหลือน้อยที่สุด ทั้งฝั่งลูกค้าและฝั่งจุดรับของ takeaway
5. **กฎการจ่ายเงินต้องสื่อสารต่างกันตามช่องทางอย่างชัดเจน ไม่ปล่อยให้ลูกค้าเดา** — มาจาก Business Rule ข้อ 3 และ 12 (dine-in จ่ายทีหลังไม่บล็อกครัว vs takeaway ต้องจ่ายก่อนเสมอ) และ persona ต้น (P2) ที่ pain point ตรงคือ "กลัวสับสนว่าต้องจ่ายเงินตรงไหน/เมื่อไหร่"
6. **ออกแบบให้ใช้ได้ในสภาพมือไม่พร้อม ไม่ใช่แค่สภาพห้องแล็บ** — มาจาก persona เบียร์ (P4): มือเปียก/เปื้อนระหว่างชงกาแฟ, เสียงเครื่องชงกลบเสียงแจ้งเตือน, ต้องดูจอสลับกับมือที่ไม่ว่าง หน้าจอฝั่งพนักงานต้องออกแบบสำหรับสถานการณ์นี้เป็นค่าเริ่มต้น ไม่ใช่กรณีพิเศษ
7. **ป้าน้อยคือ validation gate ของทุก flow หลัก ไม่ใช่ persona ที่ถูกมองข้าม** — ตามที่ระบุใน [[ux-persona-v1|UX Persona v1]] หัวข้อ 3 ทุก flow ที่ "เสร็จ" สำหรับฟ้าต้องถูกตรวจซ้ำผ่านสายตาของป้าน้อยก่อนถือว่าพร้อมส่งต่อ design จริง

## 2. Usability Requirements ที่วัดผลได้

ตารางนี้คือเกณฑ์หลักที่ SHURI ต้องออกแบบให้ผ่าน และ OKOYE ต้องทดสอบใน `03-testing`

| UX-ID | ข้อกำหนด | เกณฑ์วัดผล | Persona ที่เกี่ยวข้อง | US/BR ที่เกี่ยวข้อง |
|---|---|---|---|---|
| UX-01 | สแกน QR ถึงเห็นหน้าเมนู ไม่มีหน้ากลาง | ไม่มี splash/landing page คั่น (0 หน้ากลาง); เวลาโหลดจนเห็นเมนูพร้อมสั่งได้ ≤ 3 วินาทีบนเน็ต 4G ปกติ และ ≤ 5 วินาที เมื่อจำลองเน็ตร้านช้า (throttle "Slow 3G") | P1 ฟ้า, P2 ต้น | US-01 |
| UX-02 | จำนวนขั้นตอนจากสแกนถึงยืนยันออเดอร์รอบแรก (1 สินค้า ไม่มีตัวเลือกซับซ้อน) | ≤ 6 tap รวม (เลือกสินค้า → เพิ่มตะกร้า → ยืนยัน); เวลารวมสำหรับผู้ใช้ทักษะสูง (ฟ้า) ≤ 90 วินาที ในการทดสอบ | P1 ฟ้า | US-01, US-02, US-03, US-04 |
| UX-03 | แก้ไข/ลบรายการในตะกร้าก่อนยืนยัน | แก้จำนวนหรือลบ 1 รายการทำได้ภายใน ≤ 2 tap; ต้องมีขั้นตอนยืนยันส่งออเดอร์ (explicit confirm) แยกจากปุ่ม "เพิ่มลงตะกร้า" เสมอ — ห้ามส่งออเดอร์เข้าครัวโดยไม่มีการกดยืนยันรอบสุดท้าย | P1 ฟ้า | US-03, US-04 |
| UX-04 | ความชัดของสถานะออเดอร์แบบเรียลไทม์ | ฝั่งลูกค้าเห็นสถานะเปลี่ยนภายใน ≤ 5 วินาทีหลังพนักงานกดเปลี่ยนสถานะ โดยไม่ต้องกดรีเฟรชเอง; แสดงอย่างน้อย 3 สถานะ (รอดำเนินการ/กำลังทำ/เสร็จแล้ว) ด้วย label ข้อความ + สัญลักษณ์ (ไม่ใช้สีเป็นตัวบ่งชี้เดี่ยว) | P1 ฟ้า, P4 เบียร์ | US-05, US-14 |
| UX-05 | สั่งเพิ่มรอบสอง (reorder) โดยไม่สแกนซ้ำ | จากหน้าสถานะออเดอร์กลับไปหน้าเมนูได้ภายใน 1 tap; session/ตะกร้าคงอยู่ต่อเนื่องอย่างน้อย 60 นาทีนับจากยืนยันออเดอร์รอบแรก ตราบใดที่โต๊ะยังไม่ปิดบิล | P1 ฟ้า | US-06 |
| UX-06 | ตะกร้าแชร์หลายคน/หลายอุปกรณ์ต่อโต๊ะแบบ concurrent | 2 อุปกรณ์เพิ่มสินค้าเข้าตะกร้าเดียวกันพร้อมกัน ต้องเห็นรายการของกันและกันครบภายใน ≤ 5 วินาที โดยไม่มีรายการหายหรือถูกเขียนทับ (0% data loss ในการทดสอบ concurrent write อย่างน้อย 3 รอบ) | P1 ฟ้า | Business Rule ข้อ 2 |
| UX-07 | สื่อสารกฎจ่ายเงิน dine-in (จ่ายทีหลัง ไม่บล็อกครัว) | หลังยืนยันออเดอร์ ต้องมีข้อความชัดเจนว่าออเดอร์เข้าครัวแล้วและ "จ่ายที่เคาน์เตอร์ตอนจะกลับ"; ผู้ทดสอบ ≥ 90% เข้าใจถูกต้องโดยไม่ต้องถามซ้ำในการทดสอบ usability | P1 ฟ้า | Business Rule ข้อ 3, US-04, US-07 |
| UX-08 | สื่อสารกฎจ่ายเงิน takeaway (mandatory prepay ก่อนเข้าครัว) | ≥ 95% ของผู้ทดสอบเข้าใจว่าต้องไปจ่ายที่เคาน์เตอร์ก่อน ออเดอร์จึงจะเข้าครัว และไม่เข้าใจผิดว่าออเดอร์ถูกส่งไปทำแล้ว | P2 ต้น | Business Rule ข้อ 12, US-28 |
| UX-09 | หน้าจอพนักงานใช้งานได้ในสภาพมือเปียก/เปื้อน | พื้นที่กดของปุ่มสถานะหลัก (เปลี่ยนสถานะออเดอร์, มาร์กหมด) ≥ 48×48px พร้อมระยะห่างระหว่างปุ่ม ≥ 8px; อัตราการกดพลาด (mis-tap) ในการทดสอบจำลองมือเปียก ≤ 5% | P4 เบียร์ | US-13, US-14, US-15, US-16 |
| UX-10 | แยกที่มาออเดอร์ให้มองออกในพริบตา (โต๊ะ/เคาน์เตอร์, ลูกค้าสั่งเอง/พนักงานคีย์แทน) | ต้องมี tag ที่แยกด้วยข้อความ+ไอคอนร่วมกัน (ไม่ใช้สีเดี่ยว); ผู้ทดสอบ (เบียร์) อ่านแยกที่มาออเดอร์ถูกต้องภายใน ≤ 2 วินาที จากระยะจอสถานีปกติ (~50-80 ซม.) | P4 เบียร์ | Business Rule ข้อ 12, US-13, US-29, US-30 |
| UX-11 | แอดมินแก้เมนู/ราคาได้เองโดยไม่ต้องพึ่งโปรแกรมเมอร์ | ผู้ทดสอบระดับทักษะดิจิทัลต่ำ-ปานกลาง (แทนคุณแอน) เพิ่มสินค้าใหม่ 1 รายการสำเร็จภายใน ≤ 5 นาทีในการใช้งานครั้งแรก โดยไม่อ่านคู่มือ; success rate ≥ 90% ในการทดสอบ | P5 คุณแอน | US-23, US-24 |
| UX-12 | สรุปยอดรวมโต๊ะก่อนไปจ่ายเงิน อ่านเข้าใจได้ทันที | หน้าสรุปยอด (US-07) ต้องแสดงยอดสุทธิเป็นตัวเลขเด่นที่สุดในหน้า อ่านเจอภายใน ≤ 3 วินาทีแรกที่เปิดหน้า โดยไม่ต้องเลื่อนจอ (above the fold) บนมือถือจอ ≥ 5 นิ้ว | P1 ฟ้า, P2 ต้น | US-07 |

## 3. Accessibility & Inclusivity Requirements

อ้างอิง **WCAG 2.1 ระดับ AA** เป็นเกณฑ์ตั้งต้น (ดูหัวข้อ 11 สำหรับ NEED-INPUT ว่าจะยึดเต็มรูปแบบใน MVP หรือไม่):

| หัวข้อ | เกณฑ์ขั้นต่ำ | อ้างอิง |
|---|---|---|
| ขนาดตัวอักษร | ข้อความเนื้อหาปกติ ≥ 16px (1rem); รองรับ browser zoom ถึง 200% โดยเนื้อหาไม่ถูกตัด/ทับกัน | WCAG 1.4.4 |
| Contrast ratio | ข้อความปกติ ≥ 4.5:1, ข้อความขนาดใหญ่/ไอคอนสำคัญ ≥ 3:1 กับพื้นหลัง — ต้องผ่านทั้งในสภาพจอปกติและจอกลางแดด (ดูหัวข้อ 4) | WCAG 1.4.3 |
| ขนาดพื้นที่กด | ปุ่ม/พื้นที่กดฝั่งลูกค้า ≥ 44×44px ขั้นต่ำ; ปุ่มฝั่งพนักงาน (เบียร์) ≥ 48×48px ตาม UX-09 | WCAG 2.5.5 (แนวปฏิบัติ) |
| ไม่พึ่งพาสีเดี่ยว | ทุกจุดที่สื่อความหมายด้วยสี (สถานะออเดอร์, สินค้าหมด, ที่มาออเดอร์) ต้องมีข้อความหรือไอคอนกำกับเสมอ | WCAG 1.4.1 |
| ภาษา | เนื้อหาหลักเป็นภาษาไทย — การรองรับภาษาอังกฤษเต็มรูปแบบเป็น US-10 (P2/Phase 2) ไม่บังคับใน MVP แต่ label ที่ใช้ศัพท์เทคนิคควรมีคำไทยกำกับเสมอ (ดูหัวข้อ 7 glossary) | ดู NEED-INPUT ข้อ 1 |
| กรณีป้าน้อย (P3) | ทุก flow หลักต้องผ่านการทดสอบซ้ำกับผู้ใช้ระดับทักษะดิจิทัลต่ำ/สายตาไม่ดี ก่อนถือว่า "เสร็จจริง" ตามหลักการข้อ 7 | Persona P3 |
| Fallback ให้พนักงานช่วยสั่ง | ทุกจุดที่ลูกค้าอาจติดขัดในการสแกน/สั่งเอง ต้องมีทางเรียกพนักงานหรือให้พนักงานคีย์แทน (US-30) ที่เข้าถึงได้โดยไม่ต้องหาเอง (เช่น ป้ายบอกไว้ที่โต๊ะ/เคาน์เตอร์) — ไม่ใช่ทางเลือกที่ซ่อนอยู่ | US-30, Persona P3 |

## 4. Mobile-First & ข้อจำกัดสภาพจริง

ระบบต้องออกแบบโดยตั้งต้นจากสภาพการใช้งานจริงของร้าน ไม่ใช่สภาพห้องแล็บที่มีเน็ตแรงและจอสว่างสบายตา:

- **มือถือลูกค้าหลากรุ่น** — ต้องทดสอบบนอย่างน้อย 1 รุ่นจอเล็ก (~5 นิ้ว) และ 1 รุ่นจอใหญ่ (~6.5 นิ้ว+) ทั้ง iOS/Android เวอร์ชัน browser ที่ไม่ใหม่ล่าสุด (ย้อนหลังอย่างน้อย 1-2 ปี)
- **เน็ตร้านช้า/สัญญาณอ่อน** — ทุกหน้าที่มีผลต่อการสั่ง (เมนู, ตะกร้า, ยืนยันออเดอร์) ต้องมี loading state ที่ชัดเจน และต้อง "fail safe" คือไม่ยืนยันว่าสำเร็จจนกว่าเซิร์ฟเวอร์ตอบกลับจริง (ดู UX-13 ในหัวข้อ 5 เรื่องเน็ตหลุดกลางสั่ง)
- **จอกลางแดด** — contrast ratio ในหัวข้อ 3 ต้องคงอยู่แม้อยู่ในสภาพแสงแดดจ้า หลีกเลี่ยงการออกแบบที่พึ่งพา contrast ต่ำ (เช่น เทาอ่อนบนขาว) แม้จะดูสวยในจอห้องแอร์
- **มือเปียกของบาริสต้า (P4 เบียร์)** — ตามหลักการข้อ 6 และ UX-09 ปุ่มต้องใหญ่พอและไม่ต้องการความแม่นยำสูง หลีกเลี่ยง gesture ซับซ้อน (swipe, long-press) สำหรับ action หลัก
- **จอครัว-บาร์ต้องอ่านจากระยะไกล** — ตัวอักษร/ตัวเลขสำคัญ (เลขโต๊ะ, จำนวนรายการ) บนจอสถานีต้องอ่านออกจากระยะที่พนักงานยืนทำงานจริง (สมมติฐาน ~50-80 ซม. — ดู NEED-INPUT ข้อ 3 เรื่องอุปกรณ์จริง) ไม่ใช่ขนาดที่ออกแบบมาสำหรับดูใกล้ ๆ แบบมือถือ

## 5. Error, Empty & Edge States

| กรณี | ผู้ใช้ต้องเห็นอะไร | ต้องทำอะไรต่อได้ |
|---|---|---|
| สแกน QR ไม่ติด/ไม่ทำงาน | ข้อความเข้าใจง่ายว่าสแกนไม่สำเร็จ (ไม่ใช่ error code ทางเทคนิค) | เห็นทางเลือกเรียกพนักงานหรือแจ้งเลขโต๊ะด้วยปากเปล่าทันที (เชื่อมกับ US-30 fallback) |
| เมนูสินค้าหมด | สินค้าที่หมดชั่วคราวแสดง label "หมดชั่วคราว" ชัดเจน ปุ่มกดถูกปิดใช้งาน (ไม่ใช่ซ่อนหายไปเฉย ๆ) | เลือกสินค้าอื่นในเมนูต่อได้ตามปกติโดยไม่ต้องรีเฟรชหน้า |
| ร้านปิดรับออเดอร์ | ข้อความ "ร้านปิดรับออเดอร์แล้ว" แทนที่หน้าเมนูทั้งหมด | ไม่มีปุ่มสั่งอาหารให้กด — ถ้ามีข้อมูลเวลาเปิดร้านครั้งถัดไป ควรแสดงไว้ |
| ตะกร้าว่าง | Empty state ที่บอกว่ายังไม่มีรายการ ไม่ใช่หน้าจอเปล่า/ค้าง | มีปุ่ม/ลิงก์ให้กลับไปหน้าเมนูได้ทันที |
| เน็ตหลุดกลางสั่ง (ระหว่างกดยืนยันออเดอร์) | แจ้งเตือนว่าการเชื่อมต่อขาดหาย — **ห้ามแสดงว่ายืนยันสำเร็จจนกว่าเซิร์ฟเวอร์ยืนยันกลับจริง** | มีปุ่มลองส่งใหม่ (retry); รายการในตะกร้าต้องไม่หายระหว่างรอเชื่อมต่อกลับมา |
| ออเดอร์ซ้ำ (กดยืนยันซ้ำ/double-submit) | ฝั่งลูกค้า: ปุ่มยืนยันถูกปิดใช้งานทันทีหลังกดครั้งแรกเพื่อกันกดซ้ำ | ถ้าเกิดออเดอร์ซ้ำจริง พนักงาน (เบียร์) ต้องเห็นทั้งสองออเดอร์แยกกันชัดพร้อมเวลา และยกเลิกออเดอร์ที่ซ้ำได้ผ่านกลไกเดียวกับ US-20 |
| จ่ายเงินไม่สำเร็จ (ช่องทางเคาน์เตอร์ — ลูกค้าเปลี่ยนใจ/เงินไม่พอ) | ออเดอร์ยังคงอยู่ในสถานะ "รอยืนยันการชำระเงิน" ไม่เข้าครัว จนกว่าจะมีการยืนยันจริง | แคชเชียร์ (เบียร์) ยกเลิกออเดอร์ที่ไม่จ่ายเงินได้ผ่านกลไกเดียวกับ US-20/US-29 |

## 6. Content & Tone Guideline

**หลักการใช้ภาษากับลูกค้า:**

- สุภาพ กระชับ ไม่ใช้ศัพท์เทคนิค (เลี่ยงคำเช่น "session", "checkout", "submit" ในข้อความที่ลูกค้าเห็น — ใช้คำไทยธรรมดาแทน)
- ข้อความ error/แจ้งเตือนต้องบอก "ทำอะไรต่อได้" เสมอ ไม่ใช่แค่บอกว่าผิดพลาด (ดูตารางหัวข้อ 5)
- ข้อความที่เกี่ยวกับเงิน (เมื่อไหร่ต้องจ่าย, จ่ายที่ไหน) ต้องเขียนให้กำกวมไม่ได้ — เป็นจุดที่ persona ต้น (P2) กังวลที่สุด

**Glossary — คำที่ต้องนิยามให้ตรงกันทั้งระบบ (ลูกค้า/พนักงาน/แอดมิน ต้องเห็นคำเดียวกันสื่อความหมายเดียวกัน):**

| คำ | นิยาม |
|---|---|
| ตะกร้า | รายการสินค้าที่เลือกไว้แต่ **ยังไม่ได้กดยืนยัน** ส่งเข้าครัว แก้ไข/ลบได้อิสระ |
| ออเดอร์ | รายการที่ **กดยืนยันส่งเข้าครัวแล้ว** ในรอบหนึ่ง — แก้ไขเองไม่ได้อีกหลังจากนี้ (ต้องผ่านพนักงาน) |
| โต๊ะ | หน่วยของ session ที่ผูกกับ QR โต๊ะหนึ่งใบ 1 โต๊ะอาจมีหลายออเดอร์ต่อเนื่องกันจนกว่าจะปิดบิล |
| รอบลูกค้า | ช่วงเวลาตั้งแต่โต๊ะเปลี่ยนสถานะเป็น "ไม่ว่าง" (มีออเดอร์แรก) จนถึงปิดบิล (โต๊ะกลับเป็น "ว่าง") |
| บิล | ยอดรวมสุทธิของ**ทุกออเดอร์**ในรอบลูกค้าเดียวกันของโต๊ะนั้น ปิดบิลเมื่อพนักงานยืนยันชำระเงินครบ |
| ปลายเคาน์เตอร์ | จุดรับของสำหรับช่องทาง takeaway (ทั้งลูกค้าสั่งเองและพนักงานคีย์แทน) แยกจากจุดสั่ง/จ่ายเงิน |
| สถานะออเดอร์ | 3 ค่า: รอดำเนินการ / กำลังทำ / เสร็จแล้ว — ใช้คำเดียวกันทั้งฝั่งลูกค้าและฝั่งพนักงาน ห้ามใช้คำพ้องความหมายต่างกันคนละหน้าจอ |

## 7. เกณฑ์การยอมรับสำหรับ Usability Test (ส่งต่อ OKOYE)

Week 3 นี้ถือว่า **"UX พร้อมส่งต่อ design"** เมื่อผ่านเงื่อนไขต่อไปนี้ทั้งหมด — OKOYE ใช้เป็นฐานเขียน test plan ใน `03-testing`:

1. ทุกแถวในตาราง Usability Requirements (หัวข้อ 2) มีเกณฑ์วัดผลที่เป็นตัวเลข/เงื่อนไขชัดเจน — ไม่มีข้อไหนเขียนว่า "ใช้งานง่าย" ลอย ๆ (ผ่านแล้วในเอกสารนี้)
2. ต้องทดสอบ flow หลัก (สแกน→เมนู→ตะกร้า→ยืนยัน→ติดตามสถานะ) กับผู้ใช้ตัวแทนอย่างน้อย 3 กลุ่ม: ฟ้า (happy path, วัดเวลา/จำนวน tap), ป้าน้อย (worst-case accessibility — วัด success rate ไม่ใช่แค่ทำได้/ไม่ได้), เบียร์ (สถานีพนักงานภายใต้สภาพจำลองมือเปียก/เสียงดัง)
3. ทุกกรณีในตาราง Error/Empty/Edge States (หัวข้อ 5) ต้องมี wireframe ที่ตอบครบทั้ง "ผู้ใช้เห็นอะไร" และ "ทำอะไรต่อได้" — ไม่ปล่อยเป็น dead-end screen
4. ผ่านการตรวจ contrast ratio และขนาดตัวอักษร/ปุ่มขั้นต่ำตามหัวข้อ 3 ด้วยเครื่องมืออัตโนมัติ (เช่น axe, Lighthouse accessibility audit) ก่อนเข้าสู่ `03-testing` เต็มรูปแบบ
5. Business Rule ข้อ 2 (concurrent cart), ข้อ 3/12 (กฎจ่ายเงินตามช่องทาง) ต้องมี test case เฉพาะ ไม่ใช่ทดสอบรวมกับ flow ปกติ เพราะเป็นจุดเสี่ยงสูงสุดที่ persona ระบุ pain point ไว้ตรง ๆ

## 9. NEED-INPUT / คำถามถึง Touch

ประเด็นต่อไปนี้ต้องให้ Touch ตัดสินใจในฐานะ CEO เพราะกระทบต้นทุนการพัฒนาและทิศทางที่ XAVIER ไม่ควรเดาแทน ไม่บล็อกการเริ่ม `02-design` — COULSON/SHURI ใช้สมมติฐาน default ที่ระบุไว้ในเอกสารนี้ไปก่อนได้:

1. **รองรับสองภาษา (ไทย/อังกฤษ) ใน MVP หรือไม่?** — ปัจจุบัน US-10 เป็น P2/Phase 2 ตาม backlog อยู่แล้ว เอกสารนี้ยึดตามนั้น (ไม่บังคับ multi-language ใน Phase 0) แต่ถ้า Touch ต้องการเลื่อนขึ้นมาเร็วกว่านั้น จะกระทบโครงสร้าง content ที่ SHURI ต้องเผื่อไว้ตั้งแต่ต้น
2. **ยอมรับ WCAG 2.1 ระดับ AA แบบเต็มรูปแบบใน MVP หรือระดับที่เบากว่า?** — เอกสารนี้ตั้งสมมติฐานว่า MVP ต้องผ่านอย่างน้อย contrast ratio + ขนาดตัวอักษร/ปุ่ม + ไม่พึ่งสีเดี่ยว (รายการหลักที่ทดสอบง่ายและกระทบต้นทุนน้อย) ส่วนการรองรับ screen reader เต็มรูปแบบยังไม่ได้ตั้งเป็นเกณฑ์บังคับ Phase 0 — ถ้า Touch ต้องการเต็มรูปแบบตั้งแต่ MVP ต้องแจ้งกลับเพราะกระทบ scope/เวลาออกแบบและพัฒนา
3. **จอครัว-บาร์ (สถานีของเบียร์) ใช้อุปกรณ์อะไรจริง?** (แท็บเล็ต / จอคอมพิวเตอร์ตั้งเคาน์เตอร์ / เครื่องพิมพ์สลิปกระดาษ) — เอกสารนี้ตั้งสมมติฐานระยะการอ่าน ~50-80 ซม. แบบแท็บเล็ตวางเคาน์เตอร์ (UX-10, หัวข้อ 4) ถ้าอุปกรณ์จริงต่างจากนี้ (เช่น พิมพ์สลิปกระดาษเป็นหลัก) เกณฑ์ขนาดตัวอักษร/ปุ่มในตารางหัวข้อ 2-3 ต้องปรับใหม่
4. **เกณฑ์เวลาที่ยอมรับได้ของเน็ตร้าน (3-5 วินาที ใน UX-01) เป็นค่าที่ Touch ยืนยันแล้วหรือเป็นแค่ค่ามาตรฐานอุตสาหกรรมที่ XAVIER ตั้งสมมติฐานไว้?** — ถ้าเน็ตร้านจริงช้ากว่านี้มาก (พบได้บ่อยในร้านเล็กที่ใช้ WiFi บ้าน/มือถือแชร์เน็ต) ควรทราบล่วงหน้าเพื่อ COULSON วางแผน caching/offline-friendly design ตั้งแต่ architecture

---

ส่งงาน — XAVIER → ทัช (งาน / ผลลัพธ์ / ค้าง-เสี่ยง / skill ที่ใช้)

**งาน:** ร่างเอกสาร UX Requirements (DRAFT) สำหรับระบบสั่งอาหารด้วย QR code — แปลง UX Persona v1 + Product Backlog v1 ให้เป็นข้อกำหนดด้าน UX ระดับวัดผลได้/ทดสอบได้ ครอบคลุม UX principles, usability requirements table, accessibility (WCAG 2.1 AA), mobile-first constraints, error/edge states, content/tone glossary, และเกณฑ์ยอมรับ usability test

**ผลลัพธ์:** ไฟล์ `docs/01-requirements/01-spec/ux-requirements-v1.md` — UX Principles 7 ข้อผูกกับ persona/US, ตาราง Usability Requirements 12 รายการ (UX-01 ถึง UX-12) ครอบคลุมทุกจุดที่โจทย์ระบุ (เวลา/ขั้นตอนจากสแกน→ยืนยัน, สถานะออเดอร์, แก้ไข/ยกเลิกก่อนยืนยัน, สั่งซ้ำ, ตะกร้าแชร์หลายคน, จ่ายเงิน dine-in vs takeaway), accessibility requirements ตาม WCAG 2.1 AA, ตาราง error/edge state 7 กรณี, glossary 6 คำ, เกณฑ์ยอมรับ usability test 5 ข้อสำหรับ OKOYE, และ NEED-INPUT 4 ข้อถึง Touch

**ค้าง/เสี่ยง:** เกณฑ์ตัวเลขทั้งหมด (เวลาโหลด, จำนวน tap, contrast ratio) เป็นค่าอ้างอิงมาตรฐานอุตสาหกรรม/WCAG ที่ยังไม่ผ่านการยืนยันกับสภาพร้านจริง (เน็ตจริง, อุปกรณ์จอครัว-บาร์จริง) — เสี่ยงต้องปรับตัวเลขหลังเปิดร้านจริงหรือเมื่อ Touch ตอบ NEED-INPUT ข้อ 3-4 ไม่บล็อกการเริ่ม `02-design` เพราะ COULSON/SHURI ใช้สมมติฐาน default ในเอกสารนี้ไปก่อนได้

**skill ที่ใช้:** scrutinize (ตรวจว่าทุกข้อกำหนดมีเกณฑ์วัดผลจริงไม่ใช่คำคุณศัพท์ลอย ๆ และตรวจว่าไม่ได้ไปทำ wireframe/design system แทน 02-design), management-talk (แยก NEED-INPUT ที่ต้องให้ CEO ตัดสินออกจากสมมติฐาน default ที่ทีมออกแบบใช้ไปก่อนได้ ไม่ทิ้งเป็น raw requirement list)
