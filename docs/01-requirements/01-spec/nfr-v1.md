## 0. เอกสารนี้คืออะไร และไม่ใช่อะไร

**เป็น:** ทะเบียนกลาง (register) ของข้อกำหนดเชิงคุณภาพทั้งระบบ ที่ให้ **ID เดียวต่อ 1 ข้อกำหนดที่วัดผลได้** เพื่อให้ OKOYE เขียน test case อ้าง ID ได้ และให้ COULSON ตรวจได้ว่าออกแบบรองรับครบหรือยัง

**ไม่ใช่:** การเขียน requirement ใหม่ทับของเดิม — **NFR แทบทุกข้อในเอกสารนี้มีอยู่แล้ว** ในเอกสารต้นทาง (backlog §3 Business Rules หรือ [[ux-requirements-v1|UX Requirements v1]]) เอกสารนี้แค่ **รวบมาไว้ที่เดียวและติด ID ให้**

### กฎการอยู่ร่วมกับ ID เดิม (สำคัญ — อ่านก่อนใช้)

1. **ไม่มีการลบหรือเปลี่ยนเลข `Business Rule ข้อ N` หรือ `UX-xx` เดิมแม้แต่ตัวเดียว** — มีการอ้างอิงเลขเหล่านี้กระจายอยู่ทั่วทั้ง `01-requirements` และ `02-design` กว่า 40 จุด การเลื่อนเลขคือการทำลิงก์พังทั้งโปรเจกต์
2. **เอกสารต้นทางยังเป็น source of truth ของ "เนื้อหา"** — `NFR-xx` เป็น source of truth ของ **"เกณฑ์ที่ใช้ทดสอบ"** ถ้าเนื้อหาขัดกัน ให้ยึดเอกสารต้นทางแล้วแจ้ง XAVIER มาแก้ทะเบียนนี้
3. **NFR ที่ไม่มีต้นทาง (คอลัมน์ "ต้นทาง" = 🆕)** คือข้อที่เอกสารนี้เป็นเจ้าภาพเอง — เกิดจากช่องว่างที่ audit พบว่าไม่มีใครเขียนไว้ที่ไหนเลย
4. **ทุก NFR มีเกณฑ์ที่วัดผลได้เสมอ** — ถ้าเขียนเกณฑ์ที่วัดไม่ได้ แปลว่ายังไม่พร้อมเป็น NFR

### วิธีอ่านคอลัมน์ "Design"

✅ = `02-design` ออกแบบรองรับแล้วและระบุไว้ชัด · ⚠️ = รองรับบางส่วน · ❌ = **ไม่มีในชั้น design เลย** (ต้องส่งกลับ COULSON)

## 8. NEED-INPUT

1. **ระดับ WCAG ที่ยึดจริง** — NFR-19 อ้างเกณฑ์ระดับ AA แต่ [[ux-requirements-v1|UX Requirements v1]] §9 ยังเปิด NEED-INPUT ข้อนี้ค้างอยู่ · **Default ที่ใช้ไปก่อน:** WCAG 2.1 ระดับ AA
2. **เกณฑ์ mis-tap ≤5% ของ NFR-20 ต้องทดสอบอย่างไรให้ซ้ำได้** — ยังไม่มีวิธีทดสอบที่นิยามชัด เป็นเรื่องที่ OKOYE ควรออกแบบวิธีวัดตอนทำ test plan ไม่ใช่ตัวบล็อกของ NFR นี้
3. **อุปกรณ์จริงของจอสถานี** — กระทบ NFR-06/10/11 ทั้งสามข้อ (จำนวนเครื่อง, พฤติกรรม lock screen ของ OS) · ตรงกับ NEED-INPUT ข้อ 3 ของ [[ux-requirements-v1|UX Requirements v1]] และ screen-inventory §5 ข้อ 1 ที่ยังไม่มีคำตอบ
