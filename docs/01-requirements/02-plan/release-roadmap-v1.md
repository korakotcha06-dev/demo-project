หลักการจัดลำดับ: Phase 0 คือ MVP บางที่สุดที่ยังครบ flow หลัก "สแกน QR → ดูเมนู → สั่งออเดอร์ → ออเดอร์ไปถึงครัว/แจ้งเตือน → จ่ายเงินจบบิล" ได้จริงโดยไม่มีพนักงานมารับออเดอร์ที่โต๊ะ ทั้งช่องทางโต๊ะ (dine-in) และเคาน์เตอร์ (takeaway) พร้อมตัวเลือกระดับการคั่ว/เมล็ดพิเศษที่เป็นแก่นของกาแฟเอง ฟีเจอร์เสริม (ตัวเลือกสินค้าอื่นที่ไม่ใช่คั่ว/เมล็ด, ใบเสร็จ, รายงาน, หลายภาษา, จ่ายเงินออนไลน์สำหรับ dine-in, multi-station) เลื่อนไป Phase ถัดไปทั้งหมด ยกเว้น loyalty stamp card ที่เลื่อนมาอยู่ Phase 1 แล้ว — สำหรับ Phase 0 พนักงานฝั่งร้าน (ครัว/บาร์ + แคชเชียร์) เป็น**บทบาทเดียว**สำหรับร้านนี้ (ดู Business Rule ข้อ 13)

**Exit criteria ของ Phase 0 (เพิ่ม 2026-08-12):** ลูกค้าที่เข้าร้านครั้งแรกต้องรู้ได้เองจากป้ายที่โต๊ะ/เคาน์เตอร์ว่าสั่งเองได้และต้องจ่ายเงินตอนไหน โดยไม่มีพนักงานเดินไปอธิบาย **และ** ลูกค้าซื้อกลับต้องอ้างอิงออเดอร์ของตัวเองกับพนักงานได้ด้วยเลขคิว (รวมถึงลูกค้าที่ไม่มีมือถือ ซึ่งพนักงานเรียกด้วยเลขคิวได้) **และ** ออเดอร์ที่ลูกค้ารับของไปแล้วต้องหลุดออกจากคิวหน้าจอพนักงานเอง **และ** พนักงาน 2–4 คนใช้หน้าจอสถานีพร้อมกันได้โดยไม่เด้งกันออกและไม่ทำงานซ้ำกัน — นอกเหนือจากเกณฑ์เดิมด้านล่างนี้:

**Exit criteria ของ Phase 0:** ลูกค้าจริงในร้านสามารถสแกน QR แล้วสั่ง-รับ-จ่ายเงินจบ 1 รอบการนั่งโต๊ะได้ โดยไม่มีพนักงานมารับออเดอร์ที่โต๊ะเลยแม้แต่ครั้งเดียว **และ** ลูกค้าที่มาซื้อกลับสามารถสแกน QR เคาน์เตอร์ สั่ง จ่ายเงินก่อน แล้วรอรับของได้ครบ โดยไม่ต้องบอกพนักงานปากเปล่าเช่นกัน **และ** ลูกค้าที่ต้องการสั่งด้วยวาจาแบบร้านกาแฟทั่วไป (ไม่สแกน QR เลย) สามารถให้แคชเชียร์คีย์ออเดอร์+รับเงินแทนได้ แล้วเข้าคิวเดียวกับออเดอร์เคาน์เตอร์อื่น ๆ จนกว่าจะมารับที่ปลายเคาน์เตอร์ **และ** ลูกค้าที่สั่งเครื่องดื่มกาแฟเลือกระดับการคั่ว/เมล็ดพิเศษที่ร้านมีอยู่จริงตอนนั้นได้ (ไม่เลือกก็ได้เครื่องดื่มระดับ "กลาง" เป็นค่าเริ่มต้น) และแอดมินจัดการรายการเมล็ดพิเศษได้เอง

**หมายเหตุ (Week 3 / รอบ UX) — accessibility baseline ไม่ใช่งาน Phase 2:** Business Rule ข้อ 23 (accessibility baseline ตาม [[../01-spec/ux-requirements-v1|01-spec/ux-requirements-v1]] หัวข้อ 3 — ฟอนต์ ≥16px, contrast ≥4.5:1, พื้นที่กด ≥44px, ไม่พึ่งสีเดี่ยว) เป็น **non-functional requirement ของทุกหน้าจอฝั่งลูกค้าตั้งแต่ Phase 0** ไม่ใช่ของ US-40 (โหมดเข้าถึงง่ายแบบ toggle ที่ยังอยู่ Phase 2) — US-40 คือ "เพิ่มโหมดพิเศษให้ใหญ่กว่าเดิมอีกขั้น" ส่วน baseline คือมาตรฐานขั้นต่ำที่ทุกจอต้องผ่านอยู่แล้วโดยไม่ต้องรอ toggle ดูงานจริงที่แตกออกมาใน [[../03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] หัวข้อ "งานข้ามกลุ่ม"

**หมายเหตุ (Week 3 / รอบ UX) — US-41 อาจเลื่อนขึ้น Phase 0 (NEED-INPUT ที่ยังเปิด):** US-41 (จัดลำดับความสำคัญ+aging indicator ฝั่งพนักงานช่วง peak) วางไว้ที่ Phase 1 ตามการตัดสินใจของ Touch ในรอบนี้ แต่ [[../01-spec/ux-journey-map-v1|01-spec/ux-journey-map-v1]] หัวข้อ 7 ข้อ 2 ตั้งคำถามไว้ว่าถ้าช่วง peak overload เป็นสถานการณ์จริงตั้งแต่วันเปิดร้าน (ไม่ใช่แค่หลังร้านเดินเครื่องคล่องแล้ว) ควรดัน US-41 ขึ้นมาเป็น Phase 0 แทน — **นี่คือ NEED-INPUT ที่ยังไม่ปิด** รอ Touch ยืนยันปริมาณออเดอร์ peak จริงก่อนตัดสินใจย้าย Phase ของ US-41 ไม่ใช่การตัดสินใจที่ปิดแล้วในรอบนี้

**หมายเหตุ (รอบ requirement กลุ่มงาน A/B) — US-42 เพิ่มสโคปจริงให้ Phase 0, US-43 แทบไม่เพิ่มสโคป:** สองรายการที่เพิ่งเข้า Phase 0 ในรอบนี้มีน้ำหนักทางเทคนิคต่างกันมาก อย่าปนกัน — **US-43 (ความหวาน)** แทบไม่เพิ่มสโคปทางเทคนิคเลย เพราะยืมกลไก option-group เดียวกับที่ US-35 (ระดับการคั่ว) ต้องสร้างอยู่แล้วใน Phase 0 อยู่ก่อนหน้านี้ งานที่เพิ่มจริงคือแค่ "เพิ่มข้อมูลตัวเลือก" (fixed-list 5 ค่า: 0/25/50/75/100%) เข้ากลไกที่มีอยู่ ไม่ใช่สร้างระบบใหม่ ตรงข้ามกับ **US-42 (จัดผังโต๊ะ)** ที่เพิ่มสโคปจริงให้ Phase 0 เพราะเป็นหน้าจอจัดการใหม่ทั้งหน้าฝั่งแอดมิน (เพิ่ม/แก้ชื่อ/จัดลำดับ-โซน/ปลดระวางโต๊ะ) ที่ไม่เคยมีอยู่ในสโคปเดิมมาก่อน ต้องนับเป็นงานเพิ่มของ Phase 0 ตรง ๆ ไม่ใช่ของฟรีที่ต่อยอดจากกลไกเดิมแบบ US-43 — รายละเอียดงานจริงที่แตกออกมาดูที่ [[../03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] กลุ่มงาน A (US-42) และกลุ่มงาน B (US-43)
