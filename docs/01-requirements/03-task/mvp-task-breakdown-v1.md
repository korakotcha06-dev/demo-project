## กลุ่มงาน A — โต๊ะ และ QR Code (รองรับ US-01, US-24, US-42)

- [ ] **(แก้ไข — รอบ requirement กลุ่มงาน A/B)** ~~กำหนดจำนวนโต๊ะเริ่มต้นของร้านและรูปแบบเลขโต๊ะ (เช่น T01–T20)~~ เดิมสมมติว่าจำนวนโต๊ะเป็นค่าคงที่ที่ fix ตอนเริ่มโปรเจกต์ — **ไม่จริงอีกต่อไปหลัง US-42** (เจ้าของร้านจัดผังโต๊ะเองและเพิ่มโต๊ะได้ภายหลังตลอดอายุการใช้งานร้าน) เปลี่ยนเป็น: กำหนด**รูปแบบการตั้งชื่อ/เลขโต๊ะที่แนะนำ** (เช่น T01, T02, ... เป็น pattern ให้แอดมินอ้างอิง) และใช้จำนวนโต๊ะเริ่มต้นเป็นเพียง**ตัวอย่างข้อมูลตั้งต้น (seed data) สำหรับทดสอบ** ไม่ใช่ค่าคงที่ของระบบ — จำนวน/ชื่อโต๊ะจริงเป็นข้อมูลที่เจ้าของร้านตั้งเองผ่านหน้าจัดการโต๊ะ (US-42) และเพิ่ม/แก้ได้ตลอด
- [ ] **(ใหม่ — US-42)** ส่งต่อ COULSON ออกแบบหน้าจอจัดการโต๊ะฝั่งแอดมิน: เพิ่มโต๊ะใหม่ / แก้ชื่อ-เลขโต๊ะ / จัดลำดับ-จัดกลุ่มโซน / ปลดระวางโต๊ะ — ต้องใช้งานได้จริงโดยคนไม่สายเทค (persona P5 คุณแอน ตาม [[../01-spec/ux-persona-v1|01-spec/ux-persona-v1]]) ไม่ใช่หน้าจอที่ต้องมีความรู้ด้านเทคนิคจึงจะใช้เป็น
- [ ] **(ใหม่ — US-42, กระทบ data model โดยตรง — ส่งต่อ COULSON ก่อน finalize schema)** table entity ต้องแยก **table id (internal, คงที่ตลอดไป)** ออกจาก **ชื่อ/เลขโต๊ะที่แสดงผล (แก้ไขได้)** อย่างเด็ดขาด — QR ที่พิมพ์ไปแล้วต้องผูกกับ id ไม่ใช่ชื่อที่แสดง เพื่อให้เจ้าของร้านเปลี่ยนชื่อโต๊ะทีหลัง (เช่น "โต๊ะ 5" → "โต๊ะริมหน้าต่าง") ได้โดย QR เดิมที่พิมพ์ไปแล้วไม่พัง/ไม่ต้องพิมพ์ใหม่
- [ ] **(ใหม่ — US-42)** โต๊ะที่เพิ่มใหม่ผ่านหน้าจัดการโต๊ะต้องได้ QR static ของตัวเองทันทีผ่าน**กลไกเดียวกับ US-24**โดยอัตโนมัติ — ไม่ใช่ flow สร้าง QR แยกต่างหากที่แอดมินต้องไปกดอีกที่หนึ่ง การเพิ่มโต๊ะกับการสร้าง QR คือขั้นตอนเดียวกัน/ต่อเนื่องกัน
- [ ] **(ใหม่ — US-42)** ส่งต่อ COULSON ออกแบบ **soft delete** สำหรับการปลดระวางโต๊ะ: ห้ามลบประวัติออเดอร์ของโต๊ะนั้นออกจากระบบเด็ดขาด (แค่ mark โต๊ะเป็น "ปลดระวางแล้ว" ซ่อนจากรายการที่เลือกได้) และ**ห้ามแก้ไข/ปลดระวางโต๊ะที่ยังมีบิลเปิดค้างอยู่** (สถานะโต๊ะ "ไม่ว่าง" ตาม Business Rule ข้อ 11) — ต้องปิดบิลก่อนถึงจะแก้/ปลดโต๊ะนั้นได้
- [x] **(NEED-INPUT — ปิดแล้ว 2026-08-11 รอบ 3)** ~~ยืนยันขอบเขต "layout" กับ Touch ก่อน COULSON ออกแบบหน้าจอ~~ → **Touch ยืนยันแล้ว: "ผังง่ายพอ"** ขอบเขต Phase 0 คือผังอย่างง่าย (จัดกลุ่มโซน/ลำดับ/ตำแหน่งคร่าว ๆ) **ไม่ต้องทำ drag-and-drop floor-plan editor** — สโคป/เวลา Phase 0 ไม่บวมขึ้น COULSON เริ่มออกแบบหน้าจอจัดการโต๊ะได้เลยไม่ต้องรอ ถ้าอนาคตต้องการ floor plan ลากวางจริงให้เปิด backlog item ใหม่ ห้ามขยายสโคป US-42 เงียบ ๆ (ดู [[../01-spec/product-backlog-v1|01-spec/product-backlog-v1]] หัวข้อ 5)
- [ ] **(ยืนยันแล้ว)** QR ผูกกับ 1 โต๊ะแบบ static คงที่ตลอดไป ไม่มี flow regenerate/หมุนเวียน QR ต่อออเดอร์หรือต่อรอบลูกค้า (Business Rule ข้อ 10) — ส่งต่อ COULSON ออกแบบวิธี encode ข้อมูลโต๊ะใน QR โดยไม่ต้องเผื่อระบบสร้าง QR ใหม่อัตโนมัติ ลดสโคปที่ต้องออกแบบลงได้
- [ ] ผลิต/พิมพ์ QR code ต้นแบบอย่างน้อย 1 ใบเพื่อทดสอบ flow จริงก่อนสั่งพิมพ์เต็มจำนวนโต๊ะ (พิมพ์ครั้งเดียวใช้ได้ยาว เพราะเป็น static)
- [ ] กำหนดข้อความ error ที่ลูกค้าเห็นเมื่อ QR ใช้ไม่ได้ (หมดอายุ/โต๊ะไม่พบ)
- [ ] **(ใหม่)** ส่งต่อ COULSON: table entity ต้องมี status field ("ว่าง" / "ไม่ว่าง-มีลูกค้า") ที่อัปเดตอัตโนมัติจากเหตุการณ์ออเดอร์ (เปิด = ออเดอร์แรกของรอบเข้ามา, ปิด = แคชเชียร์ checkout เสร็จ) ไม่ใช่ field ที่พนักงานตั้งค่าด้วยมือ (Business Rule ข้อ 11) — กระทบ data model ของโต๊ะโดยตรง ต้องออกแบบ state ก่อน finalize schema
- [ ] **(ใหม่ ยืนยันแล้ว)** ตรวจ flow สแกน QR → หน้าสั่งอาหารให้ตรงตัวจริง ไม่มีหน้ากลาง (splash/landing) คั่นระหว่างทาง (US-01) — เป็นข้อกำหนดด้าน UX ที่ COULSON/SHURI ต้องออกแบบตาม ไม่ใช่แค่ทางเทคนิค
- [ ] **(ใหม่)** เพิ่ม channel field ให้ QR/order entity แยก `table` (dine-in) กับ `counter` (takeaway) — ผลกระทบจาก Business Rule ข้อ 12 กระทบทั้งการ encode QR และ data model ของออเดอร์
- [ ] **(ใหม่ 2026-08-12 — US-44)** ส่งต่อ SHURI ออกแบบ **ป้าย/สติกเกอร์ QR 2 แบบ** (โต๊ะ / เคาน์เตอร์) ที่สื่อครบ 3 อย่าง: สั่งเองได้ที่นี่ + ช่องทาง/เลขโต๊ะ + กฎการจ่ายเงินของช่องทางนั้น พร้อมข้อความ "ไม่ต้องติดตั้งแอป" (Business Rule ข้อ 24) — เลขโต๊ะต้องอ่านออกจากระยะ ~1 เมตร
- [ ] **(ใหม่ 2026-08-12 — US-44)** ส่งต่อ COULSON/BANNER: ฟังก์ชันดาวน์โหลดของ US-24 ต้องส่งออกเป็น **ไฟล์ป้ายพร้อมพิมพ์** (QR + เลขโต๊ะ + ข้อความในไฟล์เดียว) ไม่ใช่รูป QR เปล่า · รองรับป้าย QR เคาน์เตอร์ด้วย · โต๊ะที่เพิ่มผ่าน US-42 ต้องได้ป้ายรูปแบบเดียวกันอัตโนมัติ
- [ ] **(ใหม่ 2026-08-12)** พิมพ์ป้ายต้นแบบ 2 แบบไปทดสอบหน้างานจริงก่อนสั่งพิมพ์เต็มจำนวน (**5–10 ใบ** ตามจำนวนโต๊ะจริงที่ Touch ยืนยัน + ป้ายเคาน์เตอร์ 1 ใบ) — ตรวจว่าลูกค้าที่ไม่เคยใช้ระบบเข้าใจได้เองจากป้ายโดยไม่ต้องมีคนอธิบาย (นี่คือการทดสอบสมมติฐานที่สำคัญที่สุดของ US-44)

## กลุ่มงาน B — หน้าจอลูกค้า: เมนู + ตะกร้า + ส่งออเดอร์ (รองรับ US-02, US-03, US-04, US-06, US-07, US-43)

- [ ] ยืนยัน flow ว่าออเดอร์แต่ละรอบส่งแยกกัน แต่ต้องรวมยอดในบิลเดียวกันของโต๊ะ (ตาม Business Rule ข้อ 1, 7)

- [ ] **(ใหม่ — รอบ 7)** ยืนยัน default: ถ้าลูกค้าไม่เลือกระดับการคั่ว ระบบตั้งค่าเริ่มต้นเป็น "กลาง" อัตโนมัติ (ไม่บังคับเลือก) — ถ้าตัวเลือก "เมล็ดพิเศษ" ไม่มีรายการที่เปิดขายอยู่เลยในขณะนั้น ต้องซ่อนตัวเลือกนี้ทั้งหมด ไม่ใช่โชว์ตัวเลือกว่างเปล่า/กดไม่ได้ (US-35)

## กลุ่มงาน C — ติดตามสถานะออเดอร์ฝั่งลูกค้า (รองรับ US-05)

- [ ] ยืนยันกับ COULSON ว่าจะใช้กลไก real-time แบบไหน (polling หรือ push) — เป็นการตัดสินใจเชิงเทคนิค ไม่ใช่ของ XAVIER แต่ flag ไว้เป็นข้อกำหนดว่า "ต้องอัปเดตโดยลูกค้าไม่ต้องกดรีเฟรชเอง"
- [ ] กำหนดชื่อ/ลำดับสถานะที่ลูกค้าเห็นให้ตรงกับที่ครัวใช้ (รอดำเนินการ / กำลังทำ / เสร็จแล้ว)

## กลุ่มงาน D — หน้าจอพนักงานหน้าร้าน: เตรียมของ + การเงิน รวมเป็นจอเดียว (รองรับ US-13, US-14, US-15, US-16, US-18, US-19, US-20)

> **อัปเดต (รอบ feedback ที่ 5) — merge เดิมคือกลุ่มงาน D (ครัว/บาร์) + กลุ่มงาน E (แคชเชียร์) แยกกัน 2 หน้าจอ:** Touch ยืนยันว่าร้านนี้เครื่องชงกาแฟ/จุดเตรียมของอยู่ติดเคาน์เตอร์ คนเดียวกันรับเงินและทำเครื่องดื่มเอง จึง**ไม่ต้องออกแบบเป็น 2 หน้าจอ/2 อุปกรณ์แยกกันสำหรับ Phase 0 อีกต่อไป** — รวมเป็น UI เดียวที่พนักงานคนเดียวใช้ทำทั้งสองหน้าที่ ลดงานออกแบบ+พัฒนาของ COULSON ลงจริง (ไม่ใช่แค่เปลี่ยนชื่อ) — โครงสร้าง data model ยังต้องแยก concept "การเตรียมของ" กับ "การเงิน" ไว้อยู่ (คนละ field/entity) เพียงแต่แสดงผลรวมกันในหน้าจอเดียว เพื่อให้ยังรองรับ multi-station ในอนาคตได้ (ดู Business Rule ข้อ 13, US-31)

- [ ] ส่งต่อ COULSON ออกแบบหน้าจอเดียวที่รวม: ออเดอร์ใหม่แบบเรียลไทม์ + ปุ่มเปลี่ยนสถานะ (รอดำเนินการ/กำลังทำ/เสร็จแล้ว) + เลือกโต๊ะดูสรุปยอด + ปิดบิล + ยกเลิกออเดอร์ — ไม่ต้องแยกเป็นหน้าจอ "ครัว" กับหน้าจอ "แคชเชียร์" สำหรับ Phase 0
- [ ] กำหนดรูปแบบการแจ้งเตือน (เสียง/popup) ที่เหมาะกับหน้าร้านจริง (เสียงต้องได้ยินในที่มีเสียงรบกวน) — สำคัญหลักสำหรับออเดอร์ dine-in ที่มาจากโต๊ะ (US-15)
- [ ] ส่งต่อออกแบบหน้าจอ mark สินค้า "หมดชั่วคราว" ให้พนักงานกดได้เองระหว่างงานยุ่ง (ต้องเร็ว ไม่กี่คลิก) — **(รอบ 7)** กลไกเดียวกันนี้ต้องใช้ได้กับ "ตัวเลือกของสินค้า" ด้วย (เช่น เมล็ดพิเศษใน US-36) ไม่ใช่แค่ตัวสินค้าเต็ม
- [ ] ยืนยัน edge case: ถ้าลูกค้ายืนยันออเดอร์ในจังหวะที่สินค้า**หรือตัวเลือกของสินค้า**เพิ่งถูก mark หมด ระบบต้อง reject เฉพาะรายการนั้น ไม่ reject ทั้งบิล (ตาม Business Rule ข้อ 4 ที่ขยายในรอบ 7)
- [ ] ส่งต่อ COULSON ออกแบบส่วนเลือกโต๊ะ → เห็นสรุปยอดรวมทุกออเดอร์ของโต๊ะนั้น (ควรแยกให้เห็นชัดว่าโต๊ะไหน "ไม่ว่าง" อยู่ตอนนี้ เพราะสถานะนี้ derive จากออเดอร์ ไม่ใช่ค่าที่พนักงานตั้งเอง)
- [ ] **(ยืนยันแล้ว)** ปุ่ม "ปิดบิล" คือจุดเดียวที่ทำให้สถานะโต๊ะเปลี่ยนกลับเป็น "ว่าง" — ไม่ต้องออกแบบปุ่ม/ฟังก์ชัน "เปิด/ปิดโต๊ะ" แยกต่างหากให้พนักงาน (Business Rule ข้อ 11) ส่งต่อ COULSON ออกแบบเฉพาะปุ่มปิดบิลที่เคลียร์ session และเปลี่ยนสถานะโต๊ะในจังหวะเดียวกัน
- [ ] ส่งต่อออกแบบส่วนยกเลิกออเดอร์/รายการ ที่บังคับให้กรอกเหตุผลก่อนยืนยันเสมอ (ตาม Business Rule ข้อ 5)

- [ ] **(ใหม่ 2026-08-12 — จากข้อมูลพนักงาน 2–4 คนในนาทีพีค)** ส่งต่อ COULSON/BANNER: หน้าจอสถานีถูกใช้จาก **2–4 อุปกรณ์พร้อมกัน**บนบัญชีสถานีเดียว — **(ก)** ห้ามออกแบบเป็น single-session-per-account (เครื่องที่ 2 ต้องไม่เด้งเครื่องแรกออก) **(ข)** การเปลี่ยนสถานะจากเครื่องหนึ่งต้องปรากฏบนเครื่องอื่นทันทีเพื่อกันการทำงานซ้ำ **(ค)** ถ้าสองคนกดออเดอร์เดียวกันพร้อมกัน ผลลัพธ์ต้องเป็นสถานะที่ก้าวหน้าที่สุด ไม่ใช่คนกดหลังชนะ (Business Rule ข้อ 26, 27 + AC ใหม่ของ US-14)

- [ ] **(ใหม่ 2026-08-12 — US-18)** ส่งต่อ SHURI/COULSON: หน้าจอเลือกโต๊ะแสดง **ทุกโต๊ะ (5–10 โต๊ะ) พร้อมกันในจอเดียว** พร้อมสถานะว่าง/ไม่ว่างและยอดค้าง — ไม่ต้องมีช่องค้นหา/แบ่งหน้า
- [ ] **(ใหม่ 2026-08-12 — US-14)** ส่งต่อ COULSON ออกแบบสถานะปลายทาง **"ส่งมอบแล้ว"** สำหรับออเดอร์ช่องทางเคาน์เตอร์ + ให้ออเดอร์ที่ส่งมอบแล้วหลุดจากคิวหน้าจอหลักไปอยู่ประวัติ (ช่องทางโต๊ะไม่มีสถานะนี้) — ตรวจให้ตรงกับ state machine ที่ [[../../02-design/02-technical/data-model-v1|data-model-v1]] วางไว้แล้ว

## กลุ่มงาน E — หน้าจอแอดมิน: จัดการเมนู (รองรับ US-23, US-36)

- [ ] ส่งต่อ COULSON ออกแบบหน้าจอเพิ่ม/แก้ไข/ลบสินค้า ราคา รูป หมวดหมู่
- [ ] ยืนยันว่าการแก้ไขเมนูมีผลกับฝั่งลูกค้าทันทีโดยไม่ต้อง deploy ใหม่ (ข้อกำหนด ไม่ใช่วิธีทำ)
- [ ] **(ใหม่ — รอบ 7)** ส่งต่อ COULSON ออกแบบส่วนจัดการ "รายการเมล็ดกาแฟพิเศษ" (US-36) ในหน้าจัดการเมนูเดียวกัน — เพิ่ม/แก้ไข/ลบชื่อเมล็ด ใช้กลไกเดียวกับสินค้าทั่วไป (US-23) และเปิด/ปิดการมองเห็นด้วยกลไก "หมดชั่วคราว" เดียวกับ US-16 — ไม่สร้างระบบจัดการแยกต่างหาก

## กลุ่มงาน F — ช่องทางเคาน์เตอร์/ซื้อกลับ Takeaway ทั้งสองที่มา (ใหม่ — รองรับ US-28, US-29, US-30, Business Rule ข้อ 12) — เดิมชื่อ "กลุ่มงาน G"

- [ ] ส่งต่อ COULSON ออกแบบ QR เคาน์เตอร์แยกจาก QR โต๊ะ (channel field เดียวกับที่เพิ่มใน กลุ่มงาน A) — พิมพ์ติดหน้าเคาน์เตอร์ 1 ใบ ใช้ static เหมือน QR โต๊ะ
- [ ] ส่งต่อ COULSON ออกแบบสถานะออเดอร์เพิ่ม 1 สถานะ: **"รอยืนยันการชำระเงิน"** ที่ order ของช่องทางเคาน์เตอร์ต้องผ่านก่อนจะเข้าคิวครัว (ไม่ใช้กับ dine-in)
- [ ] ส่งต่อ COULSON ออกแบบหน้าจอแคชเชียร์ส่วนแยก: รายการออเดอร์ซื้อกลับที่รอยืนยันชำระเงิน + ปุ่มยืนยันรับเงิน (US-29) — แยกจากคิวปิดบิลโต๊ะ (US-19) ให้ชัดเจน
- [ ] ยืนยันว่าไม่ต้องมี payment gateway ออนไลน์สำหรับช่องทางนี้ — เป็นแค่ gate สถานะที่แคชเชียร์กดยืนยันหลังรับเงินสด/บัตรตามปกติหน้าเคาน์เตอร์ (ไม่ปนกับ US-12 ที่เป็น online payment สำหรับ dine-in และยังเป็น P2)
- [ ] ยืนยัน edge case: ลูกค้าสั่งที่เคาน์เตอร์แล้วไม่จ่ายเงิน (เดินหนี/เปลี่ยนใจ) — แคชเชียร์ยกเลิกออเดอร์นั้นด้วยกลไกเดียวกับ US-20
- [ ] **(ใหม่)** ส่งต่อ COULSON ออกแบบหน้าจอ "คีย์ออเดอร์แทนลูกค้า" ฝั่งแคชเชียร์ (US-30) — ใช้เมนู/ตะกร้าเดียวกับที่ออกแบบให้ลูกค้าใน กลุ่มงาน B แต่ให้แคชเชียร์เป็นผู้กดแทน และรวมขั้นตอนรับชำระเงินเข้าไปในหน้าเดียวกัน (ไม่แยกเป็น 2 ขั้นตอนแบบ US-28/US-29) — ต้องรองรับคีย์ออเดอร์ซ้อนกันต่อเนื่องสำหรับลูกค้าหลายคนติดกัน (คิว walk-in) โดยแต่ละออเดอร์ track แยกกัน
- [ ] **(ใหม่)** ส่งต่อ COULSON: order entity ต้องมี origin field (`customer-self` / `staff-entered`) แยกจาก channel field (`table` / `counter`) เพื่อบันทึกว่าใครเป็นคนสร้างออเดอร์ — ออเดอร์จาก US-28 (ลูกค้าสั่งเอง) และ US-30 (แคชเชียร์คีย์แทน) ต้องบรรจบกันที่คิวครัว/สถานะ "รอเสิร์ฟ" เดียวกันหลังจ่ายเงินสำเร็จ ไม่แยกคิว (Business Rule ข้อ 12)
- [ ] **(ใหม่)** ส่งต่อ COULSON ออกแบบการแสดงผล "จุดรับของ" (ปลายเคาน์เตอร์) ให้ต่างจากออเดอร์โต๊ะ — หน้าจอครัว/จุดรับของควรบอกชัดว่าออเดอร์ไหน "เสร็จแล้ว รอลูกค้ามารับที่ปลายเคาน์เตอร์" เทียบกับออเดอร์โต๊ะที่พนักงานนำไปเสิร์ฟเอง ไม่ต้องมีขั้นตอนนี้ (Business Rule ข้อ 12)
- [x] ~~**(ใหม่ — ยังไม่ยืนยันชัดเจน)** ยืนยันว่า "รอเสิร์ฟ" เป็นแค่ label หรือเป็น status field ใหม่~~ **(resolved 2026-08-12)** ข้อสรุป: **"รอเสิร์ฟ" เป็น label** ที่ครอบช่วง "จ่ายเงินสำเร็จ → ส่งมอบแล้ว" ไม่ใช่ status field · สิ่งที่ขาดจริงคือสถานะปลายทาง **"ส่งมอบแล้ว"** ซึ่งเพิ่มเข้า US-14 + Business Rule ข้อ 25 แล้ว — **finalize schema ของสถานะออเดอร์ได้ ไม่มี blocker เหลือ**
- [ ] **(ใหม่ 2026-08-12 — US-45)** ส่งต่อ COULSON/BANNER ออกแบบ **เลขคิวรูปแบบ A01** (ตัวอักษรนำ + 2 หลัก · A01–A99 แล้วขึ้นชุด B01 · รีเซ็ตกลับที่ A01 ทุกวันเปิดร้าน) ให้ทุกออเดอร์ช่องทางเคาน์เตอร์ — ห้ามใช้เลขซ้ำกับออเดอร์ที่ยังไม่ "ส่งมอบแล้ว" · ช่องทางโต๊ะไม่ใช้เลขคิว (field null ได้)
- [ ] **(ใหม่ 2026-08-12 — US-45)** ส่งต่อ SHURI: เลขคิวต้องเป็น**องค์ประกอบที่เด่นที่สุด**ในหน้าจอลูกค้าหลังกดยืนยันออเดอร์ และแสดงในคิวฝั่งพนักงานทั้งคิวรอยืนยันชำระเงินและคิวเตรียมของ · **รูปแบบต้องดูต่างจากเลขโต๊ะ (T01–T10) ด้วยตาทันที**
- [ ] **(ใหม่ 2026-08-12 — US-45)** ยืนยัน flow ของ US-30: ลูกค้าที่พนักงานคีย์แทนไม่มีหน้าจอ — พนักงานบอกเลขคิวด้วยปาก (และ/หรือสลิป) แล้วใช้เลขนี้เรียกลูกค้ามารับของ · **นี่คือคำตอบของคำถามเปิดข้อ 1 ใน [[../../02-design/01-prototypes/user-flow-v1|user-flow-v1]] หัวข้อ 7**
- [ ] **(ใหม่ 2026-08-12)** ยืนยันว่าช่องทางเคาน์เตอร์บอกกฎ "ชำระเงินก่อนรับของ" ตั้งแต่ก่อนกดยืนยันออเดอร์ (บนป้าย QR ตาม US-44 + บนหน้าเมนู/ตะกร้าของช่องทางนี้) ไม่ใช่มาบอกครั้งแรกหลังกดยืนยัน

## งานข้ามกลุ่ม (Cross-cutting)

- [x] ~~ยืนยันกับ Touch เรื่อง Business Rule ข้อ "จ่ายก่อนหรือหลัง" และ "แชร์ตะกร้าต่อโต๊ะ"~~ **(resolved รอบ feedback ที่ 3)** — ทั้งสองข้อยืนยันแล้ว พร้อมรายละเอียดเพิ่ม (แยก channel โต๊ะ/เคาน์เตอร์ที่จ่ายเงินคนละจังหวะ, concurrent multi-device ordering) ดู Business Rule ข้อ 2, 3, 12 ใน [[../01-spec/product-backlog-v1|01-spec/product-backlog-v1]]
- [ ] เตรียม checklist ทดสอบ end-to-end ของ Phase 0 ให้ OKOYE ใช้ก่อนเปิดร้านจริง: สแกน QR โต๊ะ → สั่ง → ครัวเห็น/อัปเดตสถานะ → ลูกค้าเห็นสถานะ → สั่งรอบสอง (รวมถึงสองคนสั่งพร้อมกันจากคนละมือถือ) → แคชเชียร์ปิดบิล → โต๊ะว่างสำหรับลูกค้าคนถัดไป **และแยกอีกชุดสำหรับ:** สแกน QR เคาน์เตอร์ → สั่ง → รอยืนยันชำระเงิน → แคชเชียร์ยืนยันรับเงิน → ครัวเห็นออเดอร์ **และแยกอีกชุดสำหรับ:** แคชเชียร์คีย์ออเดอร์แทนลูกค้าที่สั่งด้วยวาจา → รับเงินพร้อมกัน → ออเดอร์เข้าคิว "รอเสิร์ฟ" เดียวกับออเดอร์เคาน์เตอร์ที่ลูกค้าสั่งเอง → ทดสอบคีย์ออเดอร์ต่อเนื่องหลายลูกค้าติดกัน (walk-in queue) ว่าแต่ละออเดอร์ไม่ปนกัน
- [ ] เก็บ log การตัดสินใจสำคัญ (default "จ่ายที่เคาน์เตอร์" สำหรับ dine-in, กฎ prepay ของช่องทางเคาน์เตอร์, concurrent cart, QR static, สถานะโต๊ะ derive จากออเดอร์) ไว้ใน [[../../05-log/index|05-log]]
- [ ] **(ใหม่ 2026-08-12)** รวบรวม **non-functional requirement** ที่ค้นพบจากงานออกแบบเน้นผู้ใช้ไปเป็นหัวข้อในเอกสารข้อกำหนดระบบ (ไม่ใช่ AC ของ story ใด): **(ก)** อายุ + จำนวน session ของหน้าจอสถานี (Business Rule ข้อ 27) **(ข)** การอัปเดตสถานะเรียลไทม์ข้ามอุปกรณ์ที่ทั้งฝั่งลูกค้าและพนักงานพึ่งพา **(ค)** การป้องกันออเดอร์ซ้ำเมื่อเน็ตลูกค้าหลุดตอนกดยืนยัน (idempotency) **(ง)** ขนาดเป้าแตะ/ตัวอักษรขั้นต่ำจากข้อจำกัดทางกายภาพของหน้าร้าน (ซ้อนกับ Business Rule ข้อ 23 accessibility baseline)
- [ ] **(ใหม่ 2026-08-12)** เพิ่ม test case ให้ OKOYE สำหรับของที่เพิ่มรอบนี้: ลูกค้าใหม่เข้าใจป้าย QR ได้เองไหม (US-44) · จับคู่ออเดอร์ด้วยเลขคิว A01 ถูกคนในคิวที่มีหลายออเดอร์พร้อมกัน (US-45) · ออเดอร์ที่ "ส่งมอบแล้ว" หลุดจากคิวจริง (US-14) · **เปิดหน้าจอสถานี 3 เครื่องด้วยบัญชีเดียวกันพร้อมกัน** แล้วเครื่อง A กด "กำลังทำ" → เครื่อง B/C ต้องเห็นทันที และกดซ้ำต้องไม่ทำให้สถานะย้อนกลับ (Business Rule ข้อ 26-27)
- [ ] **(ใหม่ — ไม่ใช่งาน Phase 0 แต่ต้อง track ไว้)** ก่อนแตก Phase 1 เป็น task breakdown ในอนาคต ต้องรวม task ของ US-32/33/34 (PDPA — privacy notice, สิทธิ์เข้าถึง/ลบ/เพิกถอนข้อมูล loyalty) เข้าไปด้วย และต้องปิด NEED-INPUT เรื่องระยะเวลาเก็บข้อมูล (Business Rule ข้อ 17) กับ Touch ก่อน — ทั้งหมดต้อง ship พร้อมกับ US-11 ไม่แยกทีหลัง (ดู [[../01-spec/product-backlog-v1|01-spec/product-backlog-v1]] หัวข้อ 6)
- [ ] **(ใหม่ — Week 3 / รอบ UX) Accessibility baseline (Business Rule ข้อ 23) — บังคับทุกหน้าจอลูกค้าตั้งแต่ Phase 0:** ตาม [[../01-spec/ux-requirements-v1|01-spec/ux-requirements-v1]] หัวข้อ 3 ส่งต่อ COULSON/SHURI checklist ที่ต้องตรวจผ่านจริงก่อนถือว่าหน้าจอลูกค้าเสร็จ (ไม่ใช่แค่โน้ตไว้เฉย ๆ):

  - [ ] Contrast ratio ข้อความปกติ ≥ 4.5:1, ข้อความขนาดใหญ่/ไอคอนสำคัญ ≥ 3:1 กับพื้นหลัง — ตรวจด้วยเครื่องมืออัตโนมัติ (เช่น axe, Lighthouse) ก่อนปิดงาน
  - [ ] พื้นที่กด/ปุ่มฝั่งลูกค้า ≥ 44×44px ขั้นต่ำ
  - [ ] จุดที่สื่อความหมายด้วยสี (สถานะออเดอร์, สินค้าหมด) ต้องมีข้อความหรือไอคอนกำกับเสมอ ห้ามใช้สีเดี่ยวสื่อความหมาย
  - [ ] อ่านออกในสภาพแสงจ้า/กลางแดด — หลีกเลี่ยง contrast ต่ำที่ดูสวยเฉพาะในจอห้องแอร์ (ตาม [[../01-spec/ux-requirements-v1|01-spec/ux-requirements-v1]] หัวข้อ 4)
  - [ ] **บังคับให้ทุกหน้าจอลูกค้าใน กลุ่มงาน B (เมนู/ตะกร้า/ยืนยันออเดอร์), กลุ่มงาน C (ติดตามสถานะ), และ กลุ่มงาน F (เคาน์เตอร์/takeaway ฝั่งลูกค้า) ผ่าน checklist นี้ครบทุกข้อก่อนถือว่างานของกลุ่มนั้นเสร็จ** — ไม่ใช่ checklist แยกต่างหากที่ทำทีหลัง

## สถานะ Handoff

Phase 0 ทั้งหมดข้างต้น **พร้อมส่งต่อ COULSON เริ่ม `02-design` ได้ทันทีแบบไม่มี blocker เหลืออยู่แล้ว** — เดิมมีข้อเดียวที่ค้าง (payment timing + shared cart ต่อโต๊ะ) แต่ Touch ให้ feedback เชิงปฏิบัติการที่คลี่คลายทั้งสองข้อแล้วในรอบล่าสุด (ดู Business Rule ข้อ 2, 3, 12 ใน [[../01-spec/product-backlog-v1|01-spec/product-backlog-v1]])

การยืนยันเรื่อง QR แบบ static (Business Rule ข้อ 10), สถานะโต๊ะที่ derive จากออเดอร์ (ข้อ 11), การแยกช่องทางโต๊ะ/เคาน์เตอร์พร้อมกฎจ่ายเงิน (ข้อ 12), และ concurrent cart ต่อโต๊ะ (ข้อ 2) **ไม่ใช่ประเด็นเปิดอีกต่อไป และไม่ใช่ blocker** — ทั้งหมดเป็นการชี้ชัดที่ช่วยให้ COULSON ออกแบบได้แม่นยำขึ้น (บางข้อลดสโคป เช่น ไม่ต้องออกแบบระบบ regenerate QR หรือปุ่มเปิด/ปิดโต๊ะ, บางข้อเพิ่มสโคปเล็กน้อยแบบมีขอบเขตชัดเจน เช่น กลุ่มงาน F สำหรับช่องทางเคาน์เตอร์) — งานใหม่ทั้งหมดสะท้อนอยู่ในกลุ่มงาน A, B, D, F ด้านบนแล้ว

**อัปเดต (รอบ feedback ที่ 5) — merge actor ลดสโคป Phase 0 ลงจริง:** การรวม "ครัว/บาร์" กับ "แคชเชียร์" เป็น actor เดียว (Business Rule ข้อ 13) ทำให้กลุ่มงาน D เดิม (2 กลุ่มแยกกัน) รวมเป็นกลุ่มเดียว — COULSON ไม่ต้องออกแบบและ BANNER ไม่ต้องพัฒนา 2 หน้าจอ/2 อุปกรณ์แยกกันสำหรับ Phase 0 อีกต่อไป **นี่คืองานที่ตัดออกจริง ไม่ใช่แค่ป้ายชื่อเปลี่ยน** — ไม่มี blocker ใหม่เกิดขึ้นจากการรวมนี้ มีแต่ทำให้ Phase 0 เบาลง

**ประเด็นที่ยังไม่ปิดสนิท** (ไม่บล็อก Phase 0 ทั้งหมด): **(1)** ถ้อยคำ consent/เงื่อนไขของ loyalty stamp card (US-11) — เป็นงาน Phase 1 ไม่ใช่ Phase 0 จึงไม่กระทบการ handoff รอบนี้ **(2)** ความหมายที่แท้จริงของสถานะ "รอเสิร์ฟ" (US-30) — เป็นแค่ label ฝั่งจุดรับของ หรือ status field ใหม่ในระบบจริง ๆ — COULSON ออกแบบ UI/flow ของกลุ่มงาน F ต่อได้เลยโดยใช้การตีความปัจจุบัน (label ที่ครอบคลุมช่วงหลังจ่ายเงินถึงมารับของ) แต่ควรยืนยันกับ Touch อีกครั้งก่อน finalize data model ของสถานะออเดอร์ในรายละเอียด **(3)** ระยะเวลาเก็บข้อมูล loyalty (Business Rule ข้อ 17 — PDPA gap analysis รอบ 6) — เป็นงาน Phase 1 เช่นกัน ไม่กระทบ Phase 0

**อัปเดต (รอบ feedback ที่ 6) — PDPA gap analysis ไม่เพิ่ม blocker ให้ Phase 0:** วิเคราะห์ backlog ทั้งหมดเทียบกับ PDPA แล้วพบว่า Phase 0 ไม่เก็บข้อมูลส่วนบุคคลของลูกค้าเลย จึงไม่มีงานใหม่ใน Phase 0 จากรอบนี้ งานที่เพิ่ม (US-32/33/34, Business Rule ข้อ 14-21) ทั้งหมดผูกกับ US-11 (Phase 1) — COULSON เริ่ม Phase 0 ได้ตามเดิมทุกประการ ไม่ต้องรอผลจากรอบนี้

**อัปเดต (รอบ feedback ที่ 7) — เพิ่มสโคป Phase 0 เล็กน้อยแบบมีขอบเขตชัดเจน:** US-35 (เลือกระดับการคั่ว/เมล็ดพิเศษ) และ US-36 (แอดมินจัดการรายการเมล็ดพิเศษ) เพิ่มเข้า Phase 0 — งานใหม่ทั้งหมดสะท้อนอยู่ในกลุ่มงาน B (option-group mechanism) และกลุ่มงาน E (จัดการรายการเมล็ดพิเศษ) แล้ว ยืมกลไกที่มีอยู่แล้ว (US-08's option group, US-16's หมดชั่วคราว, US-23's จัดการเมนู) จึงเป็นสโคปที่เพิ่มแบบมีขอบเขตชัดเจน ไม่ใช่ระบบใหม่ทั้งหมด — ผลพลอยได้: การสร้าง option-group mechanism ตอนนี้ทำให้ US-08 (Phase 1) เบาลงในอนาคตด้วย

**อัปเดต 2026-08-11 (Week 3 / รอบ UX) — Touch อนุมัติ US-37 ถึง US-41 เข้า backlog, มีเอกสาร UX ใหม่เป็น input ให้ COULSON แล้ว:** [[../01-spec/ux-persona-v1|01-spec/ux-persona-v1]] (persona), [[../01-spec/ux-journey-map-v1|01-spec/ux-journey-map-v1]] (journey map ที่มาของ US-37..41), และ [[../01-spec/ux-requirements-v1|01-spec/ux-requirements-v1]] (usability requirements วัดผลได้ + accessibility baseline) — COULSON ควรอ่านทั้งสามฉบับก่อน finalize wireframe ของ Phase 0

ผลกระทบต่อ Phase 0 ในเอกสารนี้มี **2 จุดเท่านั้น** (ทั้งสองแตกเป็น task จริงแล้วด้านบน ไม่ใช่แค่โน้ต):
1. **Accessibility baseline (Business Rule ข้อ 23)** — เพิ่ม checklist บังคับในหัวข้อ "งานข้ามกลุ่ม" ที่กลุ่มงาน B, C, F ต้องผ่านก่อนถือว่าเสร็จ
2. **เตรียมทางให้ US-41** — เพิ่ม task เล็กในกลุ่มงาน D ให้เก็บ timestamp ตอนออเดอร์เข้าระบบตั้งแต่ Phase 0

**สิ่งที่ตัดสินใจไม่เพิ่มเข้า Phase 0 พร้อมเหตุผล:**
- **US-37 (ปุ่มเรียกพนักงาน), US-39 (แจ้งเตือนเชิงรุก), US-40 (โหมดเข้าถึงง่าย) — ไม่มี task ใน Phase 0 และไม่ต้องเตรียมทางล่วงหน้า** เพราะทั้งสามเป็นฟีเจอร์เพิ่มเติม (additive) ที่ต่อยอดบนโครงสร้างข้อมูลที่ Phase 0 มีอยู่แล้วโดยไม่ต้องปรับ schema เดิม — US-37 เป็นแค่ event ใหม่ที่ไม่พึ่งพา field ของ order/table ที่มีอยู่, US-39 พึ่งพากลไก realtime ของ US-05 ที่ยังไม่ได้ตัดสินใจเชิงเทคนิค (polling/push) ในทั้งสอง phase อยู่แล้วจึงไม่มีอะไรให้ "เตรียมทาง" ล่วงหน้าใน Phase 0, US-40 เป็นแค่ CSS/UI toggle ชั้นการแสดงผลที่ไม่แตะ data model เลย — ทั้งสามจึงไม่มีความเสี่ยง rework ถ้าไม่เตรียมอะไรไว้ก่อน
- **US-38 (ETA)** — ประเมินแล้วว่า "เล็กจริง" ไม่ผ่านเกณฑ์ (ดูเหตุผลเต็มในหัวข้อ "งานข้ามกลุ่ม") จึงเลื่อนทั้งก้อนไป Phase 1 โดยไม่เตรียมทางใด ๆ ใน Phase 0

**อัปเดต 2026-08-11 (รอบ requirement กลุ่มงาน A/B + ตัดหมวดปั่นออก) — เพิ่มสโคป Phase 0 อีกรอบ แบบไม่เท่ากัน:** Touch อนุมัติ US-42 (จัดผังโต๊ะ) และ US-43 (ความหวาน) เข้า Phase 0 พร้อมเอกสารใหม่ [[../01-spec/initial-menu-data-v1|01-spec/initial-menu-data-v1]] (ร่างรายชื่อสินค้า+ราคาอ้างอิง 19 รายการ หมวดร้อน/เย็น) ซึ่งเป็น **input ใหม่ให้ COULSON** อ่านก่อน finalize เมนู/ตะกร้าของ Phase 0 (โดยเฉพาะโครงสร้าง option-group ที่ต้องรองรับทั้งความหวาน/การคั่ว/เมล็ดพิเศษพร้อมกัน) — งานที่เพิ่มขึ้นจริงจากรอบนี้แบ่งเป็น 2 ระดับชัดเจน ห้ามปนกัน:
- **US-42 (กลุ่มงาน A) — เพิ่มสโคปจริง:** หน้าจอจัดการโต๊ะฝั่งแอดมินทั้งหน้า (เพิ่ม/แก้/จัดลำดับ-โซน/ปลดระวาง) ที่ไม่เคยอยู่ในสโคปเดิม + ข้อกำหนด data model ใหม่ (table id แยกจากชื่อที่แสดง, soft delete) ที่ COULSON ต้องออกแบบก่อน finalize schema ของโต๊ะ — **(อัปเดตรอบ 3: NEED-INPUT เรื่องขอบเขต layout ปิดแล้ว — Touch ยืนยัน "ผังง่ายพอ" ไม่ต้องทำ drag-and-drop floor-plan editor สโคปไม่บวมเพิ่มจากที่ประเมินไว้ เริ่มออกแบบได้เลย)**
- **US-43 (กลุ่มงาน B) — แทบไม่เพิ่มสโคป:** ยืมกลไก option-group ของ US-35 ที่ต้องสร้างอยู่แล้วใน Phase 0 เพิ่มแค่ข้อมูลตัวเลือกใหม่ (**fixed-list 5 ค่า: 0/25/50/75/100%**) และเงื่อนไข default/การแสดงผลบนตะกร้า+ตั๋วออเดอร์ — **(อัปเดตรอบ 3: NEED-INPUT 2 ข้อปิดแล้ว — Touch ยืนยันสเกล 5 ระดับ และ default = 50%)** งานที่เพิ่มขึ้นจริงจากคำตอบนี้คือ **task UX หนึ่งข้อ**: UI ต้องแสดงค่า default 50% ที่เลือกไว้ให้ลูกค้าเห็นชัด เพราะ default ไม่ใช่สูตรเต็มอีกต่อไป

**อัปเดต 2026-08-11 (รอบ 3) — NEED-INPUT ของ Phase 0 ปิดครบแล้ว:** Touch ตอบทั้ง 3 ประเด็นที่ค้างอยู่ (ขอบเขต layout = ผังง่าย · สเกลความหวาน = 5 ระดับ · default = 50%) → **ตอนนี้ไม่มี NEED-INPUT ที่บล็อกหรือค้างในระดับ Phase 0 เหลืออยู่แล้ว** COULSON เริ่ม `02-design` ของ Phase 0 ได้เต็มตัวโดยไม่ต้องรอคำตอบใดอีก ประเด็นที่ยังเปิดค้างทั้งหมดเป็นเรื่อง Phase 1/2 (priority ของ US-40/US-41, ถ้อยคำ consent และ retention ของ US-11) และราคาขายจริงที่ Touch ต้องเคาะจากร่างใน [[../01-spec/initial-menu-data-v1|01-spec/initial-menu-data-v1]] ก่อนเปิดร้าน ซึ่งไม่บล็อกงานออกแบบ

ผลคือ **Phase 0 หนักขึ้นจริงจากฝั่ง US-42 เป็นหลัก** ส่วน US-43 แทบไม่กระทบ timeline เพราะเป็นแค่ข้อมูลที่เติมเข้ากลไกเดิม — ไม่กระทบ ID/priority/phase ของ US-01 ถึง US-41 เดิมแม้แต่ตัวเดียว นอกจากนี้ Touch ยืนยันหมวดหมู่เมนูตั้งต้นคือ **ร้อน / เย็น** เท่านั้น (ตัดหมวด "ปั่น") ซึ่งเป็นแค่การแก้ seed data/ข้อมูลตั้งต้นในกลุ่มงาน B ไม่กระทบโครงสร้างระบบหรือกลไก option-group ใด ๆ
