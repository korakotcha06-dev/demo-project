## 6. ลำดับการลงมือ — ถ้า OKOYE มีเวลาครึ่งวัน

**เรียงตามความเสี่ยง ไม่ใช่ตามเลข ID** — เกณฑ์คือ *"ถ้าข้อนี้พังแล้วเสียหายแค่ไหน และรู้ช้าแล้วแพงขึ้นเท่าไร"*

| ลำดับ | ชุด | เคส | ทำไมต้องก่อน |
|---|---|---|---|
| **1** | **เงินต้องไม่ผิด** | **TC-100** · TC-065 · TC-112 · TC-102 · TC-022 | **ความเสียหายเป็นเงินจริงและกู้คืนไม่ได้** — ปิดบิลชนกับสั่งเพิ่มคือเก็บเงินขาด, ยอดบิลไม่ตรงกับผลบวกรายการคือบัญชีพัง, รับเงินซ้ำคือเก็บเกิน · api-design เองระบุว่า §5.3 เป็นจุดเสี่ยงที่สุดของทั้ง contract |
| **2** | **กฎ prepay ของช่องทางเคาน์เตอร์** | TC-106 · TC-107 · TC-014 · TC-094 | ถ้ากฎนี้รั่ว = **ของออกจากร้านโดยไม่ได้เก็บเงิน** · ต้องพิสูจน์ที่ระดับ DB (TC-106) ไม่ใช่แค่ UI |
| **3** | **ระบบใช้งานได้จริงในนาทีพีค** | **TC-062** · TC-063 · TC-066 · TC-101 | **ถ้า NFR-06 พัง ระบบใช้งานไม่ได้เลยตั้งแต่วันแรก** (พนักงาน 2–4 คนเด้งกันออก) · เป็น exit criteria ของ Phase 0 · และเป็นเรื่อง **auth architecture ที่แก้ทีหลังแพงมาก** — ต้องรู้ให้เร็วที่สุด |
| **4** | **เส้นทางหลักเดินจบได้** | TC-001 · TC-008 · TC-015 · TC-016 · TC-023 · TC-024 · TC-030 | happy path ของทั้ง 3 ช่องทาง — ถ้าพังคือเปิดร้านไม่ได้ แต่พังแบบเห็นทันที ไม่ใช่พังเงียบ |
| **5** | **สถานะโต๊ะ derive ถูกต้อง** | TC-008 · TC-023 · TC-025 · TC-104 · TC-111 | ถ้าผิด **โต๊ะไม่มีวันว่างให้ลูกค้าคนถัดไป** — พังเงียบและสังเกตยากจนกว่าจะเต็มร้าน |
| **6** | **ของหมด / reject รายรายการ** | TC-064 · TC-092 · TC-093 · TC-019 · TC-020 | เกิดทุกวัน · ถ้า reject ทั้งบิลแทนรายเดียว ลูกค้าเสียประสบการณ์ทันที |
| **7** | **ข้อมูลลูกค้าต้องไม่ถูกเก็บ** | TC-072 · TC-070 · TC-071 | **ตรวจครั้งเดียวจบและถูกมาก** แต่ถ้าพลาดคือความเสี่ยงเชิงกฎหมาย ควรตรวจก่อนเปิดร้านเสมอ |
| **8** | ตัวเลือกสินค้า + เมนู | TC-003 … TC-005 · TC-041 … TC-048 | เยอะแต่ความเสี่ยงต่อกว่า และ fail แบบเห็นชัด |
| **9** | error path ที่เหลือ | TC-082 … TC-097 | สำคัญต่อประสบการณ์ แต่ไม่บล็อกการเปิดร้าน |
| **10** | usability ที่ต้องใช้ผู้ทดสอบหลายคน | TC-074 … TC-081 | **ต้องนัดคนจริง ≥5–10 คน** — วางแผนล่วงหน้าได้ แต่ทำไม่ได้ในครึ่งวันแรก |

> **ถ้ามีเวลาแค่ 2 ชั่วโมงจริง ๆ:** รันลำดับ 1 + 3 เท่านั้น (**9 เคส**) — เป็นสองกลุ่มที่ *แก้ทีหลังแพงที่สุด* (เงินหาย + auth architecture) ส่วนที่เหลือ fail แล้วเห็นทันทีและแก้ได้ในชั้น UI

## 7. เกณฑ์ผ่าน-ไม่ผ่านของ Phase 0

| เกณฑ์ | ค่า |
|---|---|
| เคส **P0 ทั้งหมด** | ต้อง **pass 100%** — ไม่มีข้อยกเว้น |
| เคส **P1** | pass ≥90% · ที่ fail ต้องมี ticket และเจ้าของ |
| เคส **P2** | บันทึกไว้ ไม่บล็อกการเปิดร้าน |
| **invariant (S9)** | ต้อง **pass 100%** — ถ้า DB ไม่ปฏิเสธ แปลว่ากฎธุรกิจไม่มีผลบังคับจริง ไม่ว่า UI จะกันดีแค่ไหน |
| **เคสที่ถูกบล็อก** | **ห้ามนับเป็น pass และห้ามนับเป็น fail** — ต้องรายงานแยกเป็น "ยังไม่ได้ทดสอบ" พร้อมเหตุผล |

> 🔴 **ห้ามรายงานว่า Phase 0 ผ่านการทดสอบแล้ว** ตราบใดที่ยังมีเคสในหัวข้อ 5 ค้างอยู่ — ผลทดสอบที่ไม่ครอบ US-44/US-45 และ NFR-06/10/11 **ไม่ใช่หลักฐานว่าระบบพร้อมเปิดร้าน** เพราะทั้งสี่เรื่องนั้นอยู่ใน exit criteria ของ Phase 0 โดยตรง

## 8. NEED-INPUT

1. **เกณฑ์เวลาของ US-15** — ต้องได้ตัวเลขก่อนถึงจะเขียนเคสได้ (ดูหัวข้อ 4) · **ข้อเสนอของ XAVIER:** เสียงบังคับ + เตือนภายใน ≤3 วินาที + ได้ยินจากระยะ 3 เมตรในร้านที่เปิดเพลงระดับปกติ — **ยังไม่เขียนลง backlog รอ Touch เคาะ**
2. **วิธีวัด mis-tap ≤5% (TC-081) ให้ทำซ้ำได้** — NFR-20 ระบุเกณฑ์ไว้แต่ไม่ได้นิยามวิธีวัด · เป็นงานที่ OKOYE ควรออกแบบวิธีทดสอบเอง ไม่ใช่ตัวบล็อก
3. **อุปกรณ์จริงของจอสถานี** — กระทบ TC-062/066/067 โดยตรง (จำนวนเครื่อง, พฤติกรรม lock screen ของ OS) · เป็น NEED-INPUT เดิมที่ค้างมาตั้งแต่ `ux-requirements` §9 และ `screen-inventory` §5 ข้อ 1
4. 🔴 **ร้านมีเครื่องพิมพ์สลิป/ใบเสร็จตั้งแต่วันเปิดหรือไม่** — **ใหม่ 2026-08-16 · กระทบ TC-055a โดยตรง** · Touch ระบุว่าเลขคิวอยู่บนใบเสร็จ (*"มี que ที่ ใบเสร็จเช่น คิว A14"*) แต่ **US-21 (ออกใบเสร็จ) เป็น P1/Phase 1** และ [[../../02-design/01-prototypes/screen-inventory-v1|screen-inventory-v1]] §5 ข้อ 1 ตั้ง default ว่า **"ไม่มีเครื่องพิมพ์สลิปใน Phase 0"** → **ถ้าไม่มีเครื่องพิมพ์ ต้องรายงาน TC-055a ว่า "ไม่ได้ทดสอบเพราะไม่มีอุปกรณ์" ห้ามนับเป็น pass** · ถ้ามีจริง ควรพิจารณาดัน US-21 (หรือเฉพาะส่วนสลิปเลขคิว) ขึ้น Phase 0
5. **จำนวนผู้ทดสอบจริงที่หาได้** — TC-076/077 ต้องการ ≥10 คน · TC-080/081 ต้องการ ≥5 คน · ถ้าหาไม่ครบ เกณฑ์ % จะไม่มีความหมายทางสถิติ ต้องปรับเกณฑ์หรือยอมรับว่าเป็น indicative
