## 2. ตารางสืบกลับ

**วิธีเติม:** หนึ่งแถวต่อหนึ่ง requirement ในสโคป Phase 0 · เรียงตามชั้น (US → NFR → UX → BR → INV → §race → §error)

| # | Requirement ID | ที่มา | AC ID | TC ที่ครอบ | สถานะรัน | ผลล่าสุด | หมายเหตุ |
|---|---|---|---|---|---|---|---|
| 1 | `US-01` | product-backlog §… | `AC-…` | TC-001, TC-002 | ยังไม่รัน | — | |
| 2 | `US-02` | product-backlog §… | `AC-…` | TC-003, TC-004, TC-005 | ยังไม่รัน | — | |
| … | | | | | | | |

**ค่าที่ใช้ได้ในช่อง "สถานะรัน":** `ยังไม่รัน` · `รันได้` · `บล็อก` · `degraded`
**ค่าที่ใช้ได้ในช่อง "ผลล่าสุด":** `—` · `PASS` · `FAIL (BUG-xxx)` · `BLOCKED` · `DEGRADED`

> 🔴 **requirement ที่ไม่มี TC ห้ามปล่อยช่องว่าง** — ต้องเขียนเหตุผลในช่องหมายเหตุ (AC วัดผลไม่ได้ / อยู่นอก Phase / รอ design) มิฉะนั้นจะแยกไม่ออกระหว่าง *"ยังไม่ได้เขียน"* กับ *"ตั้งใจไม่เขียน"*

## 4. กติกาการดูแลเอกสารนี้

| เหตุการณ์ | ต้องอัปเดตอะไร |
|---|---|
| เพิ่ม/แก้ TC | แถวของ requirement ที่เกี่ยวข้อง |
| ออก AC ID ใหม่ | ช่อง AC ID ของแถวนั้น |
| รันเทสจบ 1 รอบ | ช่อง "สถานะรัน" และ "ผลล่าสุด" ทุกแถวที่รัน |
| requirement ใหม่เข้า Phase 0 | **เพิ่มแถวทันที** แม้ยังไม่มี TC — ให้ช่องว่างเป็นสัญญาณเตือน |

> เอกสารนี้คือที่เดียวที่ตอบคำถาม *"ถ้าเปิดร้านวันนี้ มีอะไรที่ไม่เคยถูกทดสอบเลยบ้าง"* — ถ้าไม่อัปเดต มันจะตอบผิดแบบมั่นใจ
