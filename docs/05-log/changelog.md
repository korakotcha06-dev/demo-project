## 2026-08-22 — เปิด/ปิด VAT ได้เองเมื่อร้านจดทะเบียน (A-08 · หน้าจอที่ 24)

คำสั่งของ Touch: *"เราต้องออกแบบให้เปิดและปิดได้ เมื่อถึงเวลาที่จด VAT"*

**ปัญหาที่แก้:** `shop.vat_enabled` มีอยู่ตั้งแต่ §10.1 แต่ **ไม่มีโค้ดที่ไหนเขียนมันเลย**
(grep เจอแต่ที่อ่าน 3 จุด ไม่มีที่เขียนแม้แต่จุดเดียว) → "วันที่จด VAT" กลายเป็น
งานของ developer ที่ต้องมารัน SQL มือ ไม่ใช่สวิตช์ที่เจ้าของร้านกดเองได้

### 🎯 แนวคิด: การจด VAT เป็นเหตุการณ์ ไม่ใช่ boolean

`vat_enabled` มีไว้ให้ runtime อ่านเร็ว · ตาราง `shop_vat_change` (append-only)
มีไว้ตอบคำถามที่ **snapshot ของบิลอย่างเดียวตอบไม่ได้**:

> "ทำไมบิลวันที่ 3 ไม่มี VAT แต่บิลวันที่ 4 มี"

วันที่ไม่มีบิลเลยก็ไม่มีหลักฐานอะไรว่าค่าตั้งเป็นอะไร · ประวัติจึงต้องเก็บแยก
พร้อมผู้ทำและเหตุผล และ **แก้/ลบไม่ได้** (`forbid_hard_delete` + `forbid_update`
ชุดเดียวกับที่ `payment` ใช้)

### สิ่งที่บังคับที่ฐานข้อมูล ไม่ใช่ที่ฟอร์ม

```sql
CHECK (NOT vat_enabled OR (tax_id IS NOT NULL AND branch_no IS NOT NULL
       AND tax_invoice_prefix IS NOT NULL AND vat_registered_on IS NOT NULL))
```

🔴 **เปิด VAT โดยไม่มีเลขประจำตัวผู้เสียภาษีไม่ได้** — เพราะใบกำกับที่ไม่มีเลข
ผู้เสียภาษีคือเอกสารที่ใช้ไม่ได้ และจะรู้ตัวตอน**ลูกค้าเอาไปยื่นภาษีแล้ว**
เหตุผลเดียวกับที่ §4.2 ทำให้สถานะโต๊ะแก้ด้วยมือไม่ได้

### เลขที่ใบกำกับภาษี — สามอย่างที่ห้ามสับสน

| | เริ่มที่ | ใช้ซ้ำได้ไหม |
|---|---|---|
| `sequence_no` | 1 **ทุกบิล** | — เป็นลำดับออเดอร์ในบิล |
| `queue_no` | A01 **ทุกวัน** | ✅ ใช้ซ้ำได้เมื่อออเดอร์เดิมจบ (US-45) |
| **`tax_invoice_no`** | THY0001 **ครั้งเดียวตลอดอายุร้าน** | ❌ **ห้ามซ้ำ ห้ามใช้ซ้ำ ตลอดกาล** |

คำตัดสิน 3 ข้อที่มีเหตุผลกำกับ:

1. **ออกเลขตอนปิดบิล/รับเงิน ไม่ใช่ตอนเปิดบิล** — บิลที่เปิดแล้วไม่มีใครจ่าย
   (ลูกค้าเดินหนี) ต้องไม่กินเลขไป · **ช่องว่างในลำดับเลขที่ใบกำกับคือสิ่งที่
   ต้องไปอธิบายกับสรรพากร**
2. **`next_number` ไม่รีเซ็ตเมื่อปิด VAT แล้วเปิดใหม่** — เลขที่ออกไปแล้วห้ามวนกลับ
   มาใช้ซ้ำ ต่อให้เว้นช่วงไปเป็นปี
3. **เปลี่ยน prefix หลังออกใบไปแล้วไม่ได้** — THY0001..THY0050 แล้วโดด CAFE0051
   อธิบายยากและดูเหมือนมีเอกสารหาย

ออกเลขด้วย `UPDATE tax_invoice_series SET next_number = next_number + 1 RETURNING`
บนแถวเดียว — ถ้าไปหา `max(tax_invoice_no)` จากตาราง `bill` สองเครื่องที่ปิดบิล
พร้อมกันจะได้เลขเดียวกันทั้งคู่ แล้วคนที่สองชน unique index → **ปิดบิลล้มทั้งที่
รับเงินไปแล้ว**

### A-08 — หน้าจอที่มีหน้าที่บอกสิ่งที่สวิตช์ *ไม่* ทำ

หน้าจอนี้ไม่ได้มีแค่สวิตช์ · สามข้อที่คนกดเดาเองไม่ได้และต้องเขียนบนจอ:

1. บิลที่ปิดไปแล้วไม่เปลี่ยน (snapshot ตาม §10.2)
2. 🔴 **บิลที่เปิดค้างอยู่ตอนนี้ก็ไม่เปลี่ยนด้วย** — snapshot ถูกตั้งตอน**เปิด**บิล
   บิลเหล่านั้นคิดตามค่าเดิมจนปิด · จอบอกจำนวนบิลที่ค้างและบอกว่าถ้าต้องการให้มีผล
   ทุกโต๊ะทันที ให้ปิดบิลที่ค้างให้หมดก่อน
3. ราคาบนเมนูไม่เปลี่ยน — เปลี่ยนแค่ว่าใบเสร็จแยกบรรทัด VAT ออกมาไหม

พร้อม**ตัวอย่างเลขจริง**ของเครื่องดื่ม 60 บาทในสองโหมด เพราะเลือกโหมดผิดแล้ว
ยอดที่เก็บจากลูกค้าไม่ตรงกับป้ายราคาในร้าน — เห็นเลขก่อนกดบันทึกดีกว่าไปเจอตอน
ลูกค้าทักว่า *"ป้ายบอก 60 ทำไมเก็บ 64"*

### 🔴 2 บั๊กที่เทสต์จับได้

**1. อ่านค่าก่อน commit** — `updateVatSettings` เรียก `getVatStatus` **ข้างใน**
`withTransaction` ซึ่งเปิด connection ของตัวเอง (`withShopScope`) จึงอ่านค่าเก่ากลับไป
→ กดเปิด VAT แล้วหน้าจอบอกว่ายังปิดอยู่ ทั้งที่ฐานข้อมูลเปลี่ยนแล้ว

**2. 🔴 วันที่จด VAT เลื่อนไป 1 วัน** — คอลัมน์ `date` ถูกไดรเวอร์แปลงเป็น JS `Date`
ที่เที่ยงคืนตามโซนเครื่อง (Asia/Bangkok = UTC+7) แล้ว `.toISOString()` แปลงกลับเป็น
UTC → **จด 2026-09-01 กลายเป็น 2026-08-31**
→ คืนเป็น `text` จาก Postgres ตรง ๆ ไม่แปลงผ่าน `Date` เลย

> 🎯 **บั๊กที่สองอันตรายกว่าที่ดู** — วันที่จดทะเบียนเป็นวันที่ทางภาษี
> ผิดวันเดียวก็ผิด และเป็นความผิดพลาดที่ไม่มีใครเห็นจนกว่าจะมีคนเทียบกับเอกสาร ภ.พ.20

### ยืนยันด้วยของจริงครบลำดับ

```
ยังไม่จด → ขาย 1 บิล      → ไม่มี VAT · ไม่มีเลขที่ (ถูกต้อง)
จด VAT                    → บิลเก่าไม่เปลี่ยน
ขาย 2 บิล                 → THY0001, THY0002 · VAT ฿3.93 ต่อบิล
ปิด VAT → ขาย             → ไม่คิด VAT และ **ไม่กินเลข**
เปิดใหม่ → ขาย            → THY0003 (ไม่วนกลับไป THY0001)
เปลี่ยน prefix เป็น CAFE   → 409 พร้อมบอกว่าออกใบไปแล้ว 3 ใบด้วย "THY"
พนักงาน (ไม่ใช่แอดมิน)     → 401
```

ตรวจในฐานท้ายสุด: ไม่มีบิลไหนที่ `NOT vat_enabled_snapshot` แต่มี `tax_invoice_no`

เทสต์เพิ่ม 28 เคสที่ทดสอบ **ลำดับเวลา ไม่ใช่สถานะเดี่ยว ๆ** (164 → **192 ผ่านทั้งหมด**)
เพราะสิ่งที่ผิดง่ายที่สุดคือบิลเก่าเปลี่ยนตามค่าใหม่ และเลขที่วนกลับมาใช้ซ้ำ —
สองอย่างนี้เห็นได้จากลำดับเท่านั้น · ย้อนโค้ดที่แก้แล้วเทสต์ล้มตรงจุดทั้ง 3 จุด

### ของแถมที่เจอตอนทำ

`ask_customer_name` ที่ migration 015 ใส่ไว้ **มี 0 แถว** — 015 INSERT ให้ร้านที่มี
อยู่ ณ ตอนนั้น แต่ `pnpm seed` สร้างร้านใหม่ทับ · โค้ด fallback เป็น `true` จึงทำงานได้
แต่ค่านั้น**จัดการไม่ได้**เพราะไม่มีแถวให้แก้ → 016 ใส่กลับให้

### แก้ที่เอกสารอ้างอิงเขียนเกินจริง

[[../02-design/02-technical/vat-tax-invoice-reference-v1|เอกสารอ้างอิง VAT]] §3
ฉบับแรกเขียนว่า *"ควรเปิดคอลัมน์เลขที่ใบกำกับก่อนเปิดร้าน แม้ยังไม่ใช้"* — **พูดเกินจริง**
บิลก่อนวันจด VAT ไม่ต้องมีเลขที่ใบกำกับ เพราะร้านยังไม่มีสิทธิ์ออก · เลขเริ่มนับที่
**วันจด** ไม่ใช่ย้อนไปวันเปิดร้าน จึงไม่มีอะไรต้องกรอกย้อนหลัง · แก้ในเอกสารแล้ว

### 🔴 5 บั๊กที่เจอตอนตรวจ (ไม่ได้เจอจากเทสต์ — เจอจากการขับของจริง)

**1. API ตอบ "สำเร็จ" ทั้งที่ไม่มีอะไรเปลี่ยน** — `parseBody` ใช้ Zod object ธรรมดา
ซึ่ง**ตัดคีย์ที่ไม่รู้จักทิ้งเงียบ ๆ** · ส่ง `{"isAvailable": false}` (camelCase ผิด
convention §1 ที่กำหนดว่า field ใน request เป็น snake_case) แล้วได้ `204 No Content`
ทั้งที่ฐานข้อมูลไม่ขยับ — client เข้าใจว่าบันทึกสำเร็จ
→ บังคับ `.strict()` ที่ `http.ts` **จุดเดียว** (ไฟล์ที่ architecture §2.1 กำหนดให้เป็น
จุดบังคับ contract) + เพิ่ม `requireAtLeastOneField()` กัน `PATCH {}` ที่ผ่าน schema
แต่ไม่เปลี่ยนอะไรแล้วตอบ 204 · ขัด §1 "ห้ามเขียนทับเงียบ ๆ" โดยตรง

**2. ข้อความ error กลืนเหตุผลจริง** — ชื่อซ้ำใช้ `errors.validation` ทำให้ผู้ใช้เห็นแค่
"ข้อมูลที่ส่งมาไม่ครบหรือไม่ถูกต้อง" ส่วนเหตุผลจริง (`มีเมล็ด "X" อยู่แล้ว`) ถูกซ่อนใน
`details` ที่ UI ไม่ได้อ่าน · ขัด api-design §1 ("message_th เป็นข้อความที่แสดงต่อผู้ใช้จริง")
และ UX §6 (error ต้องบอกว่าทำอะไรต่อได้เสมอ)
→ `errors.duplicateName` (409) มี `message_th` + `next_action` ของตัวเอง
**ชื่อซ้ำเป็นกฎธุรกิจ ไม่ใช่ input ผิดรูป** จึงต้องมีข้อความของตัวเองเหมือน `CATEGORY_HAS_PRODUCTS`

**3. ป้าย QR พิมพ์ออกมาผิดขนาด** — ป้ายประกาศ `width="396" height="559"` (px เปล่า)
ซึ่งเป็น A6 ที่ 96dpi พอดี **แต่เบราว์เซอร์แต่ละตัวตีค่า px เป็นขนาดจริงตอนพิมพ์ไม่เท่ากัน**
ป้ายที่พิมพ์เล็กกว่าที่ออกแบบ = QR เล็กลง = กล้องมือถือจับไม่ติดที่ระยะนั่งปกติ
→ US-44 ("ป้ายพร้อมพิมพ์") ล้มทั้งข้อโดยที่หน้าจอดูปกติดี
→ ประกาศ `105mm × 148mm` ให้ `viewBox` คุมพิกัดภายใน ได้ A6 จริงทุกเครื่องพิมพ์

**4. ฟอร์ม A-03 ทำตัวเลือกหาย** — คำนวณ `optionGroupIds` จาก `form` ที่มาจาก props
→ กด toggle สองตัวติดกันเร็ว ๆ React รวมเป็น batch เดียว ทั้งคู่อ่านค่าเดิม ตัวเลือกหนึ่งหาย
→ ใช้ updater form (`onChange(prev => ...)`) ทุกช่อง

**5. ปุ่ม "ไฟล์ PNG" ของป้าย QR พัง 500 ทุกใบ** — header ของ HTTP เป็น ByteString
(Latin-1) ใส่อักษรไทยลง `Content-Disposition` ตรง ๆ ทำให้ `new Response()` โยน TypeError
**ทั้ง response** ไม่ใช่แค่ชื่อไฟล์เพี้ยน · ชื่อโต๊ะเป็นไทยทุกใบ (`โต๊ะ 01`..`โต๊ะ 08`,
`QR เคาน์เตอร์`) → พังทั้งฟีเจอร์ 9 จาก 9 ใบ **ไม่ใช่เคสขอบ**
→ `attachmentHeader()` ตาม RFC 5987 (`filename` ASCII + `filename*=UTF-8''` ชื่อจริง)
วางไว้ใน `http.ts` เพราะจุดอื่นที่ส่งไฟล์จะเจอปัญหาเดียวกัน

> 🎯 **บั๊กข้อ 5 โผล่มาหลังหน้าจอทั้ง 8 "ผ่านการตรวจ" แล้ว** — เจอจากการกดปุ่มจริงบนหน้า A-07
> เทสต์ทั้ง 30 เคสเรียก `renderSignageSvg` ตรง ๆ จึง**ไม่แตะชั้น header เลย** ทั้งชุด

### 2. เลขคิว A01 + ชื่อถ้าลูกค้าใส่ — 🔴 แก้ Business Rule ข้อ 14

Touch ยืนยันหลังได้ฟังข้อกังวลแล้ว → **ข้อ 14 ที่เขียนว่า guest ordering "ต้องไม่เก็บ
ข้อมูลส่วนบุคคลของลูกค้าเลย (ไม่มีชื่อ…)" ไม่เป็นจริงตามตัวอักษรอีกต่อไป**

**บันทึกการแก้ไว้ต่อท้ายข้อ 14 โดยไม่ลบข้อความเดิม** เพื่อรักษาร่องรอยว่ากฎเคยเข้มกว่านี้
และแก้ NFR-17 ให้ตรงกัน — **ไม่ปล่อยให้โค้ดกับเอกสารขัดกันเงียบ ๆ**

#### วิธีลดผลกระทบให้เล็กที่สุดเท่าที่ยังตอบโจทย์

1. **ไม่บังคับกรอก** — เลขคิว A01 (US-45) ทำงานได้ด้วยตัวเอง ไม่ใส่ชื่อก็สั่งได้ครบ
2. **เฉพาะช่องทางเคาน์เตอร์** — ช่องทางโต๊ะใส่ชื่อไม่ได้เลย บังคับด้วย CHECK constraint
   เพราะเรียกด้วยเลขโต๊ะอยู่แล้ว · **ยิ่งขอบเขตแคบ ยิ่งมีที่ให้รั่วน้อย**
3. **ไม่มีตารางลูกค้า ไม่มีบัญชี** — ชื่ออยู่บนแถวออเดอร์ ไม่ผูกข้ามรอบการมาใช้บริการ
   สั่งครั้งหน้าไม่มีใครจำได้ → **ไม่มี profile ให้สะสม** (เทสยืนยันว่าไม่มีตาราง
   `customer` / `customer_profile` / `loyalty_member`)
4. 🔴 **จุดประสงค์หมดอายุตอนส่งมอบ** — ชื่อมีไว้เรียกลูกค้ามารับของ พอรับไปแล้วจุดประสงค์จบ
   → **trigger ลบชื่อทิ้งเมื่อออเดอร์ถึง `completed`/`cancelled`** บังคับที่ระดับฐานข้อมูล
   ไม่ใช่ที่ชั้นแอป **ด้วยเหตุผลเดียวกับที่ §4.2 ทำให้สถานะโต๊ะแก้ด้วยมือไม่ได้: ถ้าการลบ
   ข้อมูลส่วนบุคคลขึ้นอยู่กับว่ามีใครจำได้ว่าต้องเรียก วันหนึ่งจะมีคนลืม**
   · เลขคิวยังอยู่ (ไม่ใช่ข้อมูลส่วนบุคคล และใช้อ้างอิงย้อนหลังได้)
5. ร้านปิดการถามชื่อได้เองผ่าน `shop_setting.ask_customer_name`

#### สิ่งที่คำตัดสินนี้ลากเข้ามาและต้องยอมรับ

ชื่อที่ลูกค้าใส่เองเป็น**ข้อมูลส่วนบุคคลตาม PDPA แม้จะอยู่ชั่วคราว** → ต้องมี**ข้อความบอก
จุดประสงค์ตรงจุดที่กรอก** ("ใส่ชื่อสำหรับเรียกคิวเท่านั้น") ซึ่งเป็น notice แบบเบาที่
US-32 ยังไม่ครอบ

**แต่ไม่ได้ลากงาน US-32/33/34 ทั้งชุดเข้า Phase 0** เพราะไม่มีข้อมูลคงอยู่ให้ต้องขอเข้าถึง
หรือขอลบ (ระบบลบเองเมื่อออเดอร์จบ) — นี่คือเหตุผลที่ข้อ 4 ข้างบนสำคัญกว่าที่ดูเผิน ๆ
**การทำให้ข้อมูลหมดอายุเอง คือสิ่งที่กันงาน PDPA ทั้งชุดไม่ให้ไหลเข้า Phase 0**

### สิ่งที่ยังไม่ทำในรอบนี้

UI ของช่องทางเคาน์เตอร์ (US-28/29/30 · S-03 · S-04) ยังเป็นงานรอบถัดไป — รอบนี้วาง
schema + กฎ + เทส 8 เคสไว้ก่อน เพราะเพิ่มคอลัมน์ตอนยังไม่มีข้อมูลจริงถูกกว่า migration
บนระบบที่ร้านกำลังขายอยู่ (หลักเดียวกับ `shop_id` ใน §11.3)

nfr-v1 §9 ข้อ 4 บันทึกค่าที่ใช้ไปก่อนว่า **"ตั้งจอล็อกเป็นปิดไว้จนกว่า NFR-11 จะเสร็จ"**
ด้วยเหตุผลว่าถ้าบังคับพิมพ์รหัสผ่านเต็มด้วยมือเปียก พนักงานจะปิดจอล็อกทิ้งไปเลย ซึ่งแย่กว่า
ไม่มีจอล็อกตั้งแต่แรก · การ build จริงทำให้ไม่ต้องเลือกระหว่าง "ไม่ปลอดภัย" กับ "ใช้งานไม่ได้"

### 🔴 สองเรื่องที่เอกสารไม่ได้บอก แต่ถ้าไม่ทำจอล็อกจะไร้ความหมาย

**1. การล็อกอัตโนมัติต้องวัดจาก "คนแตะจอ" ไม่ใช่ "มี request เข้ามา"**

§10.3 บอกแค่ "จอล็อกอัตโนมัติเมื่อไม่มีการใช้งาน" แต่ไม่ได้นิยามว่า *การใช้งาน* คืออะไร ·
ปัญหาคือ **จอสถานี poll ทุก 5 วินาที** ตาม polling fallback ของ §3.3 → ถ้าวัด idle จาก
`last_seen_at` (ซึ่ง NFR-10 บังคับให้อัปเดตทุก request เพื่อให้ session อยู่ตลอดกะ)
**จอจะไม่ล็อกเลยตลอดกาล**

→ แยก `last_interaction_at` ออกจาก `last_seen_at` · client ยิง `/staff/interaction`
เฉพาะเมื่อมี `pointerdown`/`keydown` จริง throttle 1 ครั้งต่อนาที · ผลพลอยได้คือการล็อก
คำนวณที่ฝั่งเซิร์ฟเวอร์ ปิด JS แล้วเลี่ยงไม่ได้

**2. จอล็อกต้องกันการกระทำ ไม่ใช่กันแค่ภาพ**

ถ้าปิดกั้นแค่ที่ UI การล็อกจะเป็นเครื่องประดับ — ยิง API ตรง ๆ ก็ทำงานได้ปกติ ·
เพิ่ม `requireUnlocked()` ใน **ทุก endpoint ที่เปลี่ยนข้อมูล (6 จุด)** ยืนยันแล้วว่าได้
**HTTP 423 STATION_LOCKED**

⚠️ **ไม่ปิดกั้นการอ่านโดยเจตนา** — จอที่ล็อกอยู่ยังต้อง poll คิวออเดอร์ต่อได้ เพื่อให้
ปลดล็อกแล้วเห็นข้อมูลล่าสุดทันที และ**เสียงแจ้งเตือนออเดอร์ใหม่ต้องไม่หายไปตอนจอล็อก**
(ออเดอร์ที่เข้ามาตอนจอล็อกยังเป็นเรื่องที่พนักงานต้องรู้)

แก้ด้วยการใช้ `ref` เป็นแหล่งความจริง (ไม่ใช้ effect เพราะ `setState` ใน effect body

**บนแท็บเล็ตช้าที่พนักงานกดรัวด้วยมือเปียกตาม UX-09 อาการนี้จะกลายเป็น "ใส่ PIN แล้วไม่ครบ"

### ทำตามคำเตือนของ §10.3 ที่ระดับราก

§10.3 เตือนว่า **ห้ามใช้ `type="password"`** เพราะ password manager จะเด้งกล่องมาทับทั้งฟอร์ม

- หมวดหมู่เมนู **ห้าม hardcode** — ถ้าอนาคตร้านจะเพิ่มเมนูปั่นจริง เพิ่มเป็นหมวดใหม่ผ่าน US-23 (จัดการเมนู) ได้เลยโดยไม่ต้องแก้โครงสร้างระบบ บันทึกไว้ทั้งใน backlog และเอกสารเมนู
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] (US-42/US-43 เข้า Phase 0) และ [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] — กลุ่มงาน A ได้ task ใหม่ 5 รายการจาก US-42, กลุ่มงาน B ได้ task ความหวาน และ **แก้ task เดิมที่ล้าสมัยแล้ว 3 จุด**: จำนวนโต๊ะไม่ใช่ค่าคงที่อีกต่อไป · หมวดหมู่เมนูยืนยันแล้วไม่ต้องถามซ้ำ · รายชื่อสินค้าตั้งต้นมีร่างแล้ว งานเปลี่ยนเป็น "ให้ Touch เคาะราคาขายจริง"
- **NEED-INPUT ใหม่ที่ยังเปิด:** ขอบเขต layout โต๊ะ (ผังง่าย vs drag-and-drop) · สเกลความหวานขาด **75%** โดยตั้งใจหรือตกหล่น (สเกลไทยทั่วไปคือ 0/25/50/75/100%) · default ความหวานควรเป็น 100% (สูตรร้าน) หรือ 50% ตามนโยบายกรมอนามัยที่มี 9 แบรนด์เข้าร่วมตั้งแต่ 11 ก.พ. 2569 · ราคาขายจริง · มีขนาดแก้ว S/M/L ไหม · เปลี่ยนนมโอ๊ตฟรีเหมือน UNO หรือคิดเงิน — **NEED-INPUT ที่ปิดแล้วในรอบนี้:** จะมีเมนูปั่นไหม → ไม่ทำ

## 2026-08-11 — Touch อนุมัติ US-37 ถึง US-41 จาก UX Journey Map เข้า backlog จริง (หมวด 2.8 + Business Rule ข้อ 22-23)

- **การตัดสินใจสำคัญข้อที่ 2 — แยก accessibility baseline ออกจาก US-40 อย่างเด็ดขาด:** baseline (font ≥16px, contrast ≥4.5:1, touch target ≥44×44px, ห้ามใช้สีเดี่ยวสื่อความหมาย) เป็น **non-functional requirement ที่ต้องมีตั้งแต่ Phase 0** บันทึกเป็น **Business Rule ข้อ 23** — US-40 เป็นแค่ "โหมดพิเศษ" opt-in ที่ขยายใหญ่กว่า baseline อีกชั้น การที่ US-40 เป็น P2 **ไม่ใช่ข้ออ้างให้ baseline หลุดใน Phase 0-1** ผลลัพธ์: เพิ่ม checklist บังคับใน [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] หัวข้องานข้ามกลุ่ม ที่กลุ่มงาน B/C/F ต้องผ่านครบก่อนถือว่าเสร็จ — **นี่คือเนื้อหางาน Phase 0 ที่เพิ่มขึ้นจริงในรอบนี้ ไม่ใช่แค่โน้ต**
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]: US-37/38/39/41 เข้า Phase 1, US-40 เข้า Phase 2, พร้อมโน้ตว่า US-38/US-39 ควรทำเป็นชุดเดียวกันเพราะใช้กลไก realtime/สถานะร่วมกับ US-05
- เพิ่มโน้ต cross-reference ใน US-05 (จะถูกเสริมด้วย US-38/39), US-13/US-14 (จะถูกเสริมด้วย US-41), US-30 (เป็น fallback ปัจจุบันของป้าน้อย ซึ่ง US-40 จะช่วยลดการพึ่งพา) — **ไม่เปลี่ยน priority/phase ของ US-01 ถึง US-36 สักตัว**
- **ตัดสินใจไม่เตรียมทางให้ US-38 ใน Phase 0** — ต่างจาก US-41 ที่ต้องการแค่ timestamp ตอนออเดอร์เข้าระบบ (เล็กจริง จึงเพิ่ม task ไว้ในกลุ่มงาน D กัน rework) การคำนวณ ETA ต้องมีอัลกอริทึมที่ยังไม่ได้ออกแบบ (เวลาเตรียมเฉลี่ยต่อสินค้า, ตำแหน่งคิวแยกตาม channel) การ commit schema ล่วงหน้าเสี่ยง rework สูงกว่าจะไม่ทำเลย — เลื่อนทั้งก้อนไป Phase 1 ให้ COULSON ตรวจซ้ำตอนออกแบบจริง
- **NEED-INPUT ที่ยังเปิดและกระทบลำดับความสำคัญโดยตรง:** ความรุนแรงของช่วง peak (ถ้าหนักจริง US-41 เลื่อนขึ้น P0/Phase 0) และสัดส่วนลูกค้าสูงวัย/ไม่คุ้นสมาร์ทโฟน (ถ้าสูง US-40 เลื่อนขึ้น P1) — ประเด็น "จะทำ SMS/LINE ไหม" ถือว่าปิดแล้วด้วย default = ไม่ทำในสโคปนี้

- Touch ขอให้วิเคราะห์ backlog ทั้งหมดเทียบกับ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA) — ไล่ตรวจทุก actor/story/business rule ใน [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] หาจุดที่เก็บ/ประมวลผลข้อมูลส่วนบุคคล

- จุดเดียวที่เก็บข้อมูลส่วนบุคคล (เบอร์โทรสำหรับ loyalty stamp card, US-11 ใน Phase 1) มีช่องว่างจริง 3 เรื่อง: **(1)** consent ที่มีอยู่เป็นแค่ checkbox ไม่ครบองค์ประกอบ PDPA (เฉพาะเจาะจง/ได้รับข้อมูลครบ/เพิกถอนได้/อิสระ) **(2)** ไม่มีช่องทางให้ลูกค้าขอเข้าถึง/แก้ไข/ลบ/เพิกถอนข้อมูลของตัวเอง **(3)** ไม่มีการกำหนดระยะเวลาเก็บข้อมูล (retention)
- เพิ่ม Business Rule ข้อ 15-21 (consent quality, สิทธิเจ้าของข้อมูล, retention-NEED-INPUT, access control ภายใน, รายงานต้อง aggregate เท่านั้น, กระบวนการแจ้งเหตุข้อมูลรั่วไหล, ข้อมูลบัญชีพนักงานเก็บเท่าที่จำเป็น) และ user story ใหม่ 3 ข้อ (หมวด 2.6): **US-32** (privacy notice ตอนสมัคร loyalty), **US-33** (ช่องทางลูกค้าขอใช้สิทธิ์), **US-34** (แอดมินดำเนินการลบ/แก้ไขข้อมูลจริง) — ทั้งหมดผูกกับ US-11 ต้อง ship พร้อมกัน
- เพิ่มโน้ตล่วงหน้าใน US-21 (ใบเสร็จดิจิทัล) และ US-12 (จ่ายเงินออนไลน์) เตือนว่าถ้าสร้างจริงในอนาคตจะเป็นจุดเก็บข้อมูลใหม่ที่ต้องพิจารณา PDPA แยกต่างหาก — ยังไม่ใช่ช่องว่างตอนนี้เพราะยังไม่ได้สร้าง
- **NEED-INPUT ใหม่:** ระยะเวลาเก็บข้อมูล loyalty หลังลูกค้าเลิกใช้งาน — Touch ต้องกำหนดก่อน US-11 launch จริง (Business Rule ข้อ 17)
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] เพิ่ม US-32/33/34 เข้า Phase 1 คู่กับ US-11 และ [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] เพิ่มโน้ตให้ track งานนี้ตอนแตก Phase 1 เป็น task breakdown ในอนาคต (ไม่กระทบ task ของ Phase 0)
- ย้ำชัดเจน: นี่คือ**การวิเคราะห์ช่องว่างระดับวิศวกรรม ไม่ใช่คำแนะนำทางกฎหมาย** — Touch ควรให้ที่ปรึกษากฎหมายด้าน PDPA ยืนยันก่อนเปิดใช้งาน loyalty program จริง

## 2026-08-02 — รวม actor "ครัว/บาร์" กับ "แคชเชียร์" เป็นบทบาทเดียว (station model แบบ configurable)

- Touch แก้ actor-model assumption ที่ฝังอยู่ใน v1 ตั้งแต่ต้น — ร้านนี้เครื่องชงกาแฟ/จุดเตรียมของอยู่ติดเคาน์เตอร์จริง คนเดียวกันรับเงินและทำเครื่องดื่มเอง ไม่ต้องมีบทบาท/หน้าจอ "พนักงานครัว/บาร์" แยกจาก "พนักงานแคชเชียร์" สำหรับ MVP ของร้านนี้ — real-world flow คือ: ลูกค้าสั่ง → แคชเชียร์รับเงิน → ตั๋ว/สลิปออก → คนเดิมทำเครื่องดื่มเอง → จบ
- อัปเดต [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]]: รวม 2 actor เดิมเป็น "พนักงานแคชเชียร์/หน้าร้าน" ในตารางที่ 1 (พร้อมโน้ตว่าห้าม hardcode ว่ามีบทบาทรวมนี้ตลอดไป), ปรับ actor + AC ของ US-13 ถึง US-17 ให้สะท้อนความจริงนี้โดย**ไม่ตัดความสามารถเดิมทิ้งสักข้อ** (เห็นออเดอร์ใหม่, อัปเดตสถานะ, แจ้งเตือน, มาร์กของหมด, ดูประวัติกะ ยังจำเป็นเหมือนเดิม เพียงแสดงบนจอเดียวกับที่รับเงิน), เพิ่ม Business Rule ข้อ 13 (station model แบบ configurable — default คือสถานีรวมเดียว ไม่ hardcode), เพิ่ม US-31 (แอดมินตั้งค่าสถานีในอนาคต, P2/Phase 2)
- ปรับ US-28/US-29/US-30 (ช่องทางเคาน์เตอร์) เล็กน้อยให้ตรงกับความจริงที่ว่าคนที่รับเงินกับคนที่ทำเครื่องดื่มเป็นคนเดียวกัน — ยืนยันว่า flow เดิมที่วางไว้ (โดยเฉพาะ US-30 ที่ออกแบบไว้เป็น 1 ขั้นตอนรวดเดียวอยู่แล้ว) เข้ากันได้ดีกับข้อมูลใหม่นี้ ไม่ขัดแย้งกัน
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]: เปลี่ยน Actor column ของ US-13-17 เป็น "แคชเชียร์/หน้าร้าน" เพิ่ม US-31 เข้า Phase 2 และระบุชัดว่านี่คือข่าวดีสำหรับความเร็วของ Phase 0
- อัปเดต [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]]: **รวมกลุ่มงาน D (เดิมคือครัว/บาร์) กับกลุ่มงาน E (เดิมคือแคชเชียร์) เป็นกลุ่มงาน D เดียว** — ลดจำนวนหน้าจอที่ COULSON ต้องออกแบบและ BANNER ต้องพัฒนาแยกกันสำหรับ Phase 0 ลงจริง (ไม่ใช่แค่เปลี่ยนชื่อ) เลื่อนกลุ่มงานเดิม F→E (แอดมิน), G→F (เคาน์เตอร์/takeaway) เพื่อให้ตัวอักษรเรียงต่อเนื่อง
- นี่คือการแก้ไขเชิงโครงสร้างที่ใหญ่กว่ารอบก่อนหน้า (กระทบ actor model ไม่ใช่แค่ business rule เดียว) แต่ผลลัพธ์สุทธิคือ **Phase 0 เบาลง** ไม่มี blocker ใหม่เกิดขึ้น
