- **ข้อห้ามที่ตามมาโดยตรง (บันทึกใน `design-system-adoption-v1` แล้ว):** ห้ามแก้ปัญหา "เมนูยาว" ด้วยการยุบร้อน/เย็นกลับเป็นการ์ดเดียวแล้วใส่ toggle — นั่นคือการเอา tap กลับมาซึ่งเป็นสิ่งที่ Touch ตัดสินใจไม่เอา · ถ้ายาวเกินไปให้แก้ด้วย **การนำทาง** (chip หมวดปักด้านบน, SectionHeader ตามกลุ่มสินค้า) ไม่ใช่เพิ่มขั้นตอนให้ลูกค้า

- XAVIER เพิ่ม **หัวข้อ 3.5** ใน [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] — ตาราง MoSCoW ครบ **US-01 ถึง US-43 ไม่ตกสักตัว** พร้อมเกณฑ์ตัดสินที่เขียนไว้ในเอกสาร (ไม่ใช่แค่ผลลัพธ์) และเพิ่มคอลัมน์ MoSCoW เข้าตาราง Phase 0/1/2 ใน [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]

- **ผลรวม:** Must 16 · Should 22 · Could 5 · Won't 0 (มี 3 รายการนอก user story ที่เป็น Won't จริง — เดลิเวอรี่ภายนอก/จองโต๊ะล่วงหน้า/multi-branch พร้อมเงื่อนไขกลับมาพิจารณา) · **Phase 0: Must 13 / Should 10 = Must 56.5%** ใต้เกณฑ์เตือน 60% แต่ก้ำกึ่ง ควรเฝ้าระวัง
- **ประกาศชัดว่า MoSCoW ไม่แทน P0/P1/P2 + Phase** — MoSCoW ตอบว่า "ตัดอะไรได้ถ้าเวลาไม่พอ" ส่วน Phase ตอบว่า "ส่งมอบอะไรก่อนหลัง" **ไม่มี Priority หรือ Phase ของ US ใดถูกเปลี่ยนเลย**
- **สิ่งที่ MoSCoW เผยออกมาซึ่ง P0/P1/P2 บังไว้** — story ที่เป็น P0/Phase 0 แต่จริง ๆ เป็นแค่ Should เพราะมี workaround ที่ built-in อยู่ใน backlog เองอยู่แล้ว: **US-42** (จัดผังโต๊ะ — ความสามารถขั้นต่ำ "สร้างโต๊ะ+ได้ QR" มีครบใน US-24 ที่เป็น Must) · **US-28/29** (ซื้อกลับผ่าน QR เอง — US-30 พนักงานคีย์แทนรองรับลูกค้าเคาน์เตอร์ได้ทั้งหมด) · **US-35/36/43** (คั่ว/เมล็ดพิเศษ/ความหวาน — ทุกตัวมี default อัตโนมัติ)
- **ข้อสังเกตด้านความปลอดภัยที่ MoSCoW ทำให้เห็น:** US-09 (หมายเหตุถึงพนักงาน) ถูก flag ⚠️ ว่ากรณี **"แจ้งแพ้อาหาร"** อาจสมควรแยกออกมาพิจารณาเป็น Must ต่างหาก เพราะเป็นความเสี่ยงด้านความปลอดภัย ไม่ใช่แค่ความสะดวก — **เป็นการค้นพบใหม่จากการทำ MoSCoW ไม่ใช่ NEED-INPUT เดิม** ยังไม่เปลี่ยน Phase เอง รอ Touch
- **ลำดับการตัดถ้าเวลาไม่พอ (3 อันดับแรก):** US-42 → ชุด US-35/36/43 → US-06/US-07 พร้อมระบุว่าตัดแล้วใครรับภาระแทน (ส่วนใหญ่คือแอดมินและ P4 เบียร์)
- **ข้อเสนอที่รอ Touch ตัดสิน (XAVIER ไม่ย้ายเอง):** ผลัก US-42 ลง Phase 1 เพื่อลดความเสี่ยงสโคป Phase 0

### 4. วาด User Journey เป็น Mermaid Diagram (Touch สั่ง)

- เพิ่มแผนภาพลงใน [[../01-requirements/01-spec/ux-journey-map-v1|01-spec/ux-journey-map-v1]] รวม **6 แผนภาพ**: `journey` 4 เส้น (J1 ฟ้า · J2 ต้น · J3 ป้าน้อย · J4 เบียร์) + `flowchart` 2 ผัง
- เพิ่มหัวข้อ **0.5 วิธีอ่านแผนภาพ** พร้อม**ตารางแปลงอารมณ์เป็นคะแนน 0-5** (😄+2→5 · 🙂+1→4 · 😐0→3 · 😕−1→2 · 😣−2→1) และประกาศว่า **ถ้าแผนภาพขัดกับตารางให้ยึดตาราง**
- **กฎการแปลงที่สำคัญที่สุด:** แถวที่มี 2 อารมณ์ (เช่น `🙂 +1 / 😕 −1 ถ้าคิวยาว`) ถูก **แยกเป็น 2 ขั้น ไม่ใช่เฉลี่ย** — เพราะจุดที่อารมณ์ตกคือสาระของ journey map การเฉลี่ยจะกลบสิ่งที่ต้องเห็นพอดี (J1 จึงเห็นชัดว่าคิวจ่ายเงินตกไปที่ 2 ซึ่งตรงกับ Moment of truth #2 อยู่แล้ว)
- เพิ่มหัวข้อ **4.5 แผนภาพทางแยกที่ `journey` แสดงไม่ได้** — เพราะ `journey` เดินเป็นเส้นตรงเท่านั้น แต่จุดที่ระบบพังจริงอยู่ที่ทางแยก: **(4.5.1)** ผังสแกน QR ครบเงื่อนไขตาม Business Rule ข้อ 2, 4, 7, 10, 11, 12 ทำให้เห็นชัด 3 เรื่องที่มักออกแบบพลาด — สถานะโต๊ะไม่เคยถูกกดเปลี่ยนด้วยมือเลยสักจุด · ของหมดกลางคันปฏิเสธเฉพาะรายการไม่ล้มทั้งบิล · ทางแยก dine-in/takeaway อยู่**หลัง**ยืนยันออเดอร์ไม่ใช่ตอนสแกน **(4.5.2)** ผังกู้สถานการณ์ของป้าน้อย ซึ่งจบลงที่กล่อง 🔴 ช่องว่างที่ยังไม่มี US รองรับ (ลูกค้าที่สั่งด้วยวาจาไม่มีทางรู้ว่าของเสร็จ) — ตรงกับที่ COULSON ทั้งสองฝั่งจับได้อิสระตอนออกแบบ `02-design`
- ตรวจ syntax ของ `journey` ทุกบล็อกด้วยสคริปต์แล้ว: จำนวนโคลอนถูกต้อง · ไม่มีลูกน้ำในป้ายขั้นตอน · คะแนนอยู่ในช่วง 0-5 · ความยาวป้ายไม่เกินที่อ่านได้ — **0 ปัญหา**

- **ความขัดแย้งในเอกสารต้นทางที่ COULSON ทั้งสองฝั่งจับได้ตรงกัน:** backlog (US-02/US-23) บอกว่า **ร้อน/เย็น = หมวดหมู่ 2 หมวด** แต่ `initial-menu-data-v1` จัดเป็น 5 กลุ่มตามชนิดเครื่องดื่มแล้วให้ร้อน/เย็นเป็น **คอลัมน์ราคา 2 คอลัมน์ของสินค้าตัวเดียวกัน** — เป็นคนละ data model กัน · **ยึด backlog ตามคำสั่ง "ใช้ตามเอกสารเรา" → ร้อน/เย็นเป็นหมวดหมู่ สินค้าแยกรายการตามอุณหภูมิ** (หน้าเมนูมีการ์ด ~30 ใบ ไม่ใช่ 19) ทั้งสองฝั่งเลือก default เดียวกันอยู่แล้วจึงไม่มี rework
- ประเด็นที่ COULSON ส่งกลับให้ XAVIER/Touch ตัดสิน ดูสรุปในเอกสารของแต่ละฝั่ง — ที่เร่งที่สุดคือ ความหมายของสถานะ "รอเสิร์ฟ" (label vs status field) ที่ XAVIER flag ไว้เองตั้งแต่รอบ US-30 และตอนนี้**บล็อกการออกแบบจริง**เพราะกระทบ 3 หน้าจอพร้อมกัน

## 2026-08-11 — Touch ปิด NEED-INPUT ที่กระทบ Phase 0 ครบทุกข้อ: layout ผังง่าย + ความหวาน 5 ระดับ default 50%

- Touch ตอบ 3 ประเด็นที่ค้างจากรอบก่อน — **ตอนนี้ไม่มี NEED-INPUT ที่กระทบ Phase 0 ค้างอยู่แล้ว** ที่เหลือทั้งหมดเป็นเรื่อง Phase 1/2
- **(1) ขอบเขต layout ของ US-42 = "ผังง่ายพอ"** ไม่ต้องทำ drag-and-drop floor-plan editor → **สโคป/เวลาของ Phase 0 ไม่บวมขึ้นจากข้อนี้** COULSON เริ่มออกแบบหน้าจอจัดการโต๊ะได้เลยโดยไม่ต้องรออะไรอีก — บันทึกกำกับไว้ว่าถ้าอนาคตต้องการ floor plan แบบลากวางจริง ให้เปิด backlog item ใหม่ ห้ามขยายสโคป US-42 เงียบ ๆ
- **(2) สเกลความหวาน = 5 ระดับ 0% / 25% / 50% / 75% / 100%** — Touch เพิ่ม 75% กลับเข้ามาตามที่ XAVIER ตั้งข้อสังเกตว่าร้านกาแฟไทยส่วนใหญ่ใช้ 5 ระดับ (ร่างรอบก่อนใช้ 4 ระดับตามคำสั่งเดิมเป๊ะโดยไม่เพิ่มเอง) — ไม่กระทบสโคปทางเทคนิค เป็นการเพิ่ม option value ในกลไก fixed-list เดิมของ US-35
- **(3) default ความหวาน = 50% ("หวานปกติ")** เปลี่ยนจาก 100% ที่เป็น default ชั่วคราวในร่างรอบก่อน — สอดคล้องกับนโยบายกรมอนามัยที่มี 9 แบรนด์กาแฟเข้าร่วมตั้งแต่ 11 ก.พ. 2569
- **ผลข้างเคียงของ default 50% ที่บันทึกเป็นงานเพิ่ม (ไม่ใช่แค่เปลี่ยนตัวเลข):** เมื่อ default ไม่ใช่ "สูตรเต็ม" อีกต่อไป ลูกค้าที่อยากได้หวาน 100% ต้องกดเปลี่ยนเอง — UI จึงต้องแสดงค่า 50% ที่ถูกเลือกไว้ให้เห็นชัด ห้ามซ่อนไว้เบื้องหลัง มิฉะนั้นจะเกิดเคส "เครื่องดื่มหวานไม่พอ" ที่ลูกค้าไม่รู้ตัวว่าไม่ได้เลือก และกลายเป็นงานแก้ของพนักงานหน้าร้าน (persona P4 เบียร์) แทน — เพิ่มเป็น **AC ใหม่ของ US-43** และ **task ใหม่ในกลุ่มงาน B** ส่งต่อ SHURI/COULSON
- อัปเดตครบทุกจุดที่เกี่ยวข้อง: [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] (US-43 AC + Notes, หัวข้อ 4 Scope, ตาราง NEED-INPUT หัวข้อ 5 ปิด 3 แถวเป็น resolved พร้อมเหตุผล) · [[../01-requirements/01-spec/initial-menu-data-v1|01-spec/initial-menu-data-v1]] (ตาราง option group 2 จุด, ข้อจำกัดข้อ 2, NEED-INPUT ข้อ 2-3 เป็น resolved) · [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] (แถว US-43 ใน Phase 0 + หมายเหตุน้ำหนักงาน) · [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] (กลุ่มงาน A ปิด NEED-INPUT layout, กลุ่มงาน B แก้เป็น 5 ค่า/default 50% + เพิ่ม task UX)
- ทุกจุดที่ปิด NEED-INPUT ใช้วิธี **ขีดฆ่าคำถามเดิมแล้วเขียนคำตอบต่อท้าย** ไม่ลบคำถามทิ้ง เพื่อรักษาร่องรอยว่าเคยตั้งสมมติฐานอะไรไว้และ Touch ตัดสินใจต่างจากสมมติฐานตรงไหน

## 2026-08-11 — requirement ใหม่กลุ่มงาน A/B: จัดผังโต๊ะเองได้ (US-42) + ความหวาน (US-43) + เมนูตั้งต้น 19 รายการ ตัดหมวดปั่นออก

- Touch ให้ requirement เพิ่ม 2 เรื่องที่กระทบ **Phase 0** ตรง ๆ: **(ก)** กลุ่มงาน A ต้องให้เจ้าของร้าน "วาง layout โต๊ะได้เองและเพิ่มได้ภายหลัง" **(ข)** กลุ่มงาน B ต้องมีรายชื่อสินค้าตั้งต้น หมวดร้อน/เย็น/ปั่น แต่ละเมนูเลือกความหวาน 0/25/50/100% ได้ โดยใช้ **UNO Coffee** เป็นราคาอ้างอิง — แล้ว Touch สั่งเพิ่มทันทีในรอบถัดมาว่า **"ตัดปั่นออก"** เหลือหมวด **ร้อน / เย็น**
- เพิ่ม **US-42** (เจ้าของร้านจัดผังโต๊ะเอง เพิ่ม/แก้/ปลดระวางโต๊ะได้ภายหลัง, P0/Phase 0, หมวด 2.4) และ **US-43** (ลูกค้าเลือกความหวาน 0%/25%/50%/100% default 100%, P0/Phase 0, หมวด 2.7) ลง [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]]
- **น้ำหนักงานของสองตัวนี้ต่างกันมาก และบันทึกแยกไว้ชัดใน roadmap:** US-42 **เพิ่มสโคป Phase 0 จริง** (หน้าจัดการโต๊ะใหม่ทั้งหน้า + data model ใหม่) ส่วน US-43 **แทบไม่เพิ่มสโคป** เพราะยืมกลไก option-group ที่ US-35 ต้องสร้างอยู่แล้วใน Phase 0 — เป็นแค่การเติมข้อมูลตัวเลือกอีกกลุ่ม
- **ข้อกำหนด data model ที่สำคัญที่สุดของรอบนี้ (ต้องรู้ก่อน finalize schema):** table entity ต้องแยก **table id ภายในที่คงที่ตลอดไป** ออกจาก **ชื่อ/เลขโต๊ะที่แสดงผลและแก้ไขได้** — QR ที่พิมพ์ไปแล้วผูกกับ id ไม่ใช่ชื่อ เพื่อให้เปลี่ยนชื่อโต๊ะทีหลัง (เช่น "โต๊ะ 5" → "โต๊ะริมหน้าต่าง") ได้โดยไม่ต้องพิมพ์ QR ใหม่ · ปลดระวางโต๊ะเป็น **soft delete** ห้ามลบประวัติออเดอร์ · ห้ามแก้/ปลดโต๊ะที่ยังมีบิลเปิดค้าง
- **ขอบเขต "layout" ถูกนิยามไว้เป็นสมมติฐานที่ประกาศชัด** = ผังอย่างง่าย (โซน/ลำดับ/ตำแหน่งคร่าว ๆ) **ไม่ใช่** drag-and-drop floor-plan editor — ถ้า Touch ต้องการแบบหลังจะกระทบสโคป Phase 0 จริง เป็น NEED-INPUT ที่ต้องปิดก่อน COULSON เริ่มออกแบบหน้าจอนี้
- ความหวานถูกยกออกจาก **US-08** (P1/Phase 1) มาเป็น US-43 (P0) → สโคปที่เหลือของ US-08 คือ น้ำแข็ง/ขนาดแก้ว/ท็อปปิ้ง/เพิ่มช็อต **ไม่เปลี่ยน priority/phase ของ US-08** Phase 1 เบาลงเล็กน้อย
- สร้างเอกสารใหม่ [[../01-requirements/01-spec/initial-menu-data-v1|01-spec/initial-menu-data-v1]] — เมนูตั้งต้น **19 รายการ** (เอสเปรสโซเบส 7 · ชา/มัทฉะ 4 · ช็อกโกแลต/นม 3 · ซิกเนเจอร์ 3 · ดริป 2) ราคา 40-140 บาท พร้อมหลักการตั้งราคา (เย็น = ร้อน + 5-10 บาท) และ option group ต่อรายการ
- **ความโปร่งใสของราคา — ทุกจุดราคากำกับที่มาไว้ครบ 32 จุด:** [UNO-ยืนยันหลายแหล่ง] 6 · [UNO-แหล่งเดียว] 7 · [อนุมานจากหลักการตั้งราคา] 6 · [ช่วงตลาด] 13 — **ไม่มีเมนูทางการของ UNO ที่เข้าถึงได้** ราคาทั้งหมดมาจากรีวิว/สื่อช่วง พ.ค.-ธ.ค. 2568 ไม่ใช่ราคาปัจจุบันที่ยืนยันได้ และ **UNO positioning เป็น specialty (เมล็ดเกอิชา) ราคาสูงกว่าร้านกาแฟเล็กทั่วไป** ถ้าทำเลของ Touch ไม่ตรงกัน ราคาชุดนี้อาจสูงเกินตลาด — Touch ต้องเป็นผู้เคาะราคาขายจริง เอกสารนี้คือจุดตั้งต้นให้แก้ ไม่ใช่ราคาสุดท้าย
- **การตัดหมวดปั่นออกทำให้ความน่าเชื่อถือของราคาสูงขึ้นจริง** — UNO ไม่มีเมนูปั่นเลยแม้แต่รายการเดียว (ค้นหลายแหล่งยืนยัน) ราคาปั่น 10 จุดในร่างแรกจึงเป็น [ช่วงตลาด] ทั้งหมด เมื่อตัดออก สัดส่วนราคาที่อ้างอิงจาก UNO จริงเพิ่มจาก ~31% เป็น ~41% — **ไม่มีสินค้าตัวใดหายไป** เพราะไม่มีรายการใดมีแต่ราคาปั่นอย่างเดียว
- หมวดหมู่เมนู **ห้าม hardcode** — ถ้าอนาคตร้านจะเพิ่มเมนูปั่นจริง เพิ่มเป็นหมวดใหม่ผ่าน US-23 (จัดการเมนู) ได้เลยโดยไม่ต้องแก้โครงสร้างระบบ บันทึกไว้ทั้งใน backlog และเอกสารเมนู
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] (US-42/US-43 เข้า Phase 0) และ [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] — กลุ่มงาน A ได้ task ใหม่ 5 รายการจาก US-42, กลุ่มงาน B ได้ task ความหวาน และ **แก้ task เดิมที่ล้าสมัยแล้ว 3 จุด**: จำนวนโต๊ะไม่ใช่ค่าคงที่อีกต่อไป · หมวดหมู่เมนูยืนยันแล้วไม่ต้องถามซ้ำ · รายชื่อสินค้าตั้งต้นมีร่างแล้ว งานเปลี่ยนเป็น "ให้ Touch เคาะราคาขายจริง"
- **NEED-INPUT ใหม่ที่ยังเปิด:** ขอบเขต layout โต๊ะ (ผังง่าย vs drag-and-drop) · สเกลความหวานขาด **75%** โดยตั้งใจหรือตกหล่น (สเกลไทยทั่วไปคือ 0/25/50/75/100%) · default ความหวานควรเป็น 100% (สูตรร้าน) หรือ 50% ตามนโยบายกรมอนามัยที่มี 9 แบรนด์เข้าร่วมตั้งแต่ 11 ก.พ. 2569 · ราคาขายจริง · มีขนาดแก้ว S/M/L ไหม · เปลี่ยนนมโอ๊ตฟรีเหมือน UNO หรือคิดเงิน — **NEED-INPUT ที่ปิดแล้วในรอบนี้:** จะมีเมนูปั่นไหม → ไม่ทำ

## 2026-08-02 — วิเคราะห์ช่องว่างด้าน PDPA ทั้ง backlog (gap analysis, ไม่ใช่คำแนะนำทางกฎหมาย)

- เพิ่มโน้ตล่วงหน้าใน US-21 (ใบเสร็จดิจิทัล) และ US-12 (จ่ายเงินออนไลน์) เตือนว่าถ้าสร้างจริงในอนาคตจะเป็นจุดเก็บข้อมูลใหม่ที่ต้องพิจารณา PDPA แยกต่างหาก — ยังไม่ใช่ช่องว่างตอนนี้เพราะยังไม่ได้สร้าง
- **NEED-INPUT ใหม่:** ระยะเวลาเก็บข้อมูล loyalty หลังลูกค้าเลิกใช้งาน — Touch ต้องกำหนดก่อน US-11 launch จริง (Business Rule ข้อ 17)
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] เพิ่ม US-32/33/34 เข้า Phase 1 คู่กับ US-11 และ [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] เพิ่มโน้ตให้ track งานนี้ตอนแตก Phase 1 เป็น task breakdown ในอนาคต (ไม่กระทบ task ของ Phase 0)
- ย้ำชัดเจน: นี่คือ**การวิเคราะห์ช่องว่างระดับวิศวกรรม ไม่ใช่คำแนะนำทางกฎหมาย** — Touch ควรให้ที่ปรึกษากฎหมายด้าน PDPA ยืนยันก่อนเปิดใช้งาน loyalty program จริง

## 2026-08-02 — รวม actor "ครัว/บาร์" กับ "แคชเชียร์" เป็นบทบาทเดียว (station model แบบ configurable)

- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]: เปลี่ยน Actor column ของ US-13-17 เป็น "แคชเชียร์/หน้าร้าน" เพิ่ม US-31 เข้า Phase 2 และระบุชัดว่านี่คือข่าวดีสำหรับความเร็วของ Phase 0
- อัปเดต [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]]: **รวมกลุ่มงาน D (เดิมคือครัว/บาร์) กับกลุ่มงาน E (เดิมคือแคชเชียร์) เป็นกลุ่มงาน D เดียว** — ลดจำนวนหน้าจอที่ COULSON ต้องออกแบบและ BANNER ต้องพัฒนาแยกกันสำหรับ Phase 0 ลงจริง (ไม่ใช่แค่เปลี่ยนชื่อ) เลื่อนกลุ่มงานเดิม F→E (แอดมิน), G→F (เคาน์เตอร์/takeaway) เพื่อให้ตัวอักษรเรียงต่อเนื่อง
- นี่คือการแก้ไขเชิงโครงสร้างที่ใหญ่กว่ารอบก่อนหน้า (กระทบ actor model ไม่ใช่แค่ business rule เดียว) แต่ผลลัพธ์สุทธิคือ **Phase 0 เบาลง** ไม่มี blocker ใหม่เกิดขึ้น
