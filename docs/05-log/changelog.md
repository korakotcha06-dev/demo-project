## 2026-08-16 — Touch ปิดคำถามระยะเวลาเก็บชื่อเล่น (R-1): **ล้างเป็น `NULL` ทุก 90 วัน**

- **คำตัดสิน:** เก็บชื่อเล่นไว้กับออเดอร์ แล้ว **ล้างเป็น `NULL` เมื่อออเดอร์อายุครบ 90 วัน** นับจากวันที่สร้างออเดอร์ · เป็น job ที่รันเป็นประจำ ไม่ใช่ล้างมือครั้งเดียว
- 🔧 **จุดที่พังง่ายที่สุดของข้อนี้ — เป็น column-level purge ไม่ใช่ row-level:** job ล้างข้อมูลทุกตัวที่มีอยู่ในระบบตอนนี้ (`customer_session`/`cart` อายุ 24 ชม.) **ลบทั้งแถว** · ถ้าเขียน job ใหม่ตามแบบเดิมโดยไม่คิด จะ **ลบออเดอร์อายุเกิน 90 วันทิ้งทั้งแถว = ข้อมูลบัญชี/ภาษีหาย** กู้ไม่ได้ และจะรู้ตัวตอนปิดงบ · ต้อง `UPDATE … SET <ช่องชื่อ> = NULL` เท่านั้น **ห้าม `DELETE`** — เขียนเตือนไว้ทั้งใน [[../01-requirements/01-spec/acceptance-criteria-v1|acceptance-criteria-v1]] §6.1 และ [[../02-design/02-technical/data-model-v1|data-model-v1]] สองจุด
- **แก้ตามคำตัดสิน:** [[../01-requirements/01-spec/nfr-v1|NFR-17]] เพิ่มเกณฑ์ที่วัดได้ด้วย query เดียว (ออเดอร์อายุ >90 วันต้องมีช่องชื่อเป็น `NULL` ทุกแถว) · [[../01-requirements/01-spec/product-backlog-v1|Business Rule ข้อ 14]] เพิ่มระยะเวลาเก็บ · [[../02-design/02-technical/data-model-v1|data-model-v1]] §7 ข้อ 7 เพิ่ม **ข้อยกเว้นรายคอลัมน์** ให้กฎ "เก็บ `orders` ไม่มีกำหนด" ที่เดิมไม่มีข้อยกเว้นเลย
- **เพิ่ม TC-072c** — สร้างออเดอร์ย้อนหลัง **91 วัน** และ **89 วัน** รัน job แล้วตรวจว่าใบแรกชื่อเป็น `NULL` ใบหลังชื่อยังอยู่ (พิสูจน์ว่าเกณฑ์ 90 วันถูกบังคับจริง ไม่ใช่ล้างหมด) · **นับแถวก่อน-หลังต้องเท่ากันเป๊ะและยอดเงินครบ** · รันซ้ำต้องไม่พังและไม่เปลี่ยนอะไรเพิ่ม → รวมเป็น **124 เคส** ปรับตัวเลขทุกไฟล์ที่อ้างถึงแล้ว
- 🔴 **ยังค้าง — PDPA gap analysis ต้องอัปเดต (งานของ XAVIER):** [[../01-requirements/01-spec/product-backlog-v1|backlog]] หัวข้อ 6 ยังสรุปว่า *"Phase 0 ทั้งหมดไม่เก็บข้อมูลส่วนบุคคลของลูกค้าเลย จึงไม่มีช่องว่างด้าน PDPA"* ซึ่ง **ใช้ไม่ได้แล้ว** — Phase 0 มีจุดเก็บข้อมูลส่วนบุคคลจุดแรกแล้ว ต้องตอบเพิ่มอย่างน้อย: ฐานทางกฎหมายที่ใช้เก็บ · privacy notice ที่จุดกรอก · สิทธิ์ขอดู/ขอลบก่อนครบ 90 วัน
- **ข้อสังเกตที่บันทึกไว้ (ไม่ใช่คำแนะนำทางกฎหมาย):** ชื่อเล่นถูกใช้งานจริงระดับนาที (ตั้งแต่สั่งจนรับของ) แต่เก็บ 90 วัน — ส่วนต่างนี้ไม่ผิดในตัวเอง แต่ต้องมีวัตถุประสงค์รองรับว่าเก็บไว้ทำอะไร (เช่น ตรวจข้อพิพาทออเดอร์ย้อนหลัง) เพราะหลักสัดส่วนของ PDPA ดูที่เก็บเท่าที่จำเป็นต่อวัตถุประสงค์ · ควรให้ที่ปรึกษากฎหมายยืนยัน

## 2026-08-16 — Touch ตัดสิน: เรียกรับของด้วย **ชื่อเล่น + เลขคิว** (โมเดลแบบ Starbucks) — แก้ requirement ตามโปรโตไทป์

- **คำตัดสิน:** ลูกค้ากรอกชื่อเล่นได้ และ **ชื่อเล่นถูกเก็บส่งไปกับออเดอร์** พนักงานเรียก *"คุณทัช คิว A317"* — **ใช้ทั้งสองอย่าง ไม่ใช่อย่างใดอย่างหนึ่ง**
- **ทิศทางการแก้: แก้ requirement ตามโปรโตไทป์ ไม่ใช่แก้โปรโตไทป์** — ข้อขัดแย้งข้อ 1 ที่ [[../02-design/01-prototypes/prototype-v1|prototype-v1]] รายงานไว้ ปิดด้วยการยอมรับว่าโปรโตไทป์ถูกและกฎเดิมแคบเกินจริง
- **[[../01-requirements/01-spec/nfr-v1|NFR-17]]** — จาก *"Phase 0 ห้ามเก็บข้อมูลส่วนบุคคลเลย"* เป็น *"เก็บได้ชนิดเดียวคือชื่อเล่นผูกกับออเดอร์"* · ยังห้ามเบอร์โทร/อีเมล/LINE ID/device fingerprint ทั้งหมดตามเดิม · สถานะฝั่ง design เปลี่ยนจาก ✅ เป็น 🔶 **ต้องออกแบบใหม่**
- **[[../01-requirements/01-spec/product-backlog-v1|Business Rule ข้อ 14]]** — แก้เหมือนกัน พร้อมเพิ่มข้อจำกัด 3 ข้อที่ต้องคงไว้: **ห้ามผูกชื่อเล่นข้ามออเดอร์เป็นโปรไฟล์ลูกค้า** (ชื่ออยู่กับออเดอร์ ไม่ใช่กับคน) · **ห้ามบังคับกรอก** · **เลขคิวยังเป็นตัวอ้างอิงหลักที่ค้นหาได้** ชื่อเล่นเป็นแค่ตัวช่วยเรียก
- **[[../03-testing/01-test-plan/test-case-v1|Test Case]]** — แก้ **TC-072** (จาก "ไม่พบ field ชื่อแม้แต่ field เดียว" เป็น "พบได้เฉพาะชื่อเล่น") และ **TC-055b** (ตัดข้อความ "ไม่มีการถามชื่อลูกค้าในทุกขั้นตอน" ออก) · **เพิ่ม 2 เคสใหม่: TC-072a** (ไม่กรอกชื่อต้องสั่งได้ครบ พิสูจน์ว่าไม่บังคับ) และ **TC-072b** (ชื่อเดียวกัน 2 ออเดอร์ต้องไม่ถูกผูกเข้าด้วยกัน พิสูจน์ว่าไม่มีโปรไฟล์) — รวมเป็น **123 เคส**
- **[[../02-design/02-technical/data-model-v1|Data Model v1]]** — มาร์ค PDPA guardrail ของตาราง `customer_session` และ invariant ข้อ 9 ว่า **ล้าสมัย รอ COULSON ออกแบบใหม่** · ยังไม่ตัดสินว่า field ชื่อเล่นจะอยู่กับ `orders` หรือ `customer_session` — **ไม่ได้ออกแบบแทน เพราะเป็นงานของ COULSON**
- 🔴 **ค้าง 1 ข้อที่ต้องให้ Touch เคาะ (R-1) — ระยะเวลาเก็บชื่อเล่น:** `orders` ถูกกำหนดให้ **เก็บไว้ไม่มีกำหนด** เพราะเป็นข้อมูลบัญชี/ภาษี ([[../02-design/02-technical/data-model-v1|data-model]] §7 ข้อ 7) — ถ้าชื่อเล่นติดไปด้วย ร้านจะสะสมชื่อลูกค้าแบบไม่มีวันหมดอายุ ทั้งที่ใช้จริงแค่ตอนเรียกรับของ · **ข้อเสนอ: ลบชื่อทิ้งเมื่อออเดอร์ถึงสถานะส่งมอบแล้ว/ปิดบิล** เก็บแถวออเดอร์ไว้ตามเดิม — ที่ร้านกาแฟทั่วไปชื่อบนแก้วหายไปพร้อมแก้ว · **ถ้าตอบว่าเก็บถาวร ต้องทำ PDPA gap analysis ใหม่ทั้งชุด** เพราะข้อสรุปเดิมใน backlog หัวข้อ 6 (*"Phase 0 ไม่มีช่องว่าง PDPA"*) ใช้ไม่ได้แล้ว
- **AC ที่ต้องออก ID ใหม่ รอ XAVIER:** ช่องชื่อเล่นไม่บังคับ (US-01/US-28) · ชื่อเล่นแสดงคู่เลขคิวทั้งฝั่งลูกค้าและตั๋วพนักงาน (US-45) · พนักงานกรอกชื่อแทนลูกค้าได้ (US-30)
- **Touch ยืนยันเจตนาเพิ่มเติม:** *"เริ่มสั่งก็กดได้ ถ้าไม่สะดวกใส่ชื่อก็เป็นคิวอย่างเดียว"* — ตรงกับ BR ข้อ 14 ที่แก้ใหม่แล้ว ไม่ต้องแก้ requirement เพิ่ม
- 🔴 **แต่ตรวจตัวโปรโตไทป์แล้วพบว่ายังบังคับกรอกจริง** — เปิดหน้าแรกแล้วกดปุ่มทั้งที่ช่องชื่อว่าง: `#go.disabled` เป็น `true` · กดแล้วไม่เกิดอะไรขึ้น · ทั้งหน้าไม่มีปุ่มข้ามเลย มีแค่ "เริ่มสั่ง" กับ "EN" · ต้นเหตุคือ `<button id="go" ${S.name.trim() ? '' : 'disabled'}>` คู่กับ `oninput` ที่คอยเปิด-ปิดปุ่มตามความยาวข้อความ
- **สิ่งที่ต้องแก้ในโปรโตไทป์:** ถอดเงื่อนไข `disabled` ออก + ทำให้หน้ายืนยันแสดง **เลขคิวอย่างเดียว** ได้สวยเมื่อไม่มีชื่อ (ไม่ใช่บรรทัดชื่อว่างเปล่าหรือค้างอักขระคั่น) · **ขยาย TC-072a ให้ตรวจสองข้อนี้โดยตรง — เคสนี้รันตอนนี้จะ FAIL**

## 2026-08-16 — นำเข้า interactive prototype 2 ตัว และตรวจว่าขัดกับ requirement ตรงไหน

- **ตรวจด้วยการกดเดินจริงทีละขั้น ไม่ได้อ่านจากซอร์ส** — ฝั่งลูกค้าเดินครบ ต้อนรับ → เมนู → ตัวเลือกสินค้า → ตะกร้า → ยืนยัน → **เลขคิว `A317`** → ปุ่ม "สั่งเพิ่ม" กลับหน้าเมนูได้ใน 1 tap · ฝั่งร้านล็อกอินด้วย PIN 4 หลักแล้วเข้าถึงได้ครบทั้ง Assign / Order / Queue / History / Menu / Dashboard
- **สร้าง [[../02-design/01-prototypes/prototype-v1|prototype-v1]]** — แม็ปหน้าจอในโปรโตไทป์กลับไปหา `C-xx`/`S-xx`/`A-xx` ใน [[../02-design/01-prototypes/screen-inventory-v1|screen-inventory-v1]] และ US ที่รองรับ พร้อมระบุว่าหน้าจอไหนยังไม่มี (`C-00`, `C-05`, `C-06`, `S-06`, `S-07`)
- 🔴 **พบ 4 จุดที่โปรโตไทป์ขัดกับ requirement — ต้องตัดสินก่อนสร้างจริง:**

  3. **เมนูและราคาไม่ตรงกับ [[../01-requirements/01-spec/initial-menu-data-v1|initial-menu-data-v1]]** — ลาเต้ ฿105 ราคาเดียว (สเปคคือ ฿60 ร้อน / ฿70 เย็น คนละการ์ด) · โครงหมวดเป็น 6 กลุ่มแทน 2 หมวดร้อน/เย็น · มีบรรทัดภาษีที่สเปคไม่เคยพูดถึง · มีเบเกอรี่ที่ไม่มีในเมนูตั้งต้น · **กระทบ TC-003 และ TC-004 ซึ่งเป็น P0** และโครงหมวด 6 กลุ่มขัดกับเหตุผลที่ Touch ใช้ตัดสินเองเมื่อ 2026-08-16 (แยกร้อน/เย็นเป็นคนละการ์ดเพราะนับ tap ในหน้างานจริง)

## 2026-08-15 — ปิดเรื่องร้อน/เย็น · เพิ่ม MoSCoW ครบ 43 story · สร้าง PEGGY + skill feature-journey · วาด journey เป็น Mermaid

### 1. ปิดประเด็น "ร้อน/เย็น" — Touch ยืนยัน พร้อมเหตุผลที่สำคัญกว่าตัวคำตอบ

- คำตอบจาก Touch: *"ร้อนเย็นแยกกันดีกว่า กดง่ายกว่าในหน้างานจริง"* → **ร้อน/เย็น = หมวดหมู่ · สินค้าแยกรายการตามอุณหภูมิ · หน้าเมนูมีการ์ด ~30 ใบ** ตรงกับที่ทั้ง `01-prototypes` และ `02-technical` เลือกไว้ก่อนหน้าโดยอิสระ **ไม่มี rework**
- **เหตุผลถูกบันทึกเป็นข้อผูกมัดของงานออกแบบต่อจากนี้ ไม่ใช่แค่เชิงอรรถ:** เกณฑ์ตัดสินคือ **จำนวน tap ในหน้างานจริง** ("ลาเต้เย็น" = 1 tap · การ์ดเดียวแล้วเลือกอุณหภูมิทีหลัง = 2 tap) ซึ่งหนุน UX-01 และหนุน P1 ฟ้า (เวลาพักจำกัด) กับ P3 ป้าน้อย (ทุกขั้นตอนเพิ่ม = ความเสี่ยงที่จะติด)
- **ข้อห้ามที่ตามมาโดยตรง (บันทึกใน `design-system-adoption-v1` แล้ว):** ห้ามแก้ปัญหา "เมนูยาว" ด้วยการยุบร้อน/เย็นกลับเป็นการ์ดเดียวแล้วใส่ toggle — นั่นคือการเอา tap กลับมาซึ่งเป็นสิ่งที่ Touch ตัดสินใจไม่เอา · ถ้ายาวเกินไปให้แก้ด้วย **การนำทาง** (chip หมวดปักด้านบน, SectionHeader ตามกลุ่มสินค้า) ไม่ใช่เพิ่มขั้นตอนให้ลูกค้า

### 2. เพิ่มการจัดลำดับความสำคัญแบบ MoSCoW (Touch สั่ง)

- XAVIER เพิ่ม **หัวข้อ 3.5** ใน [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] — ตาราง MoSCoW ครบ **US-01 ถึง US-43 ไม่ตกสักตัว** พร้อมเกณฑ์ตัดสินที่เขียนไว้ในเอกสาร (ไม่ใช่แค่ผลลัพธ์) และเพิ่มคอลัมน์ MoSCoW เข้าตาราง Phase 0/1/2 ใน [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]
- เลือกวางเป็นหัวข้อ **3.5 แทนการเลื่อนเลขหัวข้อ 4/5/6** เพราะมีจุดอ้างอิงเลขหัวข้อเดิมกระจายอยู่ ~20 จุดทั่วเอกสาร เสี่ยงแก้ไม่ครบแล้วเอกสารอ้างผิด
- **ผลรวม:** Must 16 · Should 22 · Could 5 · Won't 0 (มี 3 รายการนอก user story ที่เป็น Won't จริง — เดลิเวอรี่ภายนอก/จองโต๊ะล่วงหน้า/multi-branch พร้อมเงื่อนไขกลับมาพิจารณา) · **Phase 0: Must 13 / Should 10 = Must 56.5%** ใต้เกณฑ์เตือน 60% แต่ก้ำกึ่ง ควรเฝ้าระวัง
- **ประกาศชัดว่า MoSCoW ไม่แทน P0/P1/P2 + Phase** — MoSCoW ตอบว่า "ตัดอะไรได้ถ้าเวลาไม่พอ" ส่วน Phase ตอบว่า "ส่งมอบอะไรก่อนหลัง" **ไม่มี Priority หรือ Phase ของ US ใดถูกเปลี่ยนเลย**
- **สิ่งที่ MoSCoW เผยออกมาซึ่ง P0/P1/P2 บังไว้** — story ที่เป็น P0/Phase 0 แต่จริง ๆ เป็นแค่ Should เพราะมี workaround ที่ built-in อยู่ใน backlog เองอยู่แล้ว: **US-42** (จัดผังโต๊ะ — ความสามารถขั้นต่ำ "สร้างโต๊ะ+ได้ QR" มีครบใน US-24 ที่เป็น Must) · **US-28/29** (ซื้อกลับผ่าน QR เอง — US-30 พนักงานคีย์แทนรองรับลูกค้าเคาน์เตอร์ได้ทั้งหมด) · **US-35/36/43** (คั่ว/เมล็ดพิเศษ/ความหวาน — ทุกตัวมี default อัตโนมัติ)
- **ข้อสังเกตด้านความปลอดภัยที่ MoSCoW ทำให้เห็น:** US-09 (หมายเหตุถึงพนักงาน) ถูก flag ⚠️ ว่ากรณี **"แจ้งแพ้อาหาร"** อาจสมควรแยกออกมาพิจารณาเป็น Must ต่างหาก เพราะเป็นความเสี่ยงด้านความปลอดภัย ไม่ใช่แค่ความสะดวก — **เป็นการค้นพบใหม่จากการทำ MoSCoW ไม่ใช่ NEED-INPUT เดิม** ยังไม่เปลี่ยน Phase เอง รอ Touch
- **ลำดับการตัดถ้าเวลาไม่พอ (3 อันดับแรก):** US-42 → ชุด US-35/36/43 → US-06/US-07 พร้อมระบุว่าตัดแล้วใครรับภาระแทน (ส่วนใหญ่คือแอดมินและ P4 เบียร์)
- **ข้อเสนอที่รอ Touch ตัดสิน (XAVIER ไม่ย้ายเอง):** ผลัก US-42 ลง Phase 1 เพื่อลดความเสี่ยงสโคป Phase 0

### 4. วาด User Journey เป็น Mermaid Diagram (Touch สั่ง)

- เพิ่มแผนภาพลงใน [[../01-requirements/01-spec/ux-journey-map-v1|01-spec/ux-journey-map-v1]] รวม **6 แผนภาพ**: `journey` 4 เส้น (J1 ฟ้า · J2 ต้น · J3 ป้าน้อย · J4 เบียร์) + `flowchart` 2 ผัง
- เพิ่มหัวข้อ **0.5 วิธีอ่านแผนภาพ** พร้อม**ตารางแปลงอารมณ์เป็นคะแนน 0-5** (😄+2→5 · 🙂+1→4 · 😐0→3 · 😕−1→2 · 😣−2→1) และประกาศว่า **ถ้าแผนภาพขัดกับตารางให้ยึดตาราง**

- ความหวานถูกยกออกจาก **US-08** (P1/Phase 1) มาเป็น US-43 (P0) → สโคปที่เหลือของ US-08 คือ น้ำแข็ง/ขนาดแก้ว/ท็อปปิ้ง/เพิ่มช็อต **ไม่เปลี่ยน priority/phase ของ US-08** Phase 1 เบาลงเล็กน้อย
- สร้างเอกสารใหม่ [[../01-requirements/01-spec/initial-menu-data-v1|01-spec/initial-menu-data-v1]] — เมนูตั้งต้น **19 รายการ** (เอสเปรสโซเบส 7 · ชา/มัทฉะ 4 · ช็อกโกแลต/นม 3 · ซิกเนเจอร์ 3 · ดริป 2) ราคา 40-140 บาท พร้อมหลักการตั้งราคา (เย็น = ร้อน + 5-10 บาท) และ option group ต่อรายการ
- **ความโปร่งใสของราคา — ทุกจุดราคากำกับที่มาไว้ครบ 32 จุด:** [UNO-ยืนยันหลายแหล่ง] 6 · [UNO-แหล่งเดียว] 7 · [อนุมานจากหลักการตั้งราคา] 6 · [ช่วงตลาด] 13 — **ไม่มีเมนูทางการของ UNO ที่เข้าถึงได้** ราคาทั้งหมดมาจากรีวิว/สื่อช่วง พ.ค.-ธ.ค. 2568 ไม่ใช่ราคาปัจจุบันที่ยืนยันได้ และ **UNO positioning เป็น specialty (เมล็ดเกอิชา) ราคาสูงกว่าร้านกาแฟเล็กทั่วไป** ถ้าทำเลของ Touch ไม่ตรงกัน ราคาชุดนี้อาจสูงเกินตลาด — Touch ต้องเป็นผู้เคาะราคาขายจริง เอกสารนี้คือจุดตั้งต้นให้แก้ ไม่ใช่ราคาสุดท้าย
- **การตัดหมวดปั่นออกทำให้ความน่าเชื่อถือของราคาสูงขึ้นจริง** — UNO ไม่มีเมนูปั่นเลยแม้แต่รายการเดียว (ค้นหลายแหล่งยืนยัน) ราคาปั่น 10 จุดในร่างแรกจึงเป็น [ช่วงตลาด] ทั้งหมด เมื่อตัดออก สัดส่วนราคาที่อ้างอิงจาก UNO จริงเพิ่มจาก ~31% เป็น ~41% — **ไม่มีสินค้าตัวใดหายไป** เพราะไม่มีรายการใดมีแต่ราคาปั่นอย่างเดียว
- หมวดหมู่เมนู **ห้าม hardcode** — ถ้าอนาคตร้านจะเพิ่มเมนูปั่นจริง เพิ่มเป็นหมวดใหม่ผ่าน US-23 (จัดการเมนู) ได้เลยโดยไม่ต้องแก้โครงสร้างระบบ บันทึกไว้ทั้งใน backlog และเอกสารเมนู
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] (US-42/US-43 เข้า Phase 0) และ [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] — กลุ่มงาน A ได้ task ใหม่ 5 รายการจาก US-42, กลุ่มงาน B ได้ task ความหวาน และ **แก้ task เดิมที่ล้าสมัยแล้ว 3 จุด**: จำนวนโต๊ะไม่ใช่ค่าคงที่อีกต่อไป · หมวดหมู่เมนูยืนยันแล้วไม่ต้องถามซ้ำ · รายชื่อสินค้าตั้งต้นมีร่างแล้ว งานเปลี่ยนเป็น "ให้ Touch เคาะราคาขายจริง"
- **NEED-INPUT ใหม่ที่ยังเปิด:** ขอบเขต layout โต๊ะ (ผังง่าย vs drag-and-drop) · สเกลความหวานขาด **75%** โดยตั้งใจหรือตกหล่น (สเกลไทยทั่วไปคือ 0/25/50/75/100%) · default ความหวานควรเป็น 100% (สูตรร้าน) หรือ 50% ตามนโยบายกรมอนามัยที่มี 9 แบรนด์เข้าร่วมตั้งแต่ 11 ก.พ. 2569 · ราคาขายจริง · มีขนาดแก้ว S/M/L ไหม · เปลี่ยนนมโอ๊ตฟรีเหมือน UNO หรือคิดเงิน — **NEED-INPUT ที่ปิดแล้วในรอบนี้:** จะมีเมนูปั่นไหม → ไม่ทำ

## 2026-08-11 — Touch อนุมัติ US-37 ถึง US-41 จาก UX Journey Map เข้า backlog จริง (หมวด 2.8 + Business Rule ข้อ 22-23)

- Touch อนุมัติข้อเสนอทั้ง 5 ข้อที่ [[../01-requirements/01-spec/ux-journey-map-v1|01-spec/ux-journey-map-v1]] หัวข้อ 6 เสนอไว้ — เขียนลง [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] เป็น **หมวด 2.8 ใหม่** "ประสบการณ์การรอ การสื่อสารสถานะ และการเข้าถึง" (แก้ในไฟล์ v1 โดยตรง ไม่สร้าง v2 เพราะเป็นการเพิ่มเติม ไม่ใช่พลิกทิศทาง)
- **US-37** ปุ่มเรียกพนักงานดิจิทัล (P1/Phase 1, จาก J1+J3) · **US-38** ETA/จำนวนคิวที่เหลือ (P1/Phase 1, จาก J1+J2) · **US-39** แจ้งเตือนเชิงรุก (P1/Phase 1, จาก J2) · **US-40** โหมดเข้าถึงง่ายตัวอักษร/ปุ่มใหญ่ (P2/Phase 2, จาก J3) · **US-41** จัดลำดับ + aging indicator บนจอพนักงาน (P1/Phase 1, จาก J4)
- **การตัดสินใจสำคัญข้อที่ 1 — ขอบเขตของ US-39 ถูกจำกัดไว้ที่ in-app/session-scoped เท่านั้น:** ไม่รวม SMS/LINE/push ที่ต้องเก็บเบอร์โทรหรือ token ผูกอุปกรณ์ เพราะจะขัด Business Rule ข้อ 14 (guest ordering ต้องไม่เก็บข้อมูลส่วนบุคคล) — บันทึกเป็น **Business Rule ข้อ 22** ใหม่ ถ้าอนาคตจะยกระดับเป็น SMS/LINE ต้องเปิด user story ใหม่ + PDPA gap analysis แบบเดียวกับ US-32/33/34 ห้ามขยายสโคป US-39 เงียบ ๆ
- **การตัดสินใจสำคัญข้อที่ 2 — แยก accessibility baseline ออกจาก US-40 อย่างเด็ดขาด:** baseline (font ≥16px, contrast ≥4.5:1, touch target ≥44×44px, ห้ามใช้สีเดี่ยวสื่อความหมาย) เป็น **non-functional requirement ที่ต้องมีตั้งแต่ Phase 0** บันทึกเป็น **Business Rule ข้อ 23** — US-40 เป็นแค่ "โหมดพิเศษ" opt-in ที่ขยายใหญ่กว่า baseline อีกชั้น การที่ US-40 เป็น P2 **ไม่ใช่ข้ออ้างให้ baseline หลุดใน Phase 0-1** ผลลัพธ์: เพิ่ม checklist บังคับใน [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] หัวข้องานข้ามกลุ่ม ที่กลุ่มงาน B/C/F ต้องผ่านครบก่อนถือว่าเสร็จ — **นี่คือเนื้อหางาน Phase 0 ที่เพิ่มขึ้นจริงในรอบนี้ ไม่ใช่แค่โน้ต**
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]: US-37/38/39/41 เข้า Phase 1, US-40 เข้า Phase 2, พร้อมโน้ตว่า US-38/US-39 ควรทำเป็นชุดเดียวกันเพราะใช้กลไก realtime/สถานะร่วมกับ US-05
- เพิ่มโน้ต cross-reference ใน US-05 (จะถูกเสริมด้วย US-38/39), US-13/US-14 (จะถูกเสริมด้วย US-41), US-30 (เป็น fallback ปัจจุบันของป้าน้อย ซึ่ง US-40 จะช่วยลดการพึ่งพา) — **ไม่เปลี่ยน priority/phase ของ US-01 ถึง US-36 สักตัว**
- **ตัดสินใจไม่เตรียมทางให้ US-38 ใน Phase 0** — ต่างจาก US-41 ที่ต้องการแค่ timestamp ตอนออเดอร์เข้าระบบ (เล็กจริง จึงเพิ่ม task ไว้ในกลุ่มงาน D กัน rework) การคำนวณ ETA ต้องมีอัลกอริทึมที่ยังไม่ได้ออกแบบ (เวลาเตรียมเฉลี่ยต่อสินค้า, ตำแหน่งคิวแยกตาม channel) การ commit schema ล่วงหน้าเสี่ยง rework สูงกว่าจะไม่ทำเลย — เลื่อนทั้งก้อนไป Phase 1 ให้ COULSON ตรวจซ้ำตอนออกแบบจริง
- **NEED-INPUT ที่ยังเปิดและกระทบลำดับความสำคัญโดยตรง:** ความรุนแรงของช่วง peak (ถ้าหนักจริง US-41 เลื่อนขึ้น P0/Phase 0) และสัดส่วนลูกค้าสูงวัย/ไม่คุ้นสมาร์ทโฟน (ถ้าสูง US-40 เลื่อนขึ้น P1) — ประเด็น "จะทำ SMS/LINE ไหม" ถือว่าปิดแล้วด้วย default = ไม่ทำในสโคปนี้

## 2026-08-02 — เพิ่มฟีเจอร์เลือกระดับการคั่ว/เมล็ดกาแฟพิเศษตอนสั่ง (US-35, US-36)

- ขยาย Business Rule ข้อ 4 (สินค้าหมดระหว่างสั่ง) ให้ครอบคลุมกรณีตัวเลือกของสินค้าหมด (ไม่ใช่แค่ตัวสินค้าเต็ม) เพราะเมล็ดพิเศษเป็น option-level availability ไม่ใช่ full-item availability
- **NEED-INPUT ที่ resolved ด้วย default:** ระดับการคั่วเป็น **optional ไม่บังคับเลือก** default เป็น **"กลาง"** ถ้าลูกค้าไม่เลือก — ถ้า Touch ต้องการบังคับเลือกทุกครั้งต้องแจ้งกลับมา ไม่ใช่ตัวบล็อกงานตอนนี้
- ยืนยันว่าไม่กระทบ Business Rule ข้อ 2 (concurrent cart ต่อโต๊ะ) เพราะเป็นแค่ attribute ระดับ order line item เดียวกับตัวเลือกอื่น

## 2026-08-02 — วิเคราะห์ช่องว่างด้าน PDPA ทั้ง backlog (gap analysis, ไม่ใช่คำแนะนำทางกฎหมาย)

- Touch ขอให้วิเคราะห์ backlog ทั้งหมดเทียบกับ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA) — ไล่ตรวจทุก actor/story/business rule ใน [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] หาจุดที่เก็บ/ประมวลผลข้อมูลส่วนบุคคล
- **ผลสรุปสำคัญ: Phase 0 ทั้งหมดไม่เก็บข้อมูลส่วนบุคคลของลูกค้าเลย** (guest ordering ไม่มีชื่อ/เบอร์โทร/device tracking) จึงไม่มีช่องว่างที่ต้องแก้ใน Phase 0 — เพิ่ม Business Rule ข้อ 14 ยืนยัน guardrail นี้เป็นลายลักษณ์อักษร
- จุดเดียวที่เก็บข้อมูลส่วนบุคคล (เบอร์โทรสำหรับ loyalty stamp card, US-11 ใน Phase 1) มีช่องว่างจริง 3 เรื่อง: **(1)** consent ที่มีอยู่เป็นแค่ checkbox ไม่ครบองค์ประกอบ PDPA (เฉพาะเจาะจง/ได้รับข้อมูลครบ/เพิกถอนได้/อิสระ) **(2)** ไม่มีช่องทางให้ลูกค้าขอเข้าถึง/แก้ไข/ลบ/เพิกถอนข้อมูลของตัวเอง **(3)** ไม่มีการกำหนดระยะเวลาเก็บข้อมูล (retention)
- เพิ่ม Business Rule ข้อ 15-21 (consent quality, สิทธิเจ้าของข้อมูล, retention-NEED-INPUT, access control ภายใน, รายงานต้อง aggregate เท่านั้น, กระบวนการแจ้งเหตุข้อมูลรั่วไหล, ข้อมูลบัญชีพนักงานเก็บเท่าที่จำเป็น) และ user story ใหม่ 3 ข้อ (หมวด 2.6): **US-32** (privacy notice ตอนสมัคร loyalty), **US-33** (ช่องทางลูกค้าขอใช้สิทธิ์), **US-34** (แอดมินดำเนินการลบ/แก้ไขข้อมูลจริง) — ทั้งหมดผูกกับ US-11 ต้อง ship พร้อมกัน
- เพิ่มโน้ตล่วงหน้าใน US-21 (ใบเสร็จดิจิทัล) และ US-12 (จ่ายเงินออนไลน์) เตือนว่าถ้าสร้างจริงในอนาคตจะเป็นจุดเก็บข้อมูลใหม่ที่ต้องพิจารณา PDPA แยกต่างหาก — ยังไม่ใช่ช่องว่างตอนนี้เพราะยังไม่ได้สร้าง
- **NEED-INPUT ใหม่:** ระยะเวลาเก็บข้อมูล loyalty หลังลูกค้าเลิกใช้งาน — Touch ต้องกำหนดก่อน US-11 launch จริง (Business Rule ข้อ 17)
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]] เพิ่ม US-32/33/34 เข้า Phase 1 คู่กับ US-11 และ [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] เพิ่มโน้ตให้ track งานนี้ตอนแตก Phase 1 เป็น task breakdown ในอนาคต (ไม่กระทบ task ของ Phase 0)
- ย้ำชัดเจน: นี่คือ**การวิเคราะห์ช่องว่างระดับวิศวกรรม ไม่ใช่คำแนะนำทางกฎหมาย** — Touch ควรให้ที่ปรึกษากฎหมายด้าน PDPA ยืนยันก่อนเปิดใช้งาน loyalty program จริง

## 2026-08-02 — รวม actor "ครัว/บาร์" กับ "แคชเชียร์" เป็นบทบาทเดียว (station model แบบ configurable)

- Touch แก้ actor-model assumption ที่ฝังอยู่ใน v1 ตั้งแต่ต้น — ร้านนี้เครื่องชงกาแฟ/จุดเตรียมของอยู่ติดเคาน์เตอร์จริง คนเดียวกันรับเงินและทำเครื่องดื่มเอง ไม่ต้องมีบทบาท/หน้าจอ "พนักงานครัว/บาร์" แยกจาก "พนักงานแคชเชียร์" สำหรับ MVP ของร้านนี้ — real-world flow คือ: ลูกค้าสั่ง → แคชเชียร์รับเงิน → ตั๋ว/สลิปออก → คนเดิมทำเครื่องดื่มเอง → จบ
- อัปเดต [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]]: รวม 2 actor เดิมเป็น "พนักงานแคชเชียร์/หน้าร้าน" ในตารางที่ 1 (พร้อมโน้ตว่าห้าม hardcode ว่ามีบทบาทรวมนี้ตลอดไป), ปรับ actor + AC ของ US-13 ถึง US-17 ให้สะท้อนความจริงนี้โดย**ไม่ตัดความสามารถเดิมทิ้งสักข้อ** (เห็นออเดอร์ใหม่, อัปเดตสถานะ, แจ้งเตือน, มาร์กของหมด, ดูประวัติกะ ยังจำเป็นเหมือนเดิม เพียงแสดงบนจอเดียวกับที่รับเงิน), เพิ่ม Business Rule ข้อ 13 (station model แบบ configurable — default คือสถานีรวมเดียว ไม่ hardcode), เพิ่ม US-31 (แอดมินตั้งค่าสถานีในอนาคต, P2/Phase 2)
- ปรับ US-28/US-29/US-30 (ช่องทางเคาน์เตอร์) เล็กน้อยให้ตรงกับความจริงที่ว่าคนที่รับเงินกับคนที่ทำเครื่องดื่มเป็นคนเดียวกัน — ยืนยันว่า flow เดิมที่วางไว้ (โดยเฉพาะ US-30 ที่ออกแบบไว้เป็น 1 ขั้นตอนรวดเดียวอยู่แล้ว) เข้ากันได้ดีกับข้อมูลใหม่นี้ ไม่ขัดแย้งกัน
- อัปเดต [[../01-requirements/02-plan/release-roadmap-v1|02-plan/release-roadmap-v1]]: เปลี่ยน Actor column ของ US-13-17 เป็น "แคชเชียร์/หน้าร้าน" เพิ่ม US-31 เข้า Phase 2 และระบุชัดว่านี่คือข่าวดีสำหรับความเร็วของ Phase 0
- อัปเดต [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]]: **รวมกลุ่มงาน D (เดิมคือครัว/บาร์) กับกลุ่มงาน E (เดิมคือแคชเชียร์) เป็นกลุ่มงาน D เดียว** — ลดจำนวนหน้าจอที่ COULSON ต้องออกแบบและ BANNER ต้องพัฒนาแยกกันสำหรับ Phase 0 ลงจริง (ไม่ใช่แค่เปลี่ยนชื่อ) เลื่อนกลุ่มงานเดิม F→E (แอดมิน), G→F (เคาน์เตอร์/takeaway) เพื่อให้ตัวอักษรเรียงต่อเนื่อง
- นี่คือการแก้ไขเชิงโครงสร้างที่ใหญ่กว่ารอบก่อนหน้า (กระทบ actor model ไม่ใช่แค่ business rule เดียว) แต่ผลลัพธ์สุทธิคือ **Phase 0 เบาลง** ไม่มี blocker ใหม่เกิดขึ้น
