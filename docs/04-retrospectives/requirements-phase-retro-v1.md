## หมายเหตุก่อนเริ่ม — ทำไมไม่มีหลักฐานจาก 03-testing/02-test-result

[[../03-testing/02-test-result/index|03-testing/02-test-result]] ยังเป็น scaffolding ว่างเปล่า **ตามที่ควรจะเป็น** ณ จุดนี้ของโปรเจกต์ — ยังไม่มีโค้ดแอปพลิเคชันใด ๆ ถูกสร้างขึ้นเลย (ดู `CLAUDE.md` หัวข้อ "สถานะโปรเจกต์": โปรเจกต์นี้เป็น Obsidian vault สำหรับเอกสาร ยังไม่มี code) โปรเจกต์ยังอยู่ที่สเตจ [[../01-requirements/index|01-requirements]] เท่านั้น ยังไปไม่ถึง [[../02-design/index|02-design]] หรือ [[../03-testing/index|03-testing]] จึงไม่มีผล pass/fail หรือบั๊กใดให้อ้างอิงจริง — **นี่ไม่ใช่ช่องโหว่ที่ต้องกลบเกลื่อน แต่เป็นสถานะที่ถูกต้องตามลำดับ pipeline ของ vault นี้**

Retrospective ฉบับนี้จึงอ้างอิงหลักฐานจาก [[../05-log/changelog|05-log/changelog]] แทน ซึ่งเป็นบันทึกเหตุการณ์จริง (ไม่ใช่ผลทดสอบ แต่เป็น decision log) ของสิ่งที่เกิดขึ้นในเฟสนี้

## สิ่งที่ทำได้ดี (What went well)

1. **MVP แบบบางที่สุดถูกกำหนดไว้ตั้งแต่รอบแรก และไม่ต้องแก้ไขทิศทางหลักเลยตลอด 3 รอบ** — [[../05-log/changelog|changelog]] entry แรก ("เริ่มต้น product backlog...") วาง flow หลัก "สแกน QR → เมนู → สั่ง → แจ้งครัว → ปิดบิล" เป็น Phase 0 ตั้งแต่ต้น และ flow นี้ยังคงเป็นแกนหลักไม่เปลี่ยนแม้จะมี feedback อีก 2 รอบตามมา — feedback ที่ได้ภายหลังเป็นการ "เติมรายละเอียด/แตกช่องทางเพิ่ม" (QR static, สถานะโต๊ะ, ช่องทางเคาน์เตอร์) ไม่ใช่การ "ทุบ flow เดิมทิ้งแล้วเริ่มใหม่" สะท้อนว่าการวาง MVP หลักตั้งแต่รอบแรกถูกทิศทางแล้ว

2. **การจดค่า default พร้อม NEED-INPUT ไว้ชัดเจน ทำให้ COULSON ไม่ต้องรอ Touch ตอบครบทุกข้อก่อนเริ่มงานได้จริง** — [[../01-requirements/03-task/mvp-task-breakdown-v1|03-task/mvp-task-breakdown-v1]] ระบุตั้งแต่แรกว่า Phase 0 "พร้อมส่งต่อ COULSON เริ่ม 02-design ได้ทันที" แม้จะมี NEED-INPUT ค้างอยู่ 3 ข้อ เพราะทุกข้อมี default ที่สอดคล้องกับโจทย์ตั้งต้นรองรับไว้แล้ว การไม่บล็อกงานทั้งหมดไว้รอคำตอบทุกข้อ (all-or-nothing) เป็นการตัดสินใจที่ถูกต้อง — เมื่อ Touch ทยอยยืนยันจริงในรอบ 2 และ 3 งานออกแบบของ COULSON (ถ้าเริ่มไปแล้ว) จะไม่ต้องหยุดรอ มีแค่รายละเอียดที่ต้องปรับตามทีหลัง

3. **แก้ไขเอกสารเดิม (in-place) แทนการสร้างเวอร์ชันใหม่ทุกรอบ ทำให้ไม่มีเอกสารซ้ำซ้อน/สับสนว่าฉบับไหนคือฉบับจริง** — ทั้ง 2 รอบ feedback ถูกแก้ลงใน `product-backlog-v1.md`, `release-roadmap-v1.md`, `mvp-task-breakdown-v1.md` ฉบับเดิมโดยตรง พร้อม changelog note กำกับแต่ละรอบไว้ในตัวเอกสารเอง — ไม่มีไฟล์ `-v2.md` ลอยอยู่คู่กัน ตรงตามธรรมเนียมของ vault (`ห้ามลบเอกสารทิ้ง... ให้ย้ายเวอร์ชันเก่ามาเก็บที่ 00-archived`) และไม่จำเป็นต้อง archive อะไรเลยเพราะไม่มีการพลิกทิศทางจริง มีแต่การชี้ชัด/ต่อยอด

4. **การตัดสินใจแยก user story ใหม่ (US-28/US-29) แทนการยัด channel-branch เข้าไปใน AC ของ US-01/US-04/US-19** — เมื่อเจอ requirement ใหม่ (ช่องทางเคาน์เตอร์/takeaway มีกฎจ่ายเงินต่างจาก dine-in) มีทางเลือกคือแก้ AC เดิมให้มีเงื่อนไข if-channel ซ้อนกันหลายจุด กับแยกเป็น story ใหม่ที่ตัดข้าม actor — เลือกแบบหลังเพราะ flow ของ takeaway ต่างจาก dine-in มากพอ (มีสถานะ "รอชำระเงิน" คั่นกลาง) การยัดเข้า AC เดิมจะทำให้ทุก story อ่านยากขึ้นโดยไม่จำเป็น — เห็นผลจริงตอนเขียน [[../01-requirements/01-spec/product-backlog-v1|01-spec/product-backlog-v1]] หมวด 2.5 ที่แยกออกมาต่างหากอย่างชัดเจน

## สิ่งที่ควรปรับปรุง (What to improve)

1. **Backlog ต้องแก้ถึง 2 รอบหลังสร้างเสร็จ เพราะรอบแรกไม่ได้ถามคำถามเชิงปฏิบัติการที่ควรถามตั้งแต่ต้น** — ดู [[../05-log/changelog|changelog]] ทั้ง 2 entry: entry แรกมีคำว่า "เดิมเป็นเพียง assumption/implicit ใน v1" (สำหรับ QR static และสถานะโต๊ะ) และ entry ที่สองระบุว่า "Touch ให้ feedback เชิงปฏิบัติการ 4 ข้อ คลี่คลายประเด็นเปิดที่เหลือ" — ทั้งสองรอบไม่ใช่ requirement ใหม่ที่เพิ่งเกิดขึ้น แต่เป็นรายละเอียดเชิงปฏิบัติการของร้านกาแฟจริงที่ **มีอยู่แล้วตั้งแต่ต้น** เพียงแต่รอบแรกไม่ได้ถูกถามออกมาตรง ๆ โดยเฉพาะเรื่องช่องทางเคาน์เตอร์/takeaway ซึ่งเป็นคำถามระดับโมเดลธุรกิจ ("ร้านนี้ขายแค่นั่งทานหรือมีซื้อกลับด้วย") ที่ควรถูกถามเป็นคำถามแรก ๆ ไม่ใช่คำถามที่โผล่มาในรอบ 3
2. **รอบแรกอนุมาน (assume) หลายเรื่องแทนที่จะตั้งเป็นคำถามเปิดชัดเจนตั้งแต่ต้น** — เช่น QR แบบ static/regenerate และสถานะโต๊ะแบบ manual-หรือ-auto ถูกเขียนเป็น "Notes/Assumptions" ในรอบแรกแทนที่จะยกเป็น NEED-INPUT อย่างเป็นทางการแบบเดียวกับเรื่องจ่ายเงิน/แชร์ตะกร้า — ทำให้ Touch ต้องมาแก้ทีหลังในรูปแบบ "แก้ assumption ที่ซ่อนอยู่" แทนที่จะเป็น "ตอบคำถามที่ตั้งไว้ชัดเจน" ซึ่งช้ากว่าและเสี่ยงตกหล่นกว่า
3. **การแก้แต่ละรอบต้องแตะ 3-4 ไฟล์พร้อมกันทุกครั้ง (spec, plan, task, log)** — เป็นต้นทุนที่ต้องยอมรับจากการเลือก "ตอบสนอง feedback ทันทีแบบ incremental" (ข้อดีข้อ 2 ด้านบน) แต่ก็หมายความว่าทุกครั้งที่ Touch ยืนยันอะไรใหม่ ต้องไล่ sync เอกสารทั้ง pipeline ไม่ใช่แค่จุดเดียว ถ้าจำนวนรอบ feedback เพิ่มขึ้นเรื่อย ๆ ต้นทุนนี้จะเพิ่มเป็นเส้นตรงตามจำนวนรอบ
4. **ระบบเลข ID (US-01...US-27 เรียงตาม actor) ไม่มีที่ว่างเผื่อไว้สำหรับ story ข้ามหมวดที่โผล่มาทีหลัง** — ตอนเพิ่ม US-28/US-29 (ช่องทางเคาน์เตอร์ ตัดข้าม 2 actor) ต้องสร้างหมวด "2.5" แยกขึ้นมาเพื่อไม่ให้ต้องเรียงเลขใหม่ทั้งเอกสาร ใช้งานได้แต่เป็น workaround ไม่ใช่โครงสร้างที่ออกแบบไว้ตั้งแต่ต้น

## Action items สำหรับรอบถัดไป (Phase 1 backlog หรือ feature ใหม่ใด ๆ)

- [ ] **ก่อนร่าง backlog รอบแรกของ feature/phase ใหม่ ให้ถาม Touch ด้วย "operational reality checklist" สั้น ๆ ก่อนเขียน user story ข้อแรก** ครอบคลุมอย่างน้อย: (ก) มีกี่ช่องทางที่ลูกค้าเข้าถึงฟีเจอร์นี้ (เช่น โต๊ะ vs เคาน์เตอร์ vs อื่น ๆ) (ข) มีใครมากกว่า 1 คน/1 อุปกรณ์ใช้งานพร้อมกันในบริบทเดียวกันหรือไม่ (concurrency) (ค) มีของที่ต้อง "พิมพ์ครั้งเดียวใช้ตลอด" หรือ hardware/สิ่งพิมพ์ที่เปลี่ยนบ่อยไม่ได้หรือไม่ (เช่น QR) (ง) มีแผน loyalty/โปรโมชั่นที่คิดไว้แล้วแม้จะยังไม่ทำตอนนี้หรือไม่ — เป้าหมายคือดักคำถามแบบที่ใช้เวลาถึง 2 รอบในครั้งนี้ให้จบได้ภายในรอบเดียว
- [ ] **เปลี่ยนจาก "เขียนเป็น assumption เงียบ ๆ ใน Notes" เป็น "ยกเป็น NEED-INPUT อย่างเป็นทางการ" ทุกครั้งที่ default ที่เลือกใช้เป็นการตัดสินใจเชิงธุรกิจ ไม่ใช่แค่รายละเอียด UI** — ใช้เกณฑ์เดียวกับที่ backlog นี้ใช้กับเรื่องจ่ายเงิน/แชร์ตะกร้าตั้งแต่ต้น แล้วนำไปใช้กับเรื่อง QR/สถานะโต๊ะด้วย เพื่อให้ Touch เห็นรายการที่ต้องยืนยันครบในที่เดียว (หัวข้อ NEED-INPUT) แทนที่จะต้องไปเจอ assumption ที่ซ่อนอยู่ใน Notes ของแต่ละ story
- [ ] **ใช้ระบบ ID ที่กันที่ไว้ล่วงหน้าสำหรับ story ข้ามหมวด/actor** เช่น เผื่อช่วงเลขว่างต่อหมวด (ลูกค้า 01-19, ครัว 20-29, แคชเชียร์ 30-39, แอดมิน 40-49, cross-actor 90+) แทนการเรียงเลขต่อเนื่องแบบเดิม เพื่อไม่ต้องสร้างหมวดพิเศษแบบ "2.5" เมื่อ feature ใหม่ตัดข้าม actor — ใช้กับ backlog รอบถัดไปเป็นต้นไป (ไม่ยุ่งกับเลขเดิมของ v1 ที่ใช้ไปแล้ว)
- [ ] **เมื่อ NEED-INPUT ข้อไหนถูก resolve ในอนาคต ให้จดไว้ในตัว NEED-INPUT entry เองว่า "ถ้าเปลี่ยน ต้องแก้ไฟล์ไหนบ้าง"** (spec/plan/task) ตั้งแต่ตอนเขียน default ครั้งแรก เพื่อลดเวลาที่ต้องไล่หาว่าการยืนยันหนึ่งข้อกระทบเอกสารกี่ไฟล์ — จะช่วยให้รอบ sync เอกสารเร็วขึ้นเมื่อเกิดรอบ feedback ถัดไป
- [ ] **ก่อนส่งต่อ COULSON เริ่ม 02-design ของ Phase ถัดไป ให้ยืนยันกับ Touch ว่า "รอบ operational reality checklist" (ข้อแรกด้านบน) ทำครบแล้วจริง** ไม่ใช่แค่เขียน user story ตามโจทย์ผิวเผิน — ใช้เป็นเกณฑ์ก่อนติด flag "พร้อม handoff" ในเอกสาร task breakdown ทุกครั้งต่อไปนี้
