## 1. ไฟล์ — **เก็บนอก repo**

ไฟล์โปรโตไทป์ **ไม่ได้ commit เข้า repo** เพราะรวมกัน 5 MB (HTML ฝังรูป base64 ไว้ในตัว) ซึ่งหนักเกินไปสำหรับ vault ที่เป็นเอกสารล้วน

**ที่อยู่จริงของไฟล์:** `Classwork/picture coffee/`

| ไฟล์ | ขนาด | ผู้ใช้ | เปิดอย่างไร |
|---|---|---|---|
| `Thyna Order (mobile).html` | 0.6 MB | **ลูกค้า** (มือถือ) | ดับเบิลคลิกเปิดในเบราว์เซอร์ · ดูที่ความกว้าง ~375px |
| `Thyna Cafe POS.html` | 4.4 MB | **พนักงาน/แคชเชียร์** (POS แท็บเล็ต) | ดับเบิลคลิกเปิด · **PIN สาธิต `1234`** · ดูที่ความกว้าง ≥1024px |

**ทั้งสองไฟล์ self-contained** — ไม่เรียก CDN, ฟอนต์ หรือรูปจากภายนอกเลย เปิดแบบออฟไลน์ได้ รูปทั้งหมดฝังเป็น base64 (ตัวมือถือ 30 รูป)

> ⚠️ ถ้าเปิดด้วย `file://` แล้วบางอย่างไม่ทำงาน ให้เสิร์ฟผ่าน http แทน: `python3 -m http.server` ในโฟลเดอร์ที่เก็บไฟล์ แล้วเปิด `http://127.0.0.1:8000/`

## 4. 🔴 จุดที่โปรโตไทป์ขัดกับ requirement — ต้องตัดสินก่อนสร้างจริง

> เขียนไว้เพราะ **โปรโตไทป์คือการตัดสินใจ ไม่ใช่แค่ภาพ** — ถ้าปล่อยไว้ คนสร้างจะสร้างตามภาพ แล้ว test case จะ fail ทั้งที่ระบบทำตามที่เห็น

### ข้อ 1 — ✅ **ปิดแล้ว 2026-08-16 — Touch ตัดสินให้เก็บชื่อเล่นไว้**

**คำตัดสิน:** ใช้โมเดลแบบร้านกาแฟทั่วไป — พนักงานเรียก *"คุณทัช คิว A317"* **ใช้ทั้งชื่อเรียกและเลขคิว ไม่ใช่อย่างใดอย่างหนึ่ง** · ชื่อถูกเก็บส่งไปกับออเดอร์ และล้างเป็น `NULL` ใน 90 วัน

> ⚠️ **แก้การตีความ 2026-08-16** — หัวข้อนี้เคยเขียนว่าเป็นเรื่อง PDPA ที่หนักและต้องรื้อ gap analysis ทั้งชุด · **หนักเกินจริง** · ช่องนี้เป็น **ชื่อสำหรับเรียก ไม่ใช่ชื่อจริง** — ลูกค้าพิมพ์อะไรก็ได้ ระบบไม่ตรวจสอบ ไม่บังคับกรอก ไม่ผูกข้ามออเดอร์ ไม่มีเบอร์/อีเมล/บัญชีให้เชื่อมกับตัวตนจริง และล้างทิ้งใน 90 วัน · **Phase 0 ไม่มีการล็อกอินเลย** ส่วนเส้นทางที่เก็บข้อมูลจริง (loyalty US-11) เป็น Phase 1 ซึ่งมีกลไก consent ออกแบบรออยู่แล้ว (BR ข้อ 15 + US-32/33/34) · เหตุผลเต็มอยู่ที่ [[../../01-requirements/01-spec/acceptance-criteria-v1|Acceptance Criteria v1]] §6.1

**แปลว่าโปรโตไทป์ถูก และ requirement เดิมผิด** — จึงแก้ requirement ตามโปรโตไทป์ ไม่ใช่แก้โปรโตไทป์:

| แก้แล้ว | เป็นอะไร |
|---|---|
| [[../../01-requirements/01-spec/nfr-v1\|NFR-17]] | เก็บได้ชนิดเดียวคือชื่อเล่นผูกกับออเดอร์ |
| [[../../01-requirements/01-spec/product-backlog-v1\|BR ข้อ 14]] | เดียวกัน + ห้ามผูกข้ามออเดอร์เป็นโปรไฟล์ · ห้ามบังคับกรอก · เลขคิวยังเป็นตัวอ้างอิงหลัก |
| **TC-072 · TC-055b** | แก้เกณฑ์ · เพิ่ม **TC-072a** (ไม่กรอกชื่อก็สั่งได้) และ **TC-072b** (ชื่อซ้ำ 2 ออเดอร์ต้องไม่ถูกผูกกัน) |
| [[../../02-design/02-technical/data-model-v1\|Data Model v1]] | มาร์คว่าล้าสมัย รอ COULSON ออกแบบ field ใหม่ |

> ✅ **R-1 ปิดแล้ว 2026-08-16 — Touch ตัดสิน: ล้างชื่อเล่นเป็น `NULL` ทุก 90 วัน** นับจากวันที่สร้างออเดอร์ · **ล้างเฉพาะช่องชื่อ ห้ามลบแถวออเดอร์** เพราะออเดอร์เป็นข้อมูลบัญชี/ภาษี · เป็น **column-level purge** ซึ่งต่างจาก job ล้างข้อมูลที่มีอยู่ทั้งหมดในระบบตอนนี้ (ลบทั้งแถว) — เขียนผิดแบบคือข้อมูลบัญชีหาย · ทดสอบด้วย **TC-072c** · รายละเอียดที่ [[../../01-requirements/01-spec/acceptance-criteria-v1|Acceptance Criteria v1]] หัวข้อ 6.1
>
### 🔶 ช่องชื่อเล่นต้องไม่บังคับ — โปรโตไทป์ยังไม่ตรงกับเจตนา

**เจตนาที่ Touch ยืนยัน 2026-08-16:** *"เริ่มสั่งก็กดได้ ถ้าไม่สะดวกใส่ชื่อก็เป็นคิวอย่างเดียว"* — ตรงกับ BR ข้อ 14 ที่แก้ใหม่แล้ว **ไม่ต้องแก้ requirement เพิ่ม**

**แต่ตัวโปรโตไทป์ยังบังคับกรอกอยู่** — ตรวจเมื่อ 2026-08-16 ด้วยการเปิดหน้าแรกแล้วกดปุ่มทั้งที่ช่องชื่อว่าง:

| ตรวจอะไร | ผลจริง |
|---|---|
| `#go.disabled` ตอนช่องชื่อว่าง | **`true`** |
| กดปุ่ม "เริ่มสั่ง" ตอนช่องว่าง | **ไม่เกิดอะไรขึ้น** หน้าจอไม่เปลี่ยน |
| ปุ่ม/ลิงก์สำหรับข้าม | **ไม่มี** — ทั้งหน้ามีแค่ "เริ่มสั่ง" กับ "EN" |

ต้นเหตุอยู่ที่ตัว render ของหน้าแรก ซึ่งใส่ `disabled` ไว้ตราบใดที่ชื่อยังว่าง และมี `oninput` คอยเปิด-ปิดปุ่มตามความยาวของข้อความ:

```
<input id="nm" … oninput="S.name=this.value; el('go').disabled=!this.value.trim()">
<button id="go" ${S.name.trim() ? '' : 'disabled'} …>
```

**สิ่งที่ต้องแก้:** ถอดเงื่อนไข `disabled` ออกให้ปุ่มกดได้เสมอ · แล้วหน้ายืนยันต้องแสดงผลได้สวยเมื่อไม่มีชื่อ — เหลือ **เลขคิวอย่างเดียว** ไม่ใช่ขึ้นบรรทัดว่างหรือ `· 1 รายการ` ที่ขาดชื่อนำหน้า

**ทดสอบด้วย TC-072a** ซึ่งเขียนไว้ตรงเคสนี้แล้ว — ตอนนี้ถ้ารันจะ **FAIL**
