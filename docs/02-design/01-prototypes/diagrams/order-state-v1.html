DATA MODEL · §4.1 · STATE MACHINE

สถานะออเดอร์

ออเดอร์เข้าระบบได้สองประตู ประตูไหนขึ้นกับช่องทาง — dine-in เข้าคิวทันที ส่วนเคาน์เตอร์ต้องผ่านการชำระเงินก่อนเสมอ ปลายทางมีสองทางและทั้งคู่เป็นทางเดียว ปิดแล้วปิดเลย

TWO DOORS IN

ประตูเข้าต่างกันตามช่องทาง

  • dine-in เข้า queued ทันที — BR 3 ห้ามบล็อกออเดอร์ด้วยการจ่ายเงิน มี CHECK constraint กันไม่ให้โต๊ะมีสถานะ awaiting_payment เลย
  • เคาน์เตอร์ ต้องผ่าน awaiting_payment ก่อน — BR 12 และข้ามได้เมื่อ bill.paid_at IS NOT NULL เท่านั้น (INV-3)
  • พนักงานคีย์แทน (US-30) จ่ายในทรานแซกชันเดียว จึงเข้า queued ได้เลย

ALLOWED SHORTCUTS

ทางลัดที่จงใจอนุญาต

  • queued → ready ข้าม in_progress ได้ — BR 13 สถานีเดียว บังคับกด 2 ครั้งคือเพิ่มงานเปล่า
  • ready → in_progress ถอยได้ 1 ขั้น — มือเปียกกดพลาดเกิดขึ้นจริง บันทึกลง event log
  • ทุกครั้งที่เปลี่ยนสถานะต้องเขียน order_status_event

FIDELITY

ต่างจากต้นฉบับตรงไหน

  • วาดมือ — extractor พังกับ state ที่ตั้งชื่อเป็นภาษาไทย
  • เส้นยกเลิก 4 เส้น ยุบเป็นกล่องย่อ "ทุกสถานะก่อน completed" ตามที่ type reference สั่ง
  • เพิ่ม 2 transition จากตารางใต้แผนภาพที่ mermaid ต้นฉบับไม่มี — ข้าม in_progress และถอยกลับ 1 ขั้น
