### 0.2 theme ให้อะไร และ **ไม่ได้** ให้อะไร

| theme เป็นแหล่งอ้างอิงของสิ่งเหล่านี้ ✅ | theme **ไม่ใช่** แหล่งอ้างอิงของสิ่งเหล่านี้ ❌ |
|---|---|
| ค่าสี (ink / surface ladder / lime accent) | Information architecture และโครงสร้างหน้าจอ |
| บุคลิกและสเกลตัวอักษร | จำนวนหน้าจอ · ลำดับหน้าจอ · การจัดกลุ่มหน้าจอ |
| จังหวะ spacing 8px และ gutter 16px | user flow และจุดตัดสินใจ |
| มุมโค้ง (ไม่มีมุมเหลี่ยม) และชุดเงา 3 ตัว | ชื่อ / ความหมาย / พฤติกรรมของ component |
| ความรู้สึกโดยรวม: near-monochrome, accent เดียว, สะอาด | สถานะของออเดอร์ / โต๊ะ / ช่องทาง |
| ลายเส้นของไอคอน (22px box, stroke 1px, monochrome) | กฎธุรกิจใด ๆ ทั้งสิ้น |

### 0.3 กฎปฏิบัติ 5 ข้อ

1. **requirement ชนะ theme เสมอ ไม่มีข้อยกเว้น** — เมื่อขัดกัน ทำตาม requirement แล้วบันทึกเหตุผลไว้ **ห้ามประนีประนอมกับ theme** และห้ามลดเกณฑ์ของ requirement ลงเพื่อรักษาหน้าตาของ theme
2. **theme เงียบ ≠ ทำไม่ได้** — สิ่งที่ requirement ต้องการแต่ theme ไม่ได้วาดตัวอย่างไว้ ให้ **ออกแบบขึ้นจาก requirement โดยใช้ token ของ theme** ถือเป็นงานปกติ ไม่ใช่ข้อจำกัดและไม่ใช่ปัญหาที่ต้องขออนุญาต
3. **ห้ามยืมชื่อ component มาทั้งดุ้น** — component ในระบบเราตั้งชื่อตามภาษาของ requirement เสมอ (`ChannelBanner`, `OrderTicketCard`, …) แล้วหมายเหตุว่ารูปลักษณ์ยืมมาจาก component ตัวไหนของ theme — ดู §5
4. **สิ่งที่ theme มีแต่เราไม่ต้องการ ให้ทิ้ง** โดยไม่ต้องหาที่ให้มันอยู่ (delivery, voucher, promo) — การมีอยู่ใน theme ไม่ได้ทำให้มันเป็น requirement
5. **ทุกครั้งที่ requirement เอาชนะ theme ต้องบันทึกเป็นบรรทัดเดียวว่าอ้าง requirement ข้อไหน** เพื่อให้ตรวจย้อนได้ว่าไม่ได้ตัดสินตามรสนิยม

## 0.4 เอกสารนี้ทำหน้าที่อะไร

เอกสารนี้คือ **สัญญาการรับรูปลักษณ์ของ theme มาใช้กับระบบที่ requirement เป็นผู้กำหนด** — บอกว่า token ตัวไหนรับมาใช้ตรง ๆ ได้ ตัวไหนต้อง override เพราะ requirement บังคับ, component ของระบบเราแต่ละตัวยืมรูปลักษณ์มาจากไหน และอะไรที่ต้องออกแบบขึ้นเองจาก requirement

**การใช้สิทธิ์ requirement-over-theme ในเอกสารนี้เกิดขึ้น 3 ที่ ทั้งหมดอ้าง Business Rule ข้อ 23:** §3.1 (สีที่ contrast ไม่ผ่าน), §3.2–3.3 (ขนาดตัวอักษร/พื้นที่กด/focus), §3.4 (การแยกการ์ดในสภาพแสงจ้า)

### 0.6.1 กรอบขนาดมือถือเมื่อเปิดบนจอกว้าง

แอปฝั่งลูกค้า (Surface A ทั้ง 7 หน้าจอ) ถูกออกแบบบนเครื่องอ้างอิง 375–430px มาตั้งแต่ต้น แต่ไม่เคยมี
อะไรจำกัดความกว้างไว้เมื่อเปิดบนจอกว้างกว่านั้น — เนื้อหาจึงยืดเต็มความกว้างจอคอม และรูปสินค้าในหน้า
รายละเอียดสูงเกินสองหน้าจอ ตอนนี้แก้แล้ว:

- จำกัดความกว้างของแอปไว้ที่ token ใหม่ `--app-frame-w: 430px` จัดกึ่งกลางจอด้วย `margin-inline: auto`
- `@media (min-width: 431px)` เท่านั้นที่แต่งพื้นหลังนอกกรอบ (`--divider`) และเส้นขอบ (`--border-a11y`,
  `--stroke-hairline`) ให้ดูเป็นกรอบที่ตั้งใจ — **ต่ำกว่า 431px (มือถือจริง) ไม่มีอะไรเปลี่ยนแม้พิกเซล
  เดียว** เพราะ `max-width` ไม่ผูกอยู่แล้วเมื่อจอแคบกว่ากรอบ
- แถบล่าง (`BottomBar`) ยึดอยู่ในกรอบเดียวกัน ไม่ใช่เต็มความกว้างจอ (`left: 50%; transform:
  translateX(-50%); max-width: var(--app-frame-w)`) แทนที่ `insetInline: 0` เดิม
- เพิ่มเพดานความสูงรูปสินค้าใน C-02 (`max-height: min(38dvh, 300px)`) — เดิมเป็นสี่เหลี่ยมจัตุรัสเต็ม
  ความกว้างซึ่งบนจอสูงจะกินพื้นที่จนปุ่ม "เพิ่มลงตะกร้า" ตกไปนอกหน้าจอแรก

**🔴 ยังไม่ได้ตัดสิน — อย่าอ่านว่าเป็นค่าสุดท้าย:** ค่า 430px (ความกว้างกรอบ) และ 431px (breakpoint)
เป็นค่าที่ผู้พัฒนาเลือกเอง (อ้างอิงความกว้าง iPhone Pro Max รุ่นปัจจุบันว่าเป็นจอที่กว้างที่สุดที่ยังนับว่า
"มือถือ") **Touch ยังไม่ได้เคาะ** — ถ้าต้องการ 390px หรือ 420px แก้ที่ตัวแปร `--app-frame-w` ตัวเดียว
(breakpoint ผูกกับตัวแปรเดียวกันโดยธรรมชาติ ต้องปรับคู่กัน) · และ**ยังไม่ได้ยืนยันหน้าตาบนจอที่แคบกว่า
กรอบด้วยตาจริงบนมือถือจริงอีกรอบ** — ตรวจผ่านแค่ตรรกะ CSS (media query ไม่มีผลต่ำกว่า 431px) เท่านั้น

- ปิดได้ 3 ทาง: กด Escape · กดพื้นหลัง (scrim) · ปุ่มปิด — ไม่มีทางใดพึ่ง gesture อย่างเดียว ตรงกับ
  กฎเดิมของ `SwipeHandle` ใน §5.2
- ปิดแล้วคืนโฟกัสไปที่การ์ดสินค้าใบเดิมที่เป็นคนเปิด (เก็บ trigger element ไว้ใน ref)
- เคารพ `prefers-reduced-motion: reduce` (ปิด animation เลื่อนขึ้น) เหมือนกฎรวมที่ §3.3 วางไว้แล้ว

**ต้นแบบคือ `OptionSheet` ของจอสถานี (Surface B, `station-app.tsx`) แต่ตั้งใจเขียนแยกกัน** — จอสถานี

component กลางที่ครอบทั้งสองจะมี prop สลับพฤติกรรมจนอ่านยากกว่าเขียนสองที่ — ตรวจแล้วว่าใช้ร่วมกัน

### 0.6.3 การเปลี่ยนแนวทาง — ไฟล์ CSS module ตัวแรกของโปรเจกต์

**นี่คือการเปลี่ยนแนวทางของ design system ไม่ใช่แค่รายละเอียดของฟีเจอร์นี้ฟีเจอร์เดียว** — ทุกหน้าจอ
ของระบบนี้ (ทั้ง 24 หน้าจอ Surface A/B/C) เขียนด้วย inline style ล้วนมาตั้งแต่ 2026-08-22 ไม่มีไฟล์
`*.module.css` เลยสักไฟล์เดียว จนกระทั่ง `customer-app.module.css` (ของ `customer-app.tsx` เท่านั้น
ไม่มีหน้าแอดมิน/จอสถานีเรียกใช้)

**เหตุผลที่ต้องแยกไฟล์ ไม่ใช่แก้ที่ inline style เดิม:** กรอบขนาดมือถือ (§0.6.1) ต้องมีผลเฉพาะผ่าน
`@media` query และแผ่นเลื่อนขึ้น (§0.6.2) ต้องมี `@keyframes` และเคารพ `@media (prefers-reduced-
motion: reduce)` — ทั้งสามอย่างเป็น **at-rule ซึ่ง inline style ของ React เขียนไม่ได้เลย** เหตุผล
เดียวกับที่ `.order-2col` / `.menu-form-2col` ใน `tokens.css` ต้องเป็น class ประกาศไว้ล่วงหน้าอยู่แล้ว
ไม่ใช่ `style={{}}` ตรง ๆ

**กฎที่ประกาศเพิ่มจากนี้ (บันทึกไว้ให้ SHURI/COULSON คนถัดไปเดินตาม):**
1. **ค่าเริ่มต้นของทั้งระบบยังเป็น inline style ตามเดิม** — ไม่ใช่การย้ายทั้งระบบไปใช้ CSS module
2. **แยกเป็น `*.module.css` เฉพาะตอนที่ inline style ทำไม่ได้จริง ๆ** (at-rule: media query,
   keyframes, `:hover`/`:focus-visible` ที่ซับซ้อนเกินจะ handle ด้วย state, `prefers-reduced-motion`)
   — ไม่ใช่เพราะสะดวกกว่าหรือจัดระเบียบง่ายกว่า
3. **ไฟล์ module ผูกกับ component เดียวเท่านั้น** (`customer-app.module.css` ↔ `customer-app.tsx`
   เท่านั้น) ไม่ทำเป็น shared stylesheet ข้าม component เพราะจะเสียจุดแข็งของ inline style เดิม
   (เห็นสไตล์ตรงจุดที่ใช้ ไม่ต้องเปิดสองไฟล์เทียบกัน)
4. **กฎ "ห้ามฮาร์ดโค้ดสี" เดิมยังบังคับเต็มที่แม้อยู่ใน CSS module** — ทุกค่าสีต้องมาจาก token ใน
   `tokens.css` เท่านั้น (`tests/unit/design-tokens.test.ts` คุมว่าทุก custom property ที่อ้างถึงต้อง
   มีจริง ครอบคลุมไฟล์ module ด้วย ไม่ใช่แค่ inline style)

ยังไม่พบเหตุผลให้ต้องแยกไฟล์ module ตัวที่สอง ณ ตอนนี้ — ถ้าจอสถานี/แอดมินต้องการ at-rule แบบเดียวกัน
ในอนาคต ให้สร้างไฟล์ module แยกต่อ component ตามกฎข้อ 3 ข้างบน ไม่ใช่รวมเข้ากับไฟล์นี้

### 3.2 ตัวอักษร — เปลี่ยนว่า "ขั้นไหนใช้ตรงไหน" ไม่ใช่เปลี่ยนสเกล

theme บอกไว้เองว่า **"14px/16px does most of the work"** และมี `--fs-caption:12px` — ทั้งสองอย่างขัดกับ Business Rule ข้อ 23 (เนื้อหาปกติ ≥16px)

| เดิม | ปัญหา | Override |
|---|---|---|
| `--fs-ui:14px` เป็นตัวหลักของ button/ชื่อสินค้า/label/chip | ชื่อสินค้าและ label ของตัวเลือกคือ**เนื้อหา** ไม่ใช่ metadata | **ชื่อสินค้า, label ของ option group, ข้อความบนปุ่ม, ข้อความสถานะ ใช้ `--fs-body:16px` เป็นขั้นต่ำ** · 14px เหลือใช้เฉพาะ metadata ที่ไม่จำเป็นต่อการตัดสินใจ (เช่น "อัปเดตเมื่อ 14:02") |
| `--fs-caption:12px` | ต่ำกว่าเกณฑ์ | **ห้ามใช้ 12px ในหน้าจอลูกค้าเลย** — ยกขั้นต่ำเป็น 14px และถ้าข้อความนั้นมีความหมายต่อการตัดสินใจให้ใช้ 16px |
| จอสถานีพนักงาน | 14px อ่านไม่ออกที่ระยะ 50–80 ซม. (UX §4) | **จอสถานีใช้ 18px (`--fs-lead`) เป็น base** · เลขโต๊ะ/เลขออเดอร์ใช้ 26–32px (`--fs-title`/`--fs-display`) |
| Line-height | `--lh-ui:16px` บน 14px = **1.14** → **ตัดวรรณยุกต์ไทยแน่นอน** | ดู §3.5 |
| Tracking `-0.03em` / `-0.01em` | ทำลายระยะกลุ่มพยัญชนะไทยและทำให้สระ/วรรณยุกต์ชนกัน | **บังคับ `letter-spacing: normal` สำหรับข้อความภาษาไทยทั้งหมด** — tracking ติดลบใช้ได้เฉพาะข้อความละตินล้วน |

### 3.3 พื้นที่กด และ focus

| เดิม | ปัญหา | Override |
|---|---|---|
| `--tap-40: 40px` | ต่ำกว่าเกณฑ์ 44×44px ของ Business Rule ข้อ 23 | **เพิ่ม `--tap-44: 44px` เป็นขั้นต่ำของทุก control ฝั่งลูกค้า** และ **เลิกใช้ `--tap-40` ในทุกหน้าจอ** (ปล่อยไว้ใน token ได้แต่ห้ามอ้างอิง) |
| `--tap-48: 48px` | ✅ มีอยู่แล้ว | **บังคับใช้กับทุกปุ่มบนจอสถานีพนักงาน** ตาม UX-09 พร้อมระยะห่างระหว่างปุ่ม ≥ 8px (`--sp-8`) |
| readme: **"No borders appear on focus, no scale on press"** | ใช้คีย์บอร์ดไม่ได้เลย และ P5 คุณแอนใช้แอดมินจากคอมพิวเตอร์ (คีย์บอร์ด+เมาส์) | **เพิ่ม focus ring บังคับ:** `outline: 3px solid var(--focus-ring); outline-offset: 2px` — ink 3px มองเห็นได้ทั้งบน surface-app (13.62:1) และบนปุ่ม lime (12.51:1) จึงใช้ค่าเดียวได้ทั้งระบบ · ใช้ `:focus-visible` เพื่อไม่ให้ขึ้นตอนคลิกเมาส์ (รักษาความสะอาดของ theme ไว้) |
| readme: selection เปลี่ยนแค่ **fill** | สื่อความหมายด้วยสีเดี่ยว — ขัด Business Rule ข้อ 23 | **ทุก selected state ต้องมี glyph กำกับ** — chip ที่ถูกเลือกต้องมี `check` glyph (มีอยู่แล้วใน `assets/icons/check.svg`) ไม่ใช่แค่พื้นเปลี่ยนเป็น ink |
| transition 180ms ease | ✅ รับมาใช้ | เคารพ `prefers-reduced-motion: reduce` — ปิด transition เมื่อผู้ใช้ตั้งค่าไว้ |

### 3.4 ปัญหาที่ยังไม่มีใครชี้ — บันไดพื้นผิว 5 ขั้นพังหมดกลางแดด

UX Requirements §4 บังคับว่าต้องอ่านออกในสภาพแสงจ้า แต่พื้นผิวทั้ง 5 ขั้นของ theme (237 / 240 / 245 / 250 / 255) ห่างกันแค่ **1.03:1 ถึง 1.09:1**

| คู่ | contrast |
|---|---|
| surface-app 240 ↔ card 250 | **1.09:1** |
| surface-app 240 ↔ surface-2 245 | **1.05:1** |
| surface-3 237 ↔ card 250 | **1.12:1** |

theme บอกเองว่า **"separation comes from the 5-step surface ladder alone"** (ไม่มีขอบ ไม่มีเงาบนการ์ด) → **กลางแดดการ์ดจะหายไปทั้งใบ ลูกค้ามองไม่ออกว่าอะไรกดได้**

**Override (เบี่ยงจาก theme อย่างจงใจ บันทึกไว้ตรงนี้):**
- การ์ดที่ **กดได้** ในหน้าจอลูกค้า (ProductCard, การ์ดออเดอร์, ตัวเลือกใน option sheet) ต้องมี **hairline 1px `--border-a11y` (3.15:1)** — ขัดกับ "no borders" ของ theme แต่จำเป็นตาม WCAG 1.4.11 + UX §4
- การ์ดที่เป็น **ข้อมูลอย่างเดียว กดไม่ได้** ยังคงไม่มีขอบตามต้นทาง — ความต่างนี้กลายเป็นภาษาการออกแบบที่มีประโยชน์: **มีขอบ = กดได้**
- ห้ามใช้ surface ladder เป็นตัวสื่อความหมายเชิงสถานะ (เช่น "การ์ดสีจางกว่า = สินค้าหมด") ในทุกกรณี

### 3.5 ฟอนต์ไทย — Urbanist ไม่มีชุดอักษรไทย

**ข้อเท็จจริง:** `tokens/fonts.css` โหลด Urbanist จาก Google Fonts ซึ่งรองรับเฉพาะ **Latin / Latin-ext / Vietnamese** ไม่มี Thai — UI ของเราเป็นภาษาไทยทั้งหมด ถ้าไม่ทำอะไรเลย เบราว์เซอร์จะ fallback ไปฟอนต์ระบบ (Thonburi/Leelawadee/Noto ตามอุปกรณ์) ซึ่งหน้าตาไม่คงที่ข้ามเครื่องและพัง metric

**ตัวเลือกที่พิจารณา 3 ตัว (ทั้งหมดอยู่บน Google Fonts, ฟรี, มีน้ำหนัก 400/500 ครบตามที่ theme ใช้):**

| ฟอนต์ | ลักษณะอักษร | x-height / ความคมบนจอเล็ก | เข้ากับ Urbanist แค่ไหน | ความเหมาะกับ P3 ป้าน้อย |
|---|---|---|---|---|
| **IBM Plex Sans Thai** | ไม่มีหัว (loopless) ช่องเปิดกว้าง | x-height สูง hinting ดีมาก คมที่ 14–16px | **สูง** — เป็น humanist geometric ที่ออกแบบมาคู่กับ Latin ของตระกูลเดียวกัน น้ำหนัก 400/500 ตรงกับที่ theme ใช้พอดี | ดี — ช่องเปิดกว้างทำให้แยกตัวอักษรออกง่าย แต่ยัง loopless |
| **Noto Sans Thai** | ไม่มีหัว | x-height สูง เป็น variable font hinting ดี | ปานกลาง-สูง — เป็นกลางมาก เข้ากับความ neutral ของ theme แต่ไม่มีบุคลิกร่วม | ดี |
| **Sarabun** | **มีหัว (looped)** | x-height ปานกลาง คมพอใช้ | ปานกลาง — บุคลิกต่างจาก Urbanist ชัด | **ดีที่สุด** — หัวคือรูปอักษรไทยดั้งเดิมที่ผู้อ่านสูงวัยจำได้ไวกว่า |

**การตัดสินใจ (พร้อมกฎที่ทดสอบได้ ไม่ใช่รสนิยมลอย ๆ):**

- **เลือก `IBM Plex Sans Thai` เป็นฟอนต์ไทยหลัก** — เหตุผล: x-height สูงและ hinting ดีที่สุดในสามตัวสำหรับขนาด 16px บนจอมือถือเก่า (UX §4 บังคับให้รองรับเบราว์เซอร์/อุปกรณ์ย้อนหลัง 1–2 ปี) น้ำหนัก 400/500 ตรงกับ theme พอดีจึงไม่ต้องเดา mapping และบุคลิก geometric-humanist เข้ากับ Urbanist ได้โดยไม่ต้องดัดหน้าตาของ theme
- **`Noto Sans Thai` เป็น fallback ตัวที่สอง** ใน stack (กันกรณี Google Fonts โหลดไม่ทันหรือถูกบล็อก)
- 🔴 **กฎที่ต้องทดสอบจริง ไม่ใช่ตัดสินจบที่นี่:** ป้าน้อย (P3) คือ validation gate ของทุก flow ตาม UX Principle ข้อ 7 — **ถ้าผลทดสอบ usability กับผู้ใช้ตัวแทน P3 พบว่าอ่านฟอนต์ไม่มีหัวช้ากว่า/ผิดพลาดกว่าอย่างมีนัย ให้สลับทั้งระบบไปใช้ `Sarabun` ทันที** การสลับต้องทำได้ด้วยการแก้ token ตัวเดียว (`--font-thai`) เท่านั้น — **นี่คือข้อกำหนดทางสถาปัตยกรรม ไม่ใช่ข้อเสนอ** ห้าม hardcode ชื่อฟอนต์กระจายในโค้ด (ส่งต่อ OKOYE เป็น test case)

**Font stack ที่ประกาศใช้:**

```css
:root{
  /* ละตินมาก่อนเสมอ เพื่อให้ตัวเลข/ตัวอักษรอังกฤษได้หน้าตาของ Urbanist
     แล้วอักขระไทยจึงตกไปที่ฟอนต์ไทยตัวถัดไปโดยอัตโนมัติ */
  --font-thai: 'IBM Plex Sans Thai','Noto Sans Thai';
  --font-sans: 'Urbanist', var(--font-thai),
               -apple-system, BlinkMacSystemFont,'Segoe UI',Roboto,
               'Helvetica Neue', Arial, sans-serif;
}
```

**การจัดการ metric mismatch ไทย–ละติน (บังคับ):**

1. **บรรทัดสูงขึ้นทั้งระบบ** — ไทยมีชั้นอักขระได้ถึง 4 ชั้น (สระบน + วรรณยุกต์ + พยัญชนะ + สระล่าง) `--lh-ui:16px` บน 14px จะ**ตัดวรรณยุกต์ทิ้ง**:

   | Token | เดิม | ใหม่ (บังคับ) | อัตราส่วน |
   |---|---|---|---|
   | `--lh-body` (16px) | 24px | **24px (คงเดิม)** | 1.50 ✅ |
   | `--lh-ui` (14px) | 16px | **20px** | 1.43 |
   | `--lh-caption` (14px หลัง override) | 16px | **20px** | 1.43 |
   | `--lh-lead` (18px) | 24px | **26px** | 1.44 |
   | `--lh-subtitle` (22px) | 32px | 32px (คงเดิม) | 1.45 ✅ |
   | `--lh-title` (26px) | 40px | 40px (คงเดิม) | 1.54 ✅ |
   | `--lh-display` (32px) | 40px | **44px** | 1.38 |

2. **`letter-spacing: normal` สำหรับข้อความไทยทุกจุด** — ยกเลิก `-0.030em` / `-0.010em` ทั้งหมด (tracking ติดลบเก็บไว้ได้เฉพาะข้อความละตินล้วน เช่น ชื่อเมนูภาษาอังกฤษบน specimen)
3. **ห้ามพึ่ง `font-size-adjust`** — รองรับไม่ทั่วถึงบนเบราว์เซอร์ย้อนหลัง 1–2 ปีตาม UX §4 ให้ยอมรับความต่าง x-height ประมาณ 2–4% ระหว่าง Urbanist กับ IBM Plex Sans Thai แทน และห้ามผสมไทย-ละตินในบรรทัดเดียวด้วยขนาดต่างกัน
4. **ใช้เลขอารบิก (0-9) เท่านั้น** ห้ามใช้เลขไทย (๐-๙) ในทุกหน้าจอ — ตัวเลขทั้งหมดจึงมาจาก Urbanist ทำให้ราคา/ยอดรวมได้หน้าตาของ theme เต็ม ๆ
5. **ไม่ตัดคำเอง** — ตั้ง `word-break: normal; overflow-wrap: break-word` และห้ามใส่ soft hyphen ในข้อความไทย

## 4. รูปแบบราคาเงินบาท

theme แสดงราคาเป็น `$12` (ไม่มีทศนิยม) และมีเฉพาะยอดรวมที่มีสตางค์ (`$40.25`) — ของเราเป็นบาทตาม [[../../01-requirements/01-spec/initial-menu-data-v1|Initial Menu Data v1]] ซึ่ง**ทุกราคาเป็นจำนวนเต็ม (40–140 บาท)**

| บริบท | รูปแบบ | ตัวอย่าง |
|---|---|---|
| ราคาบนการ์ดเมนู (PriceTag) | `฿` ติดเลข ไม่มีทศนิยม | `฿75` |
| ราคาที่มี 2 อุณหภูมิ | แสดงราคาของตัวเลือกที่เลือกอยู่เท่านั้น ไม่โชว์ทั้งคู่บนการ์ด | `฿80` |
| บรรทัดในตะกร้า | ราคาต่อหน่วย × จำนวน แล้วยอดบรรทัด | `฿75 × 2` … `฿150` |
| ยอดรวมตะกร้า / แถบ CheckoutBar | มีคอมมาคั่นหลักพัน | `฿1,250` |
| สรุปบิลของโต๊ะ (US-07/US-18) | รูปแบบเต็มภาษาไทย เพื่อความชัดในจุดที่ P2 ต้นกังวลที่สุด | `ยอดรวม 1,250 บาท` |
| ตั๋วออเดอร์ฝั่งพนักงาน | `฿` แบบสั้น อ่านเร็ว | `฿150` |

**กฎบังคับ:**
- **ห้ามแสดง `.00`** — แสดงทศนิยม 2 ตำแหน่งเฉพาะเมื่อมีค่าเศษจริง (จะเกิดใน Phase 1 ตอนคืนเงิน/ส่วนลด US-22)
- **ห้ามใช้ `THB` / `B` / `บ.`** ในหน้าจอลูกค้า — ใช้ `฿` หรือ `บาท` เท่านั้น
- ตัวเลขราคา/ยอดรวมทุกจุดตั้ง **`font-variant-numeric: tabular-nums`** เพื่อให้ตัวเลขเรียงตรงคอลัมน์ในตะกร้าและใบสรุป (สำคัญกับ UX-12 ที่ต้องอ่านยอดสุทธิได้ใน ≤3 วินาที)
- ยอดสุทธิใน US-07 ต้องเป็น **ตัวเลขที่เด่นที่สุดในหน้า** — ใช้ `--fs-title:26px` ขึ้นไป + `--ink-strong` + `--fw-medium`
- **ราคาทั้งหมดยังเป็น DRAFT** ตามคำเตือนใน Initial Menu Data — prototype ต้องดึงราคาจาก seed data ไม่ hardcode ในหน้าจอ

## 6. ช่องว่างของ Theme — สิ่งที่ต้องสร้างเพิ่ม (พูดตรง ๆ)

### 6.1 🔴 ช่องว่างที่ 1 — theme ไม่มีหน้าจอพนักงาน/แอดมินเลยแม้แต่เฟรมเดียว

`readme.md` ของ design system เขียนเรื่องนี้ไว้เองตรง ๆ ว่า brief เดิมพูดถึง POS dashboard สำหรับแท็บเล็ต แต่ไฟล์ Figma ที่แนบมา **ไม่มี artwork ของ POS/tablet เลย** มีแค่ 4 เฟรมของแอปมือถือลูกค้า — และผู้ทำ design system เลือกที่จะ **ไม่แต่งขึ้นมาเอง** (ระบุว่า "none was invented")

**แต่ระบบของเรามี 3 surface:**

| Surface | มีใน theme? | จำนวนหน้าจอ Phase 0 |
|---|---|---|
| (ก) ลูกค้ามือถือ | ✅ ครบ 4 เฟรม (375×812) | 7 |
| (ข) จอสถานีพนักงานหน้าร้าน (US-13..US-20, US-29, US-30) | ❌ **ไม่มีเลย** | 8 |
| (ค) จอแอดมิน (US-23, US-24, US-36, US-42) | ❌ **ไม่มีเลย** | 8 |

**วิธีขยาย theme ไป surface ที่ 2–3 โดยไม่แต่งขึ้นมาลอย ๆ — กฎ 4 ข้อ:**

1. **Token ทั้งชุดใช้ร่วมกัน 100%** — สี ระยะ มุมโค้ง เงา ฟอนต์ น้ำหนัก ทุก surface ดึงจากไฟล์ token เดียวกัน (พร้อม override layer §3) **ห้ามสร้าง palette หรือ scale ใหม่ให้ surface ไหนเป็นการเฉพาะเด็ดขาด**
2. **Component ที่มีอยู่ต้องถูกใช้ซ้ำก่อนสร้างใหม่เสมอ** — ตั๋วออเดอร์บนจอสถานี = `RecentOrderCard` ที่ปรับขนาด · ป้ายที่มาออเดอร์ = `Badge` · ปุ่มยืนยันรับเงิน = `Button` lime — ทุกอย่างที่ปรากฏบนจอพนักงานต้องสืบสายมาจาก component ของลูกค้าได้ ถ้าสืบไม่ได้แปลว่ากำลังจะแต่งของใหม่ ต้องกลับมาถามตัวเองก่อน
3. **สิ่งที่ต่างกันได้มีแค่ 3 อย่าง: layout grid, ขนาดตัวอักษร, ขนาดพื้นที่กด** — มือถือลูกค้า 375×812 คอลัมน์เดียว base 16px tap 44 · จอสถานี **แนวนอน คาดหมาย 1024×768 (แท็บเล็ตวางเคาน์เตอร์)** หลายคอลัมน์ base 18px tap 48 · แอดมิน desktop/แท็บเล็ต หลายคอลัมน์ base 16px tap 44 — **การเปลี่ยน layout ไม่ใช่การเปลี่ยน design system**
4. **สิ่งที่ theme ไม่มีให้จริง ๆ (§6.3) ให้สร้างจาก primitive ของ theme เท่านั้น** — เช่น ช่องกรอกข้อมูลต้องเป็นสี่เหลี่ยมมุมโค้ง `--r-pill` พื้น `--surface-2` ขอบ `--border-a11y` ข้อความ `--fs-body` ไม่ใช่ไปหยิบ input มาจาก UI library อื่น

### 6.2 🔴 ช่องว่างที่ 2 — theme คือแอป pick-up/delivery ระบบเราไม่มี delivery

theme มี "Deliver to:", การ์ดเลือกประเภทออเดอร์ 2 ใบ (pick-up ไล่สีแดงอิฐ / delivery ไล่สีส้ม) และ `DeliveryInfoCard`

**ของเราต่างกันในเชิงโครงสร้าง ไม่ใช่แค่เปลี่ยนคำ:**

| theme | ระบบเรา |
|---|---|
| ลูกค้า**เลือก**เองว่า pick-up หรือ delivery | ช่องทาง **derive จาก QR ที่สแกน** ลูกค้าเลือกเองไม่ได้ (Business Rule ข้อ 12) |
| pick-up และ delivery ต่างกันที่**การส่งของ** | โต๊ะ (dine-in) และเคาน์เตอร์ (takeaway) ต่างกันที่ **กฎการจ่ายเงิน** — dine-in จ่ายทีหลังไม่บล็อกครัว / takeaway ต้องจ่ายก่อนเสมอ |
| ไม่มีแนวคิด "โต๊ะ" | โต๊ะคือหน่วยของ session และมี lifecycle (ว่าง ↔ ไม่ว่าง) ที่ derive จากออเดอร์ (Business Rule ข้อ 11) |
| ตะกร้าเป็นของคนเดียว | **ตะกร้าเป็นของโต๊ะ และเขียนพร้อมกันได้จากหลายเครื่อง** (Business Rule ข้อ 2) |

การ remap ทั้งหมดอยู่ใน §5.2 และ §5.3 แล้ว — สรุปสั้น: **การ์ดเลือกประเภทออเดอร์กลายเป็นแถบบอกช่องทางที่กดไม่ได้ · ไล่สีทั้งสองชุดถูกทิ้ง · `DeliveryInfoCard` ถูกแทนที่ด้วย `TableInfoCard`**

### 6.3 Component ที่ theme ไม่มีให้เลย ต้องสร้างใหม่ (สร้างจาก primitive ของ theme)

| ต้องสร้าง | ทำไม theme ไม่มี | ใช้กับ US |
|---|---|---|
| **ตัวปรับจำนวน (stepper − 1 +)** | theme มีแค่ปุ่ม add ที่สลับ ink+plus ↔ lime+check ไม่มีการนับจำนวน | US-03 |
| **ช่องกรอกข้อความ / ตัวเลข / dropdown / อัปโหลดรูป** | ไม่มี form ใด ๆ ใน 4 เฟรม | US-20 (เหตุผลยกเลิก), US-23, US-36, US-42, login |
| **สวิตช์เปิด-ปิด (toggle)** | ไม่มี | US-16, US-36 |
| **กล่องยืนยัน (modal) ที่บังคับกรอกเหตุผล** | ไม่มี | US-20 (บังคับตาม Business Rule ข้อ 5) |
| **แถบแจ้งเตือนแบบ inline / toast** | ไม่มี | ทุกกรณี error ใน UX §5 (เน็ตหลุด, สินค้าหมดกลางคัน, QR ผิด) |
| **Empty state** | ไม่มี | ตะกร้าว่าง, ยังไม่มีออเดอร์, ยังไม่มีโต๊ะ, ไม่มีเมล็ดพิเศษ |
| **Loading / skeleton** | theme มีแค่ `assets/loading-barista.png` เป็นภาพเดี่ยว ไม่มี pattern | UX §4 บังคับให้ทุกหน้าที่มีผลต่อการสั่งมี loading state |
| **ตาราง/รายการพร้อม action (list-with-actions)** | ไม่มี | US-23, US-36, US-42 (หน้าแอดมิน) |
| **การ์ดสถานะโต๊ะ + ผังโต๊ะ** | ไม่มีแนวคิดโต๊ะเลย | US-18, US-19, US-42 |
| **QR preview + เลย์เอาต์สำหรับพิมพ์** | ไม่มี | US-24 |
| **สถานะ "หมดชั่วคราว" ของ ProductCard** | theme มีแค่ default/selected | US-02, US-16, Business Rule ข้อ 4 |
| **หน้าเข้าสู่ระบบ** | มีแค่ `assets/login-espresso-machine.png` เป็นภาพประกอบ ไม่มีหน้าจอ | Business Rule ข้อ 9 |
| **Focus ring** | readme ระบุชัดว่า "No borders appear on focus" | ทุกหน้าจอ (§3.3) |

### 6.4 Glyph ที่ต้องวาดเพิ่ม (theme มี 15 ตัว)

theme มี: `chevron-forward/back/down/up-lead/up-trail/down-lead/down-trail`, `check`, `calendar`, `bag`, `notification`, `home`, `product-menu`, `pickup` (+ `pickup-bg`), `image-placeholder` — ทั้งหมดวาดบนกล่อง 22px เส้น 1px (32px/1.5px สำหรับ chevron คู่)

**ยังขาดสำหรับ Phase 0:** โต๊ะ · QR code · ร้อน · เย็น · ระดับการคั่ว · ความหวาน · เมล็ดกาแฟ · เงินสด/รับชำระ · เครื่องพิมพ์ · เตือน/ผิดพลาด · หมด/ปิดการขาย · ยกเลิก · แก้ไข · ลบ · ค้นหา · บวก/ลบจำนวน · นาฬิกา (เวลาที่รอ)

**กฎในการวาดเพิ่ม:** กล่อง 22px · เส้น 1px · monochrome · ไม่มี fill · ระบายด้วย CSS mask เพื่อรับ `currentColor` ตามกลไก `Icon` เดิม · **ห้ามใช้ icon font หรือ library ภายนอก และห้ามใช้ emoji แทนไอคอนเด็ดขาด** (theme ระบุกฎนี้ไว้เอง และตรงกับความต้องการของเรา)

### 6.5 🔴 ช่องว่างที่ 3 — ไม่มีอะไรรองรับตะกร้าที่เขียนพร้อมกันหลายเครื่อง

Business Rule ข้อ 2 กำหนดว่าหลายคนที่โต๊ะเดียวกันเพิ่มของเข้าตะกร้าเดียวกัน**พร้อมกัน**ได้ และ UX-06 กำหนดว่าต้องเห็นของกันและกันภายใน ≤5 วินาที โดยไม่มีรายการหาย — theme เป็นแอปผู้ใช้คนเดียวล้วน ไม่มีภาษาการออกแบบใด ๆ สำหรับเรื่องนี้เลย

**ต้องออกแบบใหม่ทั้งหมด:** ป้ายกำกับรายการที่คนอื่นเพิ่ม · สัญญาณกำลังซิงค์ · กรณีรายการถูกลบโดยคนอื่นขณะกำลังดูอยู่ · ข้อความอธิบายกลไก "ตะกร้าของโต๊ะไม่ใช่ของคุณคนเดียว" ให้ลูกค้าใหม่เข้าใจ — ตรงกับ pain point อันดับ 5 ของ Journey Map ที่ระบุว่าไม่มี US รองรับและ flag ให้ COULSON/SHURI พิจารณาตอนออกแบบ · **มีคำถามที่ต้องกลับไปถามใน §8 ข้อ 4**

## 7. สรุปไฟล์ token ที่ระบบเราจะประกาศจริง

```css
/* 1) โหลด token ต้นทางทั้งหมดตามลำดับของ theme
      (อ้างอิงค่าจาก path ใน §1 — ไม่คัดลอกไฟล์ binary เข้ามา) */
/* fonts → colors → typography → spacing → radii → effects */

/* 2) ชั้น override ของโปรเจกต์นี้ — ทับหลังสุดเสมอ */
:root{
  /* — accessibility (§3.1) — */
  --muted-a11y:  rgb(105,105,105); /* 4.82:1 บน 240 · 5.26:1 บน 250 · 4.69:1 บน 237 */
  --border-a11y: rgb(135,135,135); /* 3.15:1 บน 240 — เส้นที่สื่อความหมาย */
  --olive-a11y:  rgb(98,107,84);   /* 4.91:1 บน 240 */
  --danger-a11y: rgb(178,30,30);   /* 5.95:1 บน 240 */
  --focus-ring:  var(--ink);       /* 13.62:1 บน 240 · 12.51:1 บน lime */

  /* ผูกทับ alias เดิมของ theme ให้ทั้งระบบได้ค่าใหม่โดยไม่ต้องไล่แก้ทีละที่ */
  --text-secondary: var(--muted-a11y);
  --text-accent:    var(--olive-a11y);
  --border-hairline:var(--border-a11y);

  /* — พื้นที่กด (§3.3) — */
  --tap-44: 44px;  /* ขั้นต่ำฝั่งลูกค้า — เลิกใช้ --tap-40 */
  /* --tap-48 มีอยู่แล้วใน theme — บังคับใช้กับจอสถานีพนักงาน */

  /* — บรรทัดสำหรับภาษาไทย (§3.5) — */
  --lh-ui: 20px; --lh-caption: 20px; --lh-lead: 26px; --lh-display: 44px;

  /* — ตัวอักษร (§3.2) — */
  --fs-caption: 14px;        /* ยกจาก 12px · ห้ามใช้ในหน้าจอลูกค้าถ้ามีความหมาย */
  --fs-station-base: 18px;   /* base ของจอสถานีพนักงาน */

  /* — ฟอนต์ (§3.5) — */
  --font-thai: 'IBM Plex Sans Thai','Noto Sans Thai';
  --font-sans: 'Urbanist', var(--font-thai), -apple-system, BlinkMacSystemFont,
               'Segoe UI', Roboto, 'Helvetica Neue', Arial, sans-serif;
}

/* 3) กฎเฉพาะภาษาไทย */
:lang(th), [lang="th"]{ letter-spacing: normal; word-break: normal; overflow-wrap: break-word; }

/* 4) focus ที่ theme ตัดออก — เพิ่มกลับเข้ามาเพราะจำเป็น */
:focus-visible{ outline: 3px solid var(--focus-ring); outline-offset: 2px; }

/* 5) ตัวเลขเงิน */
.price, .total{ font-variant-numeric: tabular-nums; }

/* 6) เคารพการตั้งค่าลดการเคลื่อนไหว */
@media (prefers-reduced-motion: reduce){ *{ transition-duration: .01ms !important; animation: none !important; } }
```

**token ที่ประกาศว่าเลิกใช้ในโปรเจกต์นี้:** `--tap-40` · `--fs-caption:12px` (ค่าเดิม) · `--gradient-delivery` และ `--delivery-*` ทั้งชุด · `--gradient-pickup` และ `--pickup-*` ทั้งชุด · `--danger` เดิม (ใช้ `--danger-a11y` แทน) · `--muted`/`--muted-2`/`--muted-3` สำหรับข้อความ (ยังใช้กับเส้นตกแต่งล้วนได้)

`tokens/fig-tokens.css` (ธีม dark / peach-toned / neo-yellow, 8 ตัวแปรที่ใช้ธีมหน้า specimen ของ Figma เท่านั้น) **ไม่นำมาใช้** — ไม่ใช่ token ของ product UI และระบบเราไม่มีโหมดสีทางเลือกใน Phase 0

> 🟢 **คำตอบจาก Touch:** *"ร้อนเย็นแยกกันดีกว่า กดง่ายกว่าในหน้างานจริง"*
> → **ร้อน/เย็น = หมวดหมู่ · สินค้าแยกรายการตามอุณหภูมิ · หน้าเมนูมีการ์ด 32 ใบ (ร้อน 16 + เย็น 16)** — ตรงกับที่ทั้ง `01-prototypes` และ `02-technical` เลือกไว้ก่อนหน้าโดยอิสระ **ไม่มี rework**
> _(นับจริงจากตารางราคาใน [[../../01-requirements/01-spec/initial-menu-data-v1|Initial Menu Data]] เมื่อ 2026-08-16 — เดิมประมาณไว้ "~30")_
> ⚠️ **จำนวน `SectionHeader` สองหมวดไม่เท่ากัน:** หมวดร้อน**ไม่มี**กลุ่มซิกเนเจอร์ (SIG เย็นล้วน) · หมวดเย็น**ไม่มี**กลุ่มกาแฟดริป (DRIP ร้อนล้วน) → หน้าเมนูต้อง**ซ่อนหัวข้อกลุ่มที่ไม่มีสินค้าในหมวดนั้น ไม่ใช่โชว์หัวข้อว่าง**
> **เหตุผลที่ Touch ให้มาสำคัญกว่าตัวคำตอบ — ต้องรักษาไว้ในทุกงานออกแบบต่อจากนี้:** เหตุผลคือ **"กดง่ายกว่าในหน้างานจริง"** ไม่ใช่เรื่องความถูกต้องของ data model → แปลว่า **จำนวน tap จากเห็นเมนูถึงเพิ่มลงตะกร้าคือเกณฑ์ตัดสิน** ("ลาเต้เย็น" = 1 tap · ถ้าเป็นการ์ดเดียวแล้วเลือกอุณหภูมิทีหลัง = 2 tap) ซึ่งหนุน **UX-01** (สแกน → ยืนยันออเดอร์ให้สั้นที่สุด) และหนุน persona **P1 ฟ้า** ที่มีเวลาพักจำกัด กับ **P3 ป้าน้อย** ที่ทุกขั้นตอนเพิ่มคือความเสี่ยงที่จะติด
> **ข้อห้ามที่ตามมาโดยตรง:** ห้าม SHURI "แก้ปัญหาเมนูยาว" ด้วยการยุบร้อน/เย็นกลับเป็นการ์ดเดียวแล้วใส่ toggle อุณหภูมิ — นั่นคือการเอา tap กลับมาซึ่งเป็นสิ่งที่ Touch ตัดสินใจไม่เอา · ถ้าหน้าเมนูยาวเกินไปให้แก้ด้วย **การนำทาง** แทน (chip หมวดร้อน/เย็นที่ปักอยู่ด้านบน, `SectionHeader` ตามกลุ่มสินค้า 5 กลุ่ม, ทางลัดไปกลุ่มที่ต้องการ) ไม่ใช่แก้ด้วยการเพิ่มขั้นตอนให้ลูกค้า

<details>
<summary>บริบทเดิมของประเด็นนี้ก่อนปิด (เก็บไว้เป็นประวัติ)</summary>

- [[../../01-requirements/01-spec/product-backlog-v1|Product Backlog]] US-02 และ US-23 ระบุว่า **หมวดหมู่เมนูตั้งต้นคือ "ร้อน / เย็น" (2 หมวด)**
- แต่ [[../../01-requirements/01-spec/initial-menu-data-v1|Initial Menu Data]] จัดกลุ่มสินค้าจริงเป็น **กาแฟเอสเปรสโซเบส / ชา-มัทฉะ / ช็อกโกแลต-นม / ซิกเนเจอร์ / กาแฟดริป (5 กลุ่ม)** แล้วให้ **ร้อน/เย็นเป็นคอลัมน์ราคา 2 คอลัมน์ของสินค้าตัวเดียวกัน** (เช่น ESP-04 ลาเต้ ร้อน ฿60 / เย็น ฿70)

**นี่ไม่ใช่แค่เรื่องคำ — มันเปลี่ยนโครงสร้างหน้าจอเมนูทั้งหน้า:**
- ถ้า ร้อน/เย็น = **หมวดหมู่** → ลาเต้ต้องแตกเป็น 2 การ์ด (ลาเต้ร้อน, ลาเต้เย็น) → เมนู 19 รายการกลายเป็นการ์ดประมาณ 30 ใบ และ ESP-01 เอสเปรสโซ (ไม่มีเย็น) กับ SIG-01..03 (ไม่มีร้อน) จะโผล่ในหมวดเดียว
- ถ้า ร้อน/เย็น = **option group** → ลาเต้เป็นการ์ดเดียว ราคาเปลี่ยนตามที่เลือก → แต่ขัดกับ AC ของ US-02 ที่บอกว่าเห็นสินค้า "แบ่งหมวดหมู่" ตามที่ Touch ยืนยันมา และกระทบ US-23 (แอดมินจัดการหมวดหมู่)

**ข้อสรุปที่ใช้เดินงานแล้ว (ตัดสินโดยกฎ precedence ในหัวข้อ 0 ไม่ใช่ default ที่ยังลอยอยู่):** **หมวดหมู่ = ร้อน / เย็น ตาม backlog** โดยสินค้า 1 ตัว 1 อุณหภูมิ = 1 การ์ด (หน้าเมนูมีการ์ด **~30 ใบ** ไม่ใช่ 19) และใช้กลุ่มสินค้า 5 กลุ่มของ Initial Menu Data เป็น `SectionHeader` ภายในแต่ละหมวดแทน

**เหตุผลที่ backlog ชนะในข้อนี้ — เป็นเรื่องที่มาของข้อมูล ไม่ใช่ความชอบ:** หมวดหมู่ "ร้อน / เย็น" ใน US-02/US-23 มาจาก**คำสั่งของ Touch โดยตรง**และถูกบันทึกเป็นบรรทัดอัปเดตในหัว backlog ส่วนการจัด 5 กลุ่ม + คอลัมน์ราคา 2 คอลัมน์ใน Initial Menu Data เป็น**วิธีนำเสนอตารางที่ XAVIER เลือกเอง**เพื่อให้อ่านราคาเทียบกันง่าย ไม่ได้เป็นการตัดสินใจเรื่องโครงสร้างข้อมูลที่ Touch เคาะ — เมื่อเอกสารระดับเดียวกันขัดกัน ให้ยึดข้อความที่สืบกลับไปถึงการตัดสินใจของ Touch ได้ · **COULSON ฝั่ง `02-technical` เลือกเหมือนกันโดยอิสระ** (แยกเป็น 2 สินค้า เพราะทำให้มาร์ก "หมดชั่วคราว" แยกร้อน/เย็นได้จริงตาม US-16) → ทั้งสองฝั่งตรงกัน ไม่มี rework

> 🔴 **ย่อหน้าถัดไปถูก SUPERSEDE แล้ว — เก็บไว้เป็นประวัติเท่านั้น ห้ามใช้เดินงาน** (แก้ 2026-08-16, D-4)
> ตอนเขียนย่อหน้านี้ยังไม่มีคำตอบจาก Touch จึงเสนอ *"toggle ร้อน/เย็นบนการ์ดเดียว"* ไว้เป็นทางออกหนึ่ง
> **Touch ตอบแล้วเมื่อ 2026-08-15 และข้อเสนอนั้นถูกปฏิเสธ** — ดูบล็อกคำตัดสินด้านบนของหัวข้อนี้:
> ห้ามยุบร้อน/เย็นกลับเป็นการ์ดเดียวแล้วใส่ toggle เพราะเป็นการเอา tap กลับมา
> **ถ้าหน้าเมนูยาวเกินไป ให้แก้ด้วยการนำทาง** (chip หมวดปักบนสุด, `SectionHeader` ตามกลุ่มสินค้า, ทางลัดไปกลุ่ม) เท่านั้น
> อีกจุด: ตัวเลข "~30" ในย่อหน้านี้เป็นการประมาณ **จำนวนจริงคือ 32 การ์ด (ร้อน 16 + เย็น 16)** นับจากตารางราคาใน [[../../01-requirements/01-spec/initial-menu-data-v1|Initial Menu Data]]

**~~ยังต้องให้ Touch รับทราบ (ไม่บล็อกงาน)~~ [ปิดแล้ว 2026-08-15]:** ผลที่ตามมาคือจำนวนการ์ดในหน้าเมนูเพิ่มจาก 19 เป็น ~~~30~~ **32** และ ESP-01 เอสเปรสโซ (ไม่มีเย็น) กับ SIG-01..03 (ไม่มีร้อน) จะปรากฏในหมวดเดียว — ~~ถ้า Touch มองว่าหน้าเมนูยาวเกินไป ทางแก้คือปรับ**การนำเสนอ** (เช่น toggle ร้อน/เย็นบนการ์ดเดียว)~~ **← ข้อเสนอนี้ถูกปฏิเสธแล้ว ดูกล่องเตือนด้านบน** ซึ่งเป็นเรื่อง UI ไม่ใช่การกลับไปแก้ data model และควรตัดสินก่อน SHURI ลงมือทำ mockup หน้าเมนู เพราะเป็นหน้าที่ทุก persona ผ่าน

### ✅ ข้อ 2 — ยังไม่มีรูปสินค้าเลยสักรายการ แต่ ProductCard ของ theme เป็นการ์ดที่นำด้วยรูป — **ปิดแล้ว (build จริง 2026-08-23)**

> 🟢 **สถานะจริงหลัง build:** Touch ได้ถ่ายภาพจริงชุดแรกด้วย Higgsfield AI photo shoot แล้ว — ตอนนี้ **7 จาก ~24 รายการสินค้ามีรูปจริง** (ESP-01 เอสเปรสโซ, ESP-02 อเมริกาโน่เย็น, ESP-04 ลาเต้ทั้งร้อน/เย็น, ESP-05 คาปูชิโน่ร้อน, TEA-01 ชาเย็น, DRIP-01 กาแฟดริปร้อน) เก็บไว้ที่ `public/products/*.jpg` ของ `qr-order-app` (resize ผ่าน `sips` เหลือ ~110–185KB ต่อไฟล์) และประกาศ `imageUrl` เข้า `MenuItem`/`seed.ts` แล้ว
> **กลไกสำหรับรายการที่ยังไม่มีรูป (แทนที่คำถามเดิม):** แทนที่จะสร้าง 2 variant การ์ด (มีรูป/ไม่มีรูป) เลือกสร้าง **ช่องอัปโหลดรูปในหน้าแอดมิน** (`A-03`, endpoint `POST /api/v1/admin/products/{id}/image` — multipart form, resize ด้วย `sharp` ฝั่งเซิร์ฟเวอร์, จำกัด 5MB/เฉพาะ JPEG) ให้ Touch ถ่ายเพิ่มและอัปโหลดเองทีละรายการได้ตลอดเวลา ไม่ต้องรอ deploy ใหม่ — ตรงกับ UX-11 ("ห้ามให้คุณแอนต้องกรอกอะไรที่เธอไม่รู้จัก") เพราะเป็นปุ่มเลือกไฟล์รูปธรรมดา ไม่ใช่ให้กรอก URL ดิบ ส่วน `ProductCard`/`ProductView` ที่ยังไม่มี `imageUrl` ยังคงตกกลับไปที่สถานะไม่มีรูป (ยังไม่ได้ทำ variant นำด้วยข้อความแยกตามที่ default เดิมเสนอไว้ — ยังเป็นช่องว่างเชิง UI เล็ก ๆ ที่เหลืออยู่ ไม่บล็อกการเปิดร้าน เพราะสัดส่วนรูป:ไม่มีรูปจะค่อย ๆ ลดลงเมื่อ Touch อัปโหลดเพิ่ม)
> 🔴 **บั๊กที่เจอตอน build และผูกกับดีไซน์นี้โดยตรง:** `image_url` มี `?v=<timestamp>` ต่อท้ายเสมอ (กันแคชรูปเก่าตอนอัปโหลดทับ) แต่ Next.js 16 บล็อกรูปโลคัลที่มี query string โดยปริยาย — ถ้าไม่ประกาศ `images.localPatterns` ให้ถูกต้อง (`search` ต้องไม่ประกาศเลย ไม่ใช่ `''`) หน้า `/t/{code}` ทั้งหน้าจะ 500 ทันทีที่สินค้าใดสินค้าหนึ่งมีรูป — แก้แล้วใน `next.config.ts` รายละเอียดเต็มอยู่ที่ [[../../05-log/changelog|05-log/changelog]] วันที่ 2026-08-23

`ProductCard` ขนาด 167×304 มีพื้นที่รูปเป็นสัดส่วนหลักของการ์ด แต่ Initial Menu Data ระบุเองว่า "รูปภาพสินค้าแต่ละเมนู — Touch (ถ่ายภาพจริงของร้าน) หรือ SHURI เลือก placeholder ชั่วคราว"

### ข้อ 3 — "รอเสิร์ฟ" ของ US-30 เป็น label หรือ status field จริง? (ประเด็นเดิมที่ XAVIER flag ไว้ ยังไม่ปิด)

ประเด็นนี้ถูกบันทึกไว้แล้วใน US-30 Notes และ "สถานะ Handoff" ของ task breakdown — **ตอนนี้มันบล็อกการออกแบบจริงแล้ว** เพราะกระทบหน้าจอ 3 หน้าพร้อมกัน: การ์ดสถานะฝั่งลูกค้า (US-05), กระดานออเดอร์ฝั่งพนักงาน (US-13), และคิวรอยืนยันชำระเงิน (US-29)
**Default:** ถือว่า "รอเสิร์ฟ" เป็น **label ของจุดรับของ** ที่ครอบช่วง "จ่ายเงินแล้ว → ลูกค้ามารับที่ปลายเคาน์เตอร์" ไม่ใช่ status ใหม่ — pipeline สถานะจริงยังคงเป็น 3 ค่าตาม Glossary ของ UX Requirements (รอดำเนินการ / กำลังทำ / เสร็จแล้ว) บวกสถานะ "รอยืนยันการชำระเงิน" ที่เป็นของช่องทางเคาน์เตอร์เท่านั้น

### ข้อ 4 — จะบอกลูกค้าอย่างไรว่า "รายการนี้คนอื่นที่โต๊ะเป็นคนเพิ่ม" โดยไม่ผิด Business Rule ข้อ 14?

Journey Map ระบุ pain point ข้อ 5 ว่าลูกค้าจะสับสนเมื่อเห็นรายการที่คนอื่นเพิ่ม และเสนอ badge "เพิ่มโดยคนอื่นที่โต๊ะ" — **แต่การจะแยกว่า "คนอื่น" คือใคร ต้องมีตัวระบุอุปกรณ์บางอย่าง** ซึ่งเฉียดกับ Business Rule ข้อ 14 ที่ห้าม "device fingerprint ที่ใช้ระบุตัวตนข้ามครั้งการมาใช้บริการ"
**คำถามถึง XAVIER:** ตัวระบุแบบ **ชั่วคราวและอยู่ในขอบเขต session ของโต๊ะเดียวเท่านั้น** (สุ่มขึ้นใหม่ทุกรอบลูกค้า ตายพร้อมการปิดบิล ไม่ผูกกับอุปกรณ์ข้ามครั้ง) ถือว่าอยู่ในกรอบ Business Rule ข้อ 14 หรือไม่?
**Default:** ใช้ตัวระบุชั่วคราวต่อ session ตามข้างต้น (ถือว่าไม่ใช่ข้อมูลส่วนบุคคลเพราะไม่ระบุตัวตนและไม่ข้าม session) และแสดงเป็น badge กลาง ๆ ว่า "เพิ่มจากอีกเครื่องที่โต๊ะนี้" **โดยไม่มีชื่อ/สี/สัญลักษณ์ประจำตัวบุคคล**

### ข้อ 5 — อุปกรณ์จริงของจอสถานีพนักงาน (NEED-INPUT เดิมข้อ 3 ของ UX Requirements ยังไม่ได้คำตอบ)

กระทบ layout ของหน้าจอพนักงานทั้ง 8 หน้าโดยตรง (จำนวนคอลัมน์, ขนาดตัวอักษร, จะมีสลิปกระดาษด้วยหรือไม่)
**Default:** แท็บเล็ตวางเคาน์เตอร์ **แนวนอน 1024×768** ระยะอ่าน 50–80 ซม. base 18px ไม่มีเครื่องพิมพ์สลิปใน Phase 0

### ข้อ 6 — ขอบเขต accessibility: คีย์บอร์ด/screen reader อยู่ใน Phase 0 หรือไม่ (NEED-INPUT เดิมข้อ 2 ของ UX Requirements)

Business Rule ข้อ 23 ระบุ 4 อย่าง (ฟอนต์ / contrast / tap / ไม่พึ่งสีเดี่ยว) แต่ **ไม่ได้พูดถึง focus ที่มองเห็นได้และการใช้คีย์บอร์ด** — ขณะที่ theme ตัด focus border ออกอย่างจงใจ และ P5 คุณแอนใช้หน้าแอดมินจากคอมพิวเตอร์
**Default:** COULSON **เพิ่ม focus ring กลับเข้ามาแล้วใน §3.3 ในฐานะข้อบังคับ** (ต้นทุนต่ำมาก ประโยชน์สูง โดยเฉพาะกับหน้าแอดมิน) ส่วน screen reader เต็มรูปแบบยังถือว่านอกสโคป Phase 0 ตาม default เดิมของ XAVIER

### ข้อ 7 — โซนของโต๊ะที่ US-42 ให้จัดกลุ่ม มีชื่อจริงว่าอะไร

US-42 บอกให้จัดกลุ่มเป็นโซน (ยกตัวอย่าง "ในร้าน/นอกร้าน/ริมหน้าต่าง") แต่ยังไม่มี seed data จริงของร้าน Touch
**Default:** ให้แอดมินตั้งชื่อโซนเองอิสระ (ไม่ hardcode) และ seed ตัวอย่างไว้ 2 โซนสำหรับ prototype — ไม่กระทบโครงสร้าง

---

ส่งงาน — COULSON → ทัช (งาน / ผลลัพธ์ / ค้าง-เสี่ยง / skill ที่ใช้)

**งาน:** รับช่วงต่อจาก XAVIER เริ่ม `02-design/01-prototypes` — วิเคราะห์ design system "Artisan Coffee" ที่ Touch กำหนด เทียบกับ requirement ทั้งชุดของ Phase 0 แล้วประกาศเป็นสัญญาการรับ theme มาใช้: token ที่รับตรง ๆ, accessibility override layer ที่คำนวณค่าจริง, font stack ไทย+ละติน, รูปแบบราคาบาท, component inventory ที่แม็ปกับ US, และช่องว่างของ theme ที่ต้องพูดตรง ๆ

**ผลลัพธ์:** ไฟล์ `docs/02-design/01-prototypes/design-system-adoption-v1.md` — token ที่รับมาใช้ตรง ๆ 13 กลุ่ม · override สี 5 ค่าพร้อม contrast ที่คำนวณครบทุกคู่พื้นผิว (muted 105 = 4.82:1 · border 135 = 3.15:1 · olive 98,107,84 = 4.91:1 · danger 178,30,30 = 5.95:1 · focus ring ink = 13.62:1) · override ตัวอักษร/บรรทัด/tap/focus · font stack IBM Plex Sans Thai + กฎ metric ไทย 5 ข้อ · รูปแบบราคาบาท 6 บริบท · แม็ป component ของ theme ทั้ง 19 ตัวเป็น 3 กลุ่ม (ใช้ต่อ 9 · remap 7 · ทิ้ง/เลื่อน 3 + gradient 2 ชุด) · ช่องว่างของ theme 3 เรื่องใหญ่ + component ที่ต้องสร้างใหม่ 13 ตัว + glyph ที่ต้องวาดเพิ่ม 17 ตัว · ประเด็นถาม XAVIER/Touch 7 ข้อพร้อม default ที่ทำงานต่อได้

**ค้าง/เสี่ยง:** **(1)** ความขัดแย้งเรื่อง "ร้อน/เย็น เป็นหมวดหมู่หรือ option" ระหว่าง Product Backlog กับ Initial Menu Data เป็นความเสี่ยงที่แท้จริงต่อโครงสร้างหน้าเมนู — มี default ให้แล้วแต่ควรได้คำตอบก่อน SHURI ลงมือ **(2)** ค่าสี override ทั้ง 4 ตัวคำนวณตามสูตร WCAG relative luminance และตรวจสอบซ้ำแล้วว่าตรงกับค่าที่มีอยู่เดิมของ theme ทุกตัว แต่ยังไม่ผ่านการตรวจด้วยเครื่องมืออัตโนมัติ (axe/Lighthouse) บนหน้าจอจริง — ต้องตรวจซ้ำตอน SHURI สร้าง prototype **(3)** การเพิ่ม hairline บนการ์ดที่กดได้เป็นการเบี่ยงจาก "no borders" ของ theme อย่างจงใจ บันทึกเหตุผลไว้ใน §3.4 แล้ว ถ้า Touch ไม่ยอมรับต้องหาทางอื่นแก้ปัญหาแดดจ้าแทน ไม่ใช่ปล่อยผ่าน **(4)** การเลือกฟอนต์ไทยยังต้องยืนยันด้วยการทดสอบกับผู้ใช้ตัวแทน P3 จริง — ออกแบบให้สลับเป็น Sarabun ได้ด้วย token ตัวเดียวแล้ว **(5)** 🔴 **ความเสี่ยงข้อนี้เกิดขึ้นจริงแล้ว 2026-08-23 — ไม่ใช่ความเสี่ยงที่เฝ้าอยู่อีกต่อไป** · theme ไม่มีหน้าจอพนักงาน/แอดมินให้เลย 16 จาก 23 หน้าจอของ Phase 0 จึงต้องขยายเอง กฎ 4 ข้อใน §6.1 ถูกปฏิบัติตามครบ (ตรวจแล้ว: ไม่มีสี hardcode, ไม่มี Tailwind palette, ใช้ token ร่วม 100%) **แต่กฎ 4 ข้อคุมได้แค่ชั้น token กับ primitive — คุม "โครงหน้าจอ" ไม่ได้** ผลคือ rail/top bar/โครงหน้าสั่ง/การแยกแอดมินออกเป็นอีกแอปหนึ่ง ถูกประดิษฐ์ขึ้นโดยไม่มีอะไรให้ยึด และ Touch แจ้งว่าไม่ตรงกับ prototype · **บทเรียน: ถ้าไม่มีเฟรมต้นทาง กฎระดับ token ไม่พอ ต้องมี เฟรมโครงหน้าจอให้ยึดก่อนลงมือ** — รายละเอียดเต็มและคำตัดสินของ Touch (รวม admin+staff เป็นแอปเดียว) อยู่ที่ [[mockup-thyna-pos-v1|mockup-thyna-pos-v1]] §6

**skill ที่ใช้:** scrutinize (ตรวจ theme ทีละ token/component เทียบกับ requirement จริงแทนการเชื่อสรุปที่ได้รับมา — คำนวณ contrast ซ้ำเองทุกคู่จนพบเพิ่มว่า `--danger` ตกแม้เกณฑ์ 3:1 และบันไดพื้นผิว 5 ขั้นห่างกันแค่ 1.03–1.09:1 ซึ่งพังทั้งชุดกลางแดดตาม UX §4 — สองข้อนี้ไม่มีอยู่ใน brief ที่ได้รับมา และตรวจข้ามเอกสารต้นทางจนพบความขัดแย้งเรื่องหมวดหมู่ ร้อน/เย็น), management-talk (แยกสิ่งที่ COULSON ตัดสินเองได้ ออกจาก 7 ข้อที่ต้องให้ XAVIER/Touch ตัดสิน โดยทุกข้อมี default ให้ทีมเดินงานต่อได้ ไม่ทิ้งเป็นคำถามค้างที่หยุดงาน)
