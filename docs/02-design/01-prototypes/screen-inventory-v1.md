## 0. ขอบเขตและวิธีอ่านเอกสารนี้

เอกสารนี้คือ **รายการหน้าจอทั้งหมดที่ Phase 0 ต้องมี** แยกตาม 3 surface — ใช้เป็นฐานให้ SHURI ทำ wireframe/mockup และให้ OKOYE แปลงเป็น test case

**สรุปจำนวน:**

| Surface | อุปกรณ์เป้าหมาย | จำนวนหน้าจอ | Persona หลัก |
|---|---|---|---|
| **A — ลูกค้ามือถือ** | มือถือส่วนตัว 375×812 (ทดสอบ ~5" และ ~6.5") | **7** | P1 ฟ้า · P2 ต้น · P3 ป้าน้อย |
| **B — จอสถานีพนักงานหน้าร้าน** | แท็บเล็ตวางเคาน์เตอร์ แนวนอน ~1024×768 (สมมติฐาน — ดู §5 ข้อ 1) | **8** | P4 เบียร์ |
| **C — จอแอดมิน** | คอมพิวเตอร์/แท็บเล็ต ที่ร้าน นอกเวลาขาย | **8** | P5 คุณแอน |
| | | **รวม 23 หน้าจอ** | |

> **หมายเหตุ:** หน้าเข้าสู่ระบบ S-00 กับ A-00 ใช้ component และ layout ชุดเดียวกัน (ต่างกันแค่ปลายทางหลัง login) — นับแยกเพราะเป็นคนละ surface และคนละ persona แต่ **SHURI ออกแบบครั้งเดียวใช้ทั้งสองที่ได้**

**กติกาที่ทุกหน้าจอในเอกสารนี้ต้องผ่าน (ไม่เขียนซ้ำในทุกหน้า):**
- ทุกหน้าจอฝั่งลูกค้า (Surface A) ต้องผ่าน accessibility baseline ของ Business Rule ข้อ 23 ครบทุกข้อ — ฟอนต์เนื้อหา ≥16px · contrast ≥4.5:1 (ใช้ค่า override ใน [[design-system-adoption-v1|Design System Adoption v1]] §3.1) · พื้นที่กด ≥44×44px · **ห้ามใช้สีเดี่ยวสื่อความหมายทุกจุด** ต้องมีข้อความหรือไอคอนกำกับเสมอ
- ทุกหน้าจอ Surface B ปุ่มหลัก ≥48×48px ระยะห่างระหว่างปุ่ม ≥8px (UX-09) และตัวอักษร base 18px อ่านได้ที่ระยะ 50–80 ซม.
- ทุกหน้าจอที่มีการเรียกข้อมูลต้องมี **สถานะโหลด** ที่ชัดเจน และ **ห้ามแสดงว่าสำเร็จจนกว่าเซิร์ฟเวอร์ตอบกลับจริง** (UX §4)
- ทุก state ในตาราง "สถานะที่ต้องออกแบบ" ต้องมี wireframe จริง **ห้ามเป็น dead-end screen** — ทุกหน้าต้องบอกได้ว่า "ทำอะไรต่อได้" (UX §5)
- ใช้คำศัพท์ตาม Glossary ของ [[../../01-requirements/01-spec/ux-requirements-v1|UX Requirements v1]] หัวข้อ 6 เท่านั้น (ตะกร้า / ออเดอร์ / โต๊ะ / รอบลูกค้า / บิล / ปลายเคาน์เตอร์ / สถานะออเดอร์) — ห้ามใช้ "session", "checkout", "submit" ในข้อความที่ลูกค้าเห็น

## 3. Surface B — จอสถานีพนักงานหน้าร้าน (8 หน้าจอ)

> **บริบทที่ต้องออกแบบเผื่อเป็นค่าเริ่มต้น ไม่ใช่กรณีพิเศษ (UX Principle ข้อ 6):** เบียร์ (P4) **มือเปียก/เปื้อนตลอดกะ** · เสียงเครื่องชงกลบเสียงแจ้งเตือน · ต้องดูจอสลับกับมือที่ไม่ว่าง · **เป็น single point of failure ของทั้งระบบ** ถ้าจอนี้พังทุก journey พังตาม
> ปุ่มหลักทุกปุ่ม ≥48×48px ระยะห่าง ≥8px · **ห้ามใช้ swipe / long-press กับ action หลัก** · แจ้งเตือนต้องเห็นชัดแม้ไม่ได้ยินเสียง

## 5. ประเด็นที่ต้องกลับไปถาม XAVIER / Touch

> ทุกข้อมี default ที่ใช้ทำงานต่อได้ · **ห้ามแก้ไฟล์ใน `docs/01-requirements/` เอง**
> ข้อ 1–7 ที่เป็นเรื่อง design system อยู่ใน [[design-system-adoption-v1|Design System Adoption v1]] §8 — ด้านล่างคือประเด็นที่โผล่มาจากการทำ **screen inventory** โดยเฉพาะ

1. **อุปกรณ์จริงของจอสถานี (NEED-INPUT เดิมข้อ 3 ของ UX Requirements ยังไม่ได้คำตอบ)** — กระทบ layout ของ S-00 ถึง S-07 ทั้ง 8 หน้าโดยตรง และกระทบว่าจะมี **เครื่องพิมพ์สลิปกระดาษ** ด้วยหรือไม่ (US-13 Notes เปิดทางไว้ว่า "จอ vs พิมพ์สลิป" เป็นการตัดสินใจของ COULSON) **Default:** แท็บเล็ตแนวนอน 1024×768 บนเคาน์เตอร์ **ไม่มีเครื่องพิมพ์สลิปใน Phase 0** — ถ้า Touch ต้องการสลิปกระดาษจริง จำนวนหน้าจอไม่เปลี่ยน แต่ต้องเพิ่มงานออกแบบเลย์เอาต์สลิป

2. **"ร้อน/เย็น" เป็นหมวดหมู่หรือ option group** (รายละเอียดเต็มใน Design System Adoption §8 ข้อ 1) — เป็นประเด็นเดียวที่ **เปลี่ยนจำนวนการ์ดบนหน้า C-01 จาก ~19 เป็น ~30 ใบ** และเปลี่ยนโครงสร้าง C-02 ทั้งหน้า **Default:** หมวดหมู่ = ร้อน/เย็น ตาม backlog

3. **ลูกค้าช่องทาง takeaway ต้องมีหน้าสรุปยอด (C-06) ด้วยหรือไม่** — US-07 เขียนสำหรับ dine-in ("สรุปยอดของโต๊ะ ... ไปชำระที่เคาน์เตอร์") แต่ takeaway จ่ายก่อนไปแล้ว จึงไม่มีบิลค้างให้สรุป **Default:** ช่องทาง takeaway ไม่มี C-06 — ลูกค้าเห็นยอดที่จ่ายไปแล้วบนการ์ดออเดอร์ใน C-05 แทน และ TabBar ของโหมดเคาน์เตอร์มี 3 ปุ่มแทน 4

4. **US-09 (หมายเหตุพิเศษ เช่น "แพ้ถั่ว") เป็น Phase 1 — ตั๋วออเดอร์ของ Phase 0 ควรเผื่อพื้นที่ไว้เลยหรือไม่** — ถ้าไม่เผื่อ ตอน Phase 1 ต้องรื้อ layout ของ S-01/S-02 ใหม่ **Default:** SHURI เผื่อพื้นที่ในโครง layout ของตั๋วไว้ **แต่ไม่สร้าง UI ใด ๆ ของ US-09 ใน Phase 0**

5. **US-26 (เปิด/ปิดรับออเดอร์ของร้าน) เป็น Phase 1 แต่ UX §5 บรรจุกรณี "ร้านปิดรับออเดอร์" ไว้ในตาราง error state ที่บังคับให้มี wireframe** — เกิดความกำกวมว่าหน้าจอนี้อยู่ใน Phase 0 หรือไม่ **Default:** ออกแบบ **ข้อความ/สถานะ** ของ C-01 กรณีร้านปิดรับออเดอร์ไว้ตั้งแต่ Phase 0 (เพราะ UX §5 บังคับ) แต่ **ไม่สร้างหน้าจอฝั่งแอดมินสำหรับกดเปิด/ปิด** (นั่นคือ US-26 ของ Phase 1)

6. **จำนวน QR เคาน์เตอร์** — Business Rule ข้อ 12 พูดถึง QR เคาน์เตอร์แบบเอกพจน์ แต่ไม่ได้ระบุว่าร้านมีจุดสั่งกี่จุด **Default:** 1 ใบ และ A-07 ออกแบบให้รองรับมากกว่า 1 ใบได้โดยไม่ต้องแก้โครงสร้าง
