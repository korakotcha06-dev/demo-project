- ทุกหน้าจอฝั่งลูกค้า (Surface A) ต้องผ่าน accessibility baseline ของ Business Rule ข้อ 23 ครบทุกข้อ — ฟอนต์เนื้อหา ≥16px · contrast ≥4.5:1 (ใช้ค่า override ใน [[design-system-adoption-v1|Design System Adoption v1]] §3.1) · พื้นที่กด ≥44×44px · **ห้ามใช้สีเดี่ยวสื่อความหมายทุกจุด** ต้องมีข้อความหรือไอคอนกำกับเสมอ
- ทุกหน้าจอ Surface B ปุ่มหลัก ≥48×48px ระยะห่างระหว่างปุ่ม ≥8px (UX-09) และตัวอักษร base 18px อ่านได้ที่ระยะ 50–80 ซม.
- ทุกหน้าจอที่มีการเรียกข้อมูลต้องมี **สถานะโหลด** ที่ชัดเจน และ **ห้ามแสดงว่าสำเร็จจนกว่าเซิร์ฟเวอร์ตอบกลับจริง** (UX §4)
- ทุก state ในตาราง "สถานะที่ต้องออกแบบ" ต้องมี wireframe จริง **ห้ามเป็น dead-end screen** — ทุกหน้าต้องบอกได้ว่า "ทำอะไรต่อได้" (UX §5)
- ใช้คำศัพท์ตาม Glossary ของ [[../../01-requirements/01-spec/ux-requirements-v1|UX Requirements v1]] หัวข้อ 6 เท่านั้น (ตะกร้า / ออเดอร์ / โต๊ะ / รอบลูกค้า / บิล / ปลายเคาน์เตอร์ / สถานะออเดอร์) — ห้ามใช้ "session", "checkout", "submit" ในข้อความที่ลูกค้าเห็น

## 3. Surface B — จอสถานีพนักงานหน้าร้าน (8 หน้าจอ)

> **บริบทที่ต้องออกแบบเผื่อเป็นค่าเริ่มต้น ไม่ใช่กรณีพิเศษ (UX Principle ข้อ 6):** เบียร์ (P4) **มือเปียก/เปื้อนตลอดกะ** · เสียงเครื่องชงกลบเสียงแจ้งเตือน · ต้องดูจอสลับกับมือที่ไม่ว่าง · **เป็น single point of failure ของทั้งระบบ** ถ้าจอนี้พังทุก journey พังตาม

**การตัดสินใจเชิงออกแบบของแท็บวิเคราะห์เชิงลึกที่ต้องบันทึกไว้ (คนอ่านทีหลังจะสงสัยถ้าไม่มี):**

1. **แกนเวลาของตารางสี (heatmap) คิดคนละแกนกันโดยเจตนา** — แถวคือ**วันธุรกิจ** (`extract(dow FROM pb.business_date)`, หัก `business_day_cutoff` แล้ว) ส่วนคอลัมน์คือ**ชั่วโมงตามนาฬิกาไทยจริง** ไม่หัก cutoff เหตุผล: คนจัดตารางเข้างานคิดเป็นกะไม่ใช่วันตามปฏิทิน และแบบนี้ผลรวมของตารางสีจะเท่ากับผลรวมของกราฟแนวโน้มเสมอ (กระทบยอดกันได้) — เดิมถ้าคิดแถวจากนาฬิกาดิบ ออเดอร์ตี 0 ครึ่งของร้านที่ปิดตี 1 จะถูกนับเงินเข้าวันพุธ (ตามวันธุรกิจ) แต่วาดลงช่องพฤหัส (ตามนาฬิกา) ทำให้ตารางกับกราฟกระทบยอดกันไม่ได้ — **เทส integration เป็นตัวจับพฤติกรรมนี้ได้ ไม่ใช่การรีวิวด้วยตา** (ดูกลุ่มเทส "ขอบวันธุรกิจมีผลกับทุกก้อนเหมือนกัน" ใน `tests/integration/analytics.test.ts`)
2. **ยอดสองสกุลในหน้าเดียวโดยเจตนา** — แนวโน้มและช่วงเทียบใช้ยอดระดับ**บิล** (`bill.total_satang`) เพื่อให้ทับกับรายงานรายวันของแท็บภาพรวม (US-25) ได้เป๊ะทุกวัน ส่วนหมวดหมู่/สินค้า/ช่องทาง/ชั่วโมงใช้ยอดระดับ**รายการในออเดอร์** (`order_item.line_total_satang`) เพราะคุณสมบัติเหล่านั้นเป็นของออเดอร์ ไม่ใช่ของบิล (บิลโต๊ะใบเดียวมีได้หลายออเดอร์) — สัดส่วนร้อยละ (`sharePct`) จึงหารด้วยผลรวมของก้อนตัวเอง ไม่ใช่ยอดของ trend เพื่อให้บวกกันได้ครบ 100% เสมอแม้ร้านเปิดโหมด VAT แบบ exclude
3. **ข้อจำกัดที่ยังเหลือ 3 ข้อ (ตั้งใจ ไม่ใช่บั๊ก):** response ไม่มียอดรวมของช่วงหลักส่งตรงมาให้ ต้องบวกเอาจากอาร์เรย์ `trend` เอง · หมวดหมู่ในกราฟอ่านจาก**หมวดปัจจุบัน**ของสินค้า เพราะ `order_item` ไม่ได้ snapshot หมวดหมู่ไว้ตอนขาย — ย้ายสินค้าข้ามหมวดแล้ว ยอดเก่าจะตามไปกองที่หมวดใหม่ทันที ไม่ใช่คงอยู่กับหมวดตอนขาย · ชั่วโมงหนาแน่นนับจากเวลาที่ออเดอร์**เข้าคิว** (`orders.placed_at`) ไม่ใช่เวลาที่จ่ายเงิน เพราะภาระของพนักงานเกิดตอนออเดอร์เข้า ไม่ใช่ตอนโต๊ะเรียกเก็บเงินซึ่งอาจห่างกันหลายชั่วโมง

**AC ทั้ง 5 ข้อของ US-53 ปิดครบ:** [x] แนวโน้มเทียบช่วงเวลา (พร้อม `deltaPct = null` เมื่อไม่มีฐานเทียบ) · [x] เปรียบเทียบหมวดหมู่/สินค้า 20 อันดับ · [x] สัดส่วน 3 ช่องทาง (ไม่เพิ่มจุดเก็บข้อมูลใหม่) · [x] ชั่วโมงหนาแน่น (แท่ง 24 ชม. + heatmap 168 ช่อง) · [x] aggregate ล้วน (เทส recursive ยืนยัน) — รายละเอียดหลักฐานเต็มอยู่ที่หัวข้อ US-53 ใน product-backlog-v1

**สมมติฐานที่ตั้งไว้ตอนเริ่มออกแบบ A-09 (ก่อนพบว่ามีโค้ดจริงอยู่แล้ว) เทียบกับสิ่งที่โค้ดจริง
ตัดสินใจไปแล้ว — 2 ใน 4 ข้อขัดกัน ต้องแจ้ง Touch ว่าจะยึดตามโค้ดจริงหรือแก้โค้ดให้ตรงสมมติฐาน:**

1. **สมมติฐานเดิม: ขอบเขตวันธุรกิจตัดที่ 04:00 น. คงที่ ไม่ใช่เที่ยงคืน** — เหตุผลตอนตั้งสมมติฐาน: ร้านกาแฟเปิดเช้าปิดค่ำ ไม่มีออเดอร์ข้ามเที่ยงคืนอยู่แล้วในทางปฏิบัติ แต่การตัดที่เที่ยงคืนเสี่ยงพลาดถ้าร้านเปิดดึก
   **สิ่งที่โค้ดจริงทำ (ขัดกับสมมติฐาน):** `migrations/024_business_day_cutoff.sql` เพิ่มคอลัมน์ `shop.business_day_cutoff time` ให้ **เจ้าของร้านตั้งเอง** (ไม่ hardcode) โดย **default = '00:00' (เที่ยงคืนตามปกติ)** — คอมเมนต์ในไมเกรชันระบุตรง ๆ ว่าเป็น "คำสั่งของ Touch: ขอบวันของรายงานต้องอ่านจากเวลาปิดร้านที่เจ้าของร้านตั้งเอง ไม่ใช่ค่าคงที่ในโค้ด" — ต่างจากสมมติฐาน 04:00 คงที่ทั้งแนวคิด (configurable) และค่า default (เที่ยงคืน ไม่ใช่ 04:00)
2. **สมมติฐานเดิม: group by ต้อง cast เป็น Asia/Bangkok ก่อนเสมอ** — เพราะ DB เก็บเวลาเป็น `timestamptz` (UTC) ตามที่ `DISPLAY_TIMEZONE` ใน `src/lib/env.ts` กำหนดไว้
   **ตรงกับโค้ดจริง (ยืนยันแล้ว):** ทุกคิวรีใน `src/server/admin/reports.ts` ใช้ `(paid_at AT TIME ZONE 'Asia/Bangkok') - cutoff::interval` ก่อน cast เป็น `date` เสมอ — คอมเมนต์ในโค้ดอธิบายเหตุผลตรงกับสมมติฐานนี้ทุกคำ
3. **สมมติฐานเดิม: แสดงยอดก่อน VAT โดยใช้เรต VAT ของวันนั้นจากตาราง `shop_vat_change` ไม่ใช่เรตปัจจุบัน**
   **สิ่งที่โค้ดจริงทำ (ขัดกับสมมติฐาน):** ไม่แตะ `shop_vat_change` เลย — ใช้ `bill.vat_amount_satang` ที่ snapshot ไว้ตอน**เปิดบิล**แทน คอมเมนต์ในโค้ดระบุว่า "ทัชตัดสิน 2026-08-28: รายงานต้องกระทบยอดกับใบกำกับภาษีที่ออกไปจริงได้เป๊ะ ... บิลที่เปิดก่อนเปลี่ยนเรตแล้วมาจ่ายทีหลังยึดเรตตอนเปิดบิล" — มีเทสยืนยันตรง ๆ ว่า "ร้านเปลี่ยนเรต VAT หลังบิลปิดไปแล้ว → ยอดในรายงานต้องไม่ขยับตาม" ซึ่งเป็นเกณฑ์ที่ต่างจากการไล่ดู `shop_vat_change` ย้อนหลังตามสมมติฐาน
4. **สมมติฐานเดิม: Phase 0 ใช้ query สดยังไม่ทำ rollup table**
   **ตรงกับโค้ดจริง (ยืนยันแล้ว):** `getSalesSummary()` เป็น SQL query สดทั้งหมด (CTE `paid_bill` คิวรีตรงจากตาราง `bill`/`order_item`) ไม่มี materialized view หรือตาราง rollup ใด ๆ ในชุด migration นี้

**คำตัดสินปิดท้าย (Touch, 2026-08-28)** — ทั้งสองข้อที่ขัดกันถูกเคาะให้**ยึดตามโค้ดจริง**:

- **ขอบวันธุรกิจ** ใช้ `shop.business_day_cutoff` ที่เจ้าของร้านตั้งเอง default เที่ยงคืน
  เหตุผล: ร้านแต่ละร้านปิดไม่พร้อมกัน ค่าคงที่ 04:00 ในโค้ดจะผิดกับร้านที่ปิดเที่ยงคืนตรง
  และผิดกับร้านที่ปิดตี 2 พอ ๆ กัน · ข้อจำกัดที่ยังเหลือ: **ยังไม่มีหน้าจอให้ตั้งค่านี้**
  แก้ได้ทาง SQL เท่านั้น ต้องเปิดงานใหม่รองรับ
- **เรต VAT** อ่านจาก `bill.vat_amount_satang` ที่ล็อกไว้ตอนเปิดบิล ไม่ใช่ไล่ย้อนจาก
  `shop_vat_change` เหตุผล: รายงานต้องกระทบยอดกับใบกำกับภาษีที่ออกจริงได้ทุกบาททุกสตางค์
  ไม่มีส่วนต่างจากการปัดเศษซ้ำ และบิลที่เปิดก่อนเปลี่ยนเรตแล้วมาจ่ายทีหลังต้องยึดเรตตอนเปิดบิล
  ซึ่งคือยอดที่ลูกค้าจ่ายจริง

> ข้อ 1–7 ที่เป็นเรื่อง design system อยู่ใน [[design-system-adoption-v1|Design System Adoption v1]] §8 — ด้านล่างคือประเด็นที่โผล่มาจากการทำ **screen inventory** โดยเฉพาะ

1. **อุปกรณ์จริงของจอสถานี (NEED-INPUT เดิมข้อ 3 ของ UX Requirements ยังไม่ได้คำตอบ)** — กระทบ layout ของ S-00 ถึง S-07 ทั้ง 8 หน้าโดยตรง และกระทบว่าจะมี **เครื่องพิมพ์สลิปกระดาษ** ด้วยหรือไม่ (US-13 Notes เปิดทางไว้ว่า "จอ vs พิมพ์สลิป" เป็นการตัดสินใจของ COULSON) **Default:** แท็บเล็ตแนวนอน 1024×768 บนเคาน์เตอร์ **ไม่มีเครื่องพิมพ์สลิปใน Phase 0** — ถ้า Touch ต้องการสลิปกระดาษจริง จำนวนหน้าจอไม่เปลี่ยน แต่ต้องเพิ่มงานออกแบบเลย์เอาต์สลิป

2. **"ร้อน/เย็น" เป็นหมวดหมู่หรือ option group** (รายละเอียดเต็มใน Design System Adoption §8 ข้อ 1) — เป็นประเด็นเดียวที่ **เปลี่ยนจำนวนการ์ดบนหน้า C-01 จาก ~19 เป็น ~30 ใบ** และเปลี่ยนโครงสร้าง C-02 ทั้งหน้า **Default:** หมวดหมู่ = ร้อน/เย็น ตาม backlog

3. **ลูกค้าช่องทาง takeaway ต้องมีหน้าสรุปยอด (C-06) ด้วยหรือไม่** — US-07 เขียนสำหรับ dine-in ("สรุปยอดของโต๊ะ ... ไปชำระที่เคาน์เตอร์") แต่ takeaway จ่ายก่อนไปแล้ว จึงไม่มีบิลค้างให้สรุป **Default:** ช่องทาง takeaway ไม่มี C-06 — ลูกค้าเห็นยอดที่จ่ายไปแล้วบนการ์ดออเดอร์ใน C-05 แทน และ TabBar ของโหมดเคาน์เตอร์มี 3 ปุ่มแทน 4

4. **US-09 (หมายเหตุพิเศษ เช่น "แพ้ถั่ว") เป็น Phase 1 — ตั๋วออเดอร์ของ Phase 0 ควรเผื่อพื้นที่ไว้เลยหรือไม่** — ถ้าไม่เผื่อ ตอน Phase 1 ต้องรื้อ layout ของ S-01/S-02 ใหม่ **Default:** SHURI เผื่อพื้นที่ในโครง layout ของตั๋วไว้ **แต่ไม่สร้าง UI ใด ๆ ของ US-09 ใน Phase 0**

5. **US-26 (เปิด/ปิดรับออเดอร์ของร้าน) เป็น Phase 1 แต่ UX §5 บรรจุกรณี "ร้านปิดรับออเดอร์" ไว้ในตาราง error state ที่บังคับให้มี wireframe** — เกิดความกำกวมว่าหน้าจอนี้อยู่ใน Phase 0 หรือไม่ **Default:** ออกแบบ **ข้อความ/สถานะ** ของ C-01 กรณีร้านปิดรับออเดอร์ไว้ตั้งแต่ Phase 0 (เพราะ UX §5 บังคับ) แต่ **ไม่สร้างหน้าจอฝั่งแอดมินสำหรับกดเปิด/ปิด** (นั่นคือ US-26 ของ Phase 1)

6. **จำนวน QR เคาน์เตอร์** — Business Rule ข้อ 12 พูดถึง QR เคาน์เตอร์แบบเอกพจน์ แต่ไม่ได้ระบุว่าร้านมีจุดสั่งกี่จุด **Default:** 1 ใบ และ A-07 ออกแบบให้รองรับมากกว่า 1 ใบได้โดยไม่ต้องแก้โครงสร้าง

**ผลลัพธ์:** ไฟล์ `docs/02-design/01-prototypes/screen-inventory-v1.md` — **23 หน้าจอ** (ลูกค้ามือถือ 7 · จอสถานีพนักงาน 8 · จอแอดมิน 8) พร้อมตารางตรวจความครบถ้วนที่ยืนยันว่า **US ของ Phase 0 ครบทั้ง 23 ตัวมีหน้าจอรองรับ ไม่มีตกหล่น** · ทุกหน้าจอระบุ state ที่ต้องออกแบบครบ (ปกติ/ว่าง/โหลด/error/edge) โดยแมปตรงกับตาราง Error-Empty-Edge States ของ UX Requirements ทั้ง 7 กรณี · ระบุ component จาก theme ที่ใช้ต่อ vs ที่ต้องสร้างใหม่ในทุกหน้า · ประเด็นถาม XAVIER/Touch เพิ่มอีก 6 ข้อพร้อม default

**ค้าง/เสี่ยง:** **(1)** 16 จาก 23 หน้าจอ (Surface B และ C) **ไม่มีต้นแบบใน theme เลย** — theme ให้มาแค่ 4 เฟรมของแอปมือถือลูกค้า ความเสี่ยงคือ SHURI จะแต่งหน้าตาใหม่ที่หลุดจากภาษาของ theme มีกฎกำกับไว้แล้ว 4 ข้อใน Design System Adoption §6.1 แต่ต้องเฝ้าตอน review **(2)** A-06 (ผังโต๊ะ US-42) เป็นหน้าเดียวที่เพิ่มสโคปจริงให้ Phase 0 ตามที่ roadmap เตือนไว้ — ควรจัดเวลาออกแบบมากกว่าหน้าแอดมินอื่น **(3)** S-01 ช่วง peak เป็นหน้าจอเสี่ยงที่สุดของทั้งระบบ (J4 ระบุว่าเบียร์คือ single point of failure) และ Phase 0 **ยังไม่มี US-41 (จัดลำดับ+aging) มาช่วย** — Phase 0 ลดความเสี่ยงได้แค่ด้วย layout ที่ไม่พังเมื่อออเดอร์เยอะและการทำให้คิว "รอยืนยันการชำระเงิน" มองเห็นตลอดเวลา ถ้า Touch ยืนยันว่า peak หนักจริงตั้งแต่วันเปิดร้าน ควรดัน US-41 ขึ้น Phase 0 ตามที่ XAVIER เปิดทางไว้ **(4)** ประเด็น "ร้อน/เย็น เป็นหมวดหมู่หรือ option" กระทบจำนวนการ์ดในหน้าเมนูโดยตรง ควรได้คำตอบก่อน SHURI ลงมือ

**skill ที่ใช้:** scrutinize (ไล่ Phase 0 US ทีละตัวเทียบกับหน้าจอที่แตกออกมา จนได้ตารางตรวจความครบถ้วนที่พิสูจน์ว่าไม่มี US ตกหล่น และไล่ตาราง Error/Empty/Edge States ทั้ง 7 กรณีของ UX Requirements ว่ามีหน้าจอเจ้าภาพจริงทุกกรณี — ทำให้พบเพิ่มว่า US-07 ไม่ครอบคลุมช่องทาง takeaway และ US-26 ที่เป็น Phase 1 มี error state บังคับใน Phase 0), management-talk (แยกสิ่งที่ตัดสินเองแล้วออกจาก 6 ข้อที่ต้องถามกลับ โดยทุกข้อมี default ให้ SHURI เดินงานต่อได้ทันที)
