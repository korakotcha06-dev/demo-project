## 1. โครงบันไดยอดเงินตามมาตรฐาน

หัวใจของเรื่องนี้ · ถอดจาก `Forms/Invoice.xaml.cs` เมธอด `calculate()`

```
lineTotal      = Σ (item.pricePerUnit × item.quantity − item.discount)   ← "มูลค่าสินค้า/บริการ"
totalDiscount  = lineTotal × extraDiscountRate / 100                     ← ส่วนลดท้ายบิล
serviceCharge  = (lineTotal − totalDiscount) × serviceChargeRate / 100   ← ค่าบริการ

basisAmount    = lineTotal − totalDiscount + serviceCharge               ← 🔴 "จำนวนเงินรวมสุทธิ" = ฐานภาษี
taxTotal       = basisAmount × taxRate / 100                             ← "ภาษีมูลค่าเพิ่ม"
grandTotal     = basisAmount + taxTotal                                  ← "มูลค่าสุทธิ"
```

ป้ายกำกับภาษาไทยข้างบนคือคำที่ปรากฏบนฟอร์มของ ETDA จริง (`Forms/Invoice.xaml`) —
**ควรใช้คำเดียวกันบนใบเสร็จของเราด้วย** เพราะเป็นคำที่ผู้ทำบัญชีและสรรพากรใช้อยู่

### 1.1 สามข้อที่ต่างจากที่เราทำอยู่

| # | มาตรฐาน | ของเรา ([[data-model-v1|Data Model]] §10.3) |
|---|---|---|
| 1 | ฐานภาษีมี **ส่วนลดท้ายบิล** และ **ค่าบริการ** อยู่ในบันได | `subtotal` วิ่งเข้า VAT ตรง ๆ ไม่มีสองขั้นนี้ |
| 2 | ราคาต่อหน่วยในรายการเป็น **ราคาไม่รวม VAT** เสมอ (`"จำนวนเงิน (ไม่รวม VAT)"` เป็นหัวคอลัมน์) | รองรับทั้ง `include` และ `exclude` — ร้านกาแฟจริงมักติดป้ายราคารวม VAT แล้ว |
| 3 | มีแต่ทาง **exclude** (`grandTotal = basisAmount + taxTotal`) ไม่มีการถอด VAT ออกจากราคารวม | เรามี `include` ที่ถอดกลับด้วย `subtotal × rate / (10000 + rate)` |

> 🎯 **ข้อ 3 คือเหตุผลที่เราต้องตรวจสูตร `include` ด้วยตัวเอง** — เครื่องมืออ้างอิงไม่มีทางนี้เลย
> จึงไม่มีของให้เทียบ · สูตรของเราถูกต้องทางคณิตศาสตร์ (ถ้า total = base × (1+r)
> แล้ว vat = total × r/(1+r)) แต่ **ไม่มีใครนอกโปรเจกต์ยืนยันให้** จนกว่าผู้ทำบัญชีจะดู

### 1.2 🔴 สิ่งที่เครื่องมืออ้างอิงทำแล้ว "อย่าลอก"

```csharp
// eTaxInvoicePdfGenerator/Entity/InvoiceObj.cs
public double basisAmount { get; set; }
public double taxTotal { get; set; }
public double grandTotal { get; set; }
```

เครื่องมือของ ETDA เก็บเงินเป็น **`double`** และแสดงผลด้วย `.ToString("N")` (ปัด 2 ตำแหน่ง
ตอนแสดง) · แล้วอ่านค่ากลับจาก **TextBox บนหน้าจอ** เข้า object ด้วย `Convert.ToDouble(taxTotalTb.Text)`

นี่คือรูปแบบที่ [[architecture-v1|Architecture v1]] §3.5 สั่งห้ามไว้ตรง ๆ และเป็นเหตุผลที่เรา
เก็บเงินเป็น **integer สตางค์** กับอัตราเป็น **basis point** · **การตัดสินใจของเราถูก —
อย่าย้อนกลับไปตามเครื่องมืออ้างอิงในข้อนี้**

## 2. รหัสประเภทเอกสาร — ร้านกาแฟออกใบไหน

ถอดจาก `util/getInvoice_Xml.cs` บรรทัด 42–58

|---|---|---|
| `388` | ใบกำกับภาษี | ขายแบบ B2B ที่ออกใบกำกับแยกจากใบเสร็จ |
| **`T03`** | **ใบเสร็จรับเงิน/ใบกำกับภาษี** | 🔴 **ใบเดียวจบ — เป็นแบบที่ร้านกาแฟใช้** *(อนุมานจากลักษณะการขาย)* |
| `80` | ใบเพิ่มหนี้ | เก็บเงินเพิ่มจากใบเดิม |

> 🎯 **ประเด็นสำหรับเรา:** ถ้า Touch จด VAT เอกสารที่ระบบต้องออกคือ **T03 ไม่ใช่ 388**
> — เอกสาร US-21 ที่จะเขียนต้องระบุรหัสนี้ให้ชัด ไม่ใช่เขียนแค่คำว่า "ใบกำกับภาษี"
> เพราะสองอย่างมีรูปแบบและข้อมูลบังคับไม่เท่ากัน

### 2.1 ใบลดหนี้ (81) — ฐานภาษีคือ **ผลต่าง** ไม่ใช่ยอดใหม่

```csharp
// Forms/CreditNote.xaml.cs
double taxTotal   = difference * taxRate / 100;
double grandTotal = difference + taxTotal;
obj.basisAmount   = obj.difference;
```

`InvoiceObj` มี `original` (ยอดเดิม) และ `difference` (ผลต่าง) แยกกัน · ใบลดหนี้ต้อง
**อ้างเลขที่และวันที่ของใบเดิม** พร้อมสาเหตุ

🔴 **ช่องว่างของเรา:** เรามี `payment_kind = 'refund'` เป็นแถวใน ledger เท่านั้น
ไม่มีการอ้างใบเดิม ไม่มีการเก็บผลต่างเป็นฐานภาษี · ถ้าร้านจด VAT แล้วคืนเงินลูกค้า
การคืนเงินนั้น *(อนุมาน)* ต้องมีใบลดหนี้คู่กัน ซึ่งวันนี้ระบบออกให้ไม่ได้

## 3. เลขที่เอกสาร — เรียงลำดับ ห้ามข้าม

ถอดจาก `util/RunningNumber.cs` + `Entity/SellerObj.cs`

- เลขที่ = **prefix (ตัวอักษร) + ตัวเลขเติมศูนย์หน้า** เช่น `INV0001` → `INV0002`
- แยกเลขรัน **คนละชุดต่อประเภทเอกสาร** — `SellerObj` มี `inv_no`, `dbn_no`, `crn_no` แยกกัน
- ความยาวรวมของเลขที่ **ไม่เกิน 35 ตัวอักษร** (`3 + prefix.Length + number.Length > 35` → รีเซ็ตเป็น 1)
- เลขรันผูกกับ **ผู้ขาย** ไม่ใช่กับเครื่อง

🔴 **ช่องว่างของเรา:** `bill` **ไม่มีคอลัมน์เลขที่ใบกำกับภาษีเลย** · `sequence_no` ที่เรามี
คือลำดับออเดอร์ **ในบิล** (เริ่มที่ 1 ทุกบิล) ไม่ใช่เลขรันของเอกสารภาษี · และ `queue_no`
เป็นเลขคิวรายวันที่ **วนใช้ซ้ำ** ตาม US-45 — ใช้เป็นเลขที่ใบกำกับไม่ได้เด็ดขาด

> ✅ **แก้แล้ว 2026-08-22** (migration 016) — `bill.tax_invoice_no` +
> `tax_invoice_series` + หน้าจอ A-08 · ดู changelog วันเดียวกัน
>
> 🔴 **แก้ความเข้าใจผิดของเอกสารฉบับแรก:** ตอนแรกเขียนว่า "ควรเปิดคอลัมน์นี้
> ก่อนเปิดร้าน แม้ยังไม่ใช้" ซึ่ง**พูดเกินจริง** · บิลก่อนวันจด VAT
> **ไม่ต้องมีเลขที่ใบกำกับ** เพราะร้านยังไม่มีสิทธิ์ออกใบกำกับ — เลขเริ่มนับที่
> **วันจด** ไม่ใช่ย้อนไปวันเปิดร้าน จึงไม่มีอะไรต้องกรอกย้อนหลังเลย
>
> สิ่งที่จริงคือ: โครงต้องมี**ก่อนวันจด** (ไม่ใช่ก่อนวันเปิดร้าน) และเลขที่
> **ที่ออกไปแล้ว**ย้อนกลับไปแก้ไม่ได้ — ซึ่งเป็นเหตุผลที่ `tax_invoice_series`
> ไม่รีเซ็ตเมื่อปิด VAT แล้วเปิดใหม่

## 5. ห้ามแก้ใบเดิม — ยกเลิกแล้วออกใหม่

ฟอร์มใบกำกับของ ETDA มีชุดฟิลด์นี้ (`Forms/Invoice.xaml`):

- `ยกเลิกใบกำกับภาษีเดิม เพื่อออกใบกำกับภาษีใหม่` (checkbox)
- `สาเหตุในการยกเลิกใบกำกับภาษีเดิม` + `เหตุอื่น`
- `เลขที่ใบกำกับภาษีเดิม` · `วันที่ของใบกำกับภาษีเดิม`

แปลว่า **การแก้ใบกำกับที่ออกไปแล้วทำไม่ได้** — ต้องออกใบใหม่ที่อ้างใบเดิมพร้อมสาเหตุ

> 🎯 **ตรงกับหลักของเราพอดี** — [[data-model-v1|Data Model]] §10.2 เขียนไว้แล้วว่า
> *"บิลที่ปิดไปแล้วต้องนิ่งตลอดกาล"* และ `forbid_hard_delete` / `payment` แบบ append-only
> บังคับไว้ที่ระดับฐานข้อมูล · **สถาปัตยกรรมเราพร้อมรับข้อนี้อยู่แล้ว ไม่ต้องรื้อ**
> ที่ขาดคือ *กลไกออกใบใหม่ที่อ้างใบเดิม* ไม่ใช่หลักการ

### 6.1 ข้อที่ต้องอ่านให้ระวัง (ไม่ใช่บั๊ก แต่หลอกคนอ่านรายงานได้)

`bill.subtotal_satang` **มีความหมายไม่เหมือนกันในสองโหมด**:

| โหมด | `subtotal_satang` คืออะไร | ฐานภาษีหาจากไหน |
|---|---|---|
| `exclude` | ยอด**ก่อน** VAT = ฐานภาษีตรง ๆ | `subtotal_satang` |
| `include` | ยอด**รวม** VAT แล้ว | ต้องคำนวณ `subtotal_satang − vat_amount_satang` |

**ตัวเลขจริงจาก `computeBillTotals()` (ยืนยันด้วยการรันโค้ด อัตรา 7%):**

| `subtotal_satang` | โหมด | VAT | **ฐานภาษี** | ยอดที่เก็บจากลูกค้า |
|---|---|---|---|---|
| 10,700 | `include` | 700 | **10,000** | 10,700 |
| 10,700 | `exclude` | 749 | **10,700** | 11,449 |
| 6,000 | `include` | 393 | **5,607** | 6,000 |
| 6,000 | `exclude` | 420 | **6,000** | 6,420 |

เลขตัวเดียวกันในคอลัมน์เดียวกัน ให้ฐานภาษีคนละค่า และยอดที่เก็บจริงคนละค่า

🔴 **และ VAT ของสองโหมดไม่เท่ากันด้วย** — `10,700` สตางค์ให้ VAT `700` ถ้าเป็นราคารวม
แต่ให้ `749` ถ้าเป็นราคาที่ยังไม่รวม · **ต่างกัน 49 สตางค์ต่อบิล** ใช้สลับกันไม่ได้เด็ดขาด

ข้อมูลไม่หาย (หาฐานภาษีกลับได้จาก snapshot ที่เก็บไว้ — ตรวจแล้วว่า
`ฐานภาษี + VAT = subtotal` เป๊ะทุกค่าตั้งแต่ 1 ถึง 3,000 สตางค์ ไม่มีเงินหายจากการปัด)
แต่ **ใครที่เขียนรายงานแล้ว `SUM(subtotal_satang)` ข้ามบิลที่คนละโหมด จะได้ตัวเลขที่
ไม่มีความหมาย** — และ §10.2 อนุญาตให้ร้านเปลี่ยนโหมดกลางทางอยู่แล้ว จึงเกิดขึ้นได้จริง

> **ข้อเสนอ:** รายงานทุกตัวต้องอ่าน `vat_mode_snapshot` คู่ไปด้วยเสมอ · ถ้าจะทำรายงาน
> ภาษีจริง ให้เก็บ **ฐานภาษี** เป็นคอลัมน์ของตัวเองตอนปิดบิล จะได้ไม่ต้องคำนวณซ้ำ
> ทุกครั้งด้วยตรรกะที่อาจเพี้ยนคนละที่

## 7. สิ่งที่ต้องตัดสินก่อนเขียน US-21

คำถามที่ต้องได้คำตอบจาก **Touch + ผู้ทำบัญชี** ไม่ใช่จากโค้ด:

1. ~~ร้านจะจด VAT ตั้งแต่วันเปิด หรือรอถึงเกณฑ์รายได้?~~ — **ไม่ต้องตัดสินก่อนแล้ว**
   ระบบเปิด/ปิดได้เองเมื่อถึงเวลา (A-08) · ตัดสินตอนไหนก็ได้
2. **ราคาบนป้ายจะรวม VAT หรือบวกตอนท้าย?** (`vat_mode`) — กระทบข้อความบนเมนูและใบเสร็จ
3. **ลูกค้าขอใบกำกับแบบเต็มบ่อยแค่ไหน?** — ถ้าแทบไม่มี ข้อ 2 ในตาราง §6 เลื่อนได้ยาว
4. **จะมีค่าบริการ (service charge) ไหม?** — ถ้ามี ต้องเข้าบันไดยอดเงินก่อนคิด VAT ไม่ใช่บวกท้าย
5. **คืนเงินลูกค้าเกิดขึ้นจริงไหม และบ่อยแค่ไหน?** — ตัดสินน้ำหนักของใบลดหนี้ (§2.1)
6. **จะออกเอกสารเป็น PDF/A-3 มี XML ฝังตามมาตรฐาน หรือใบเสร็จกระดาษพอ?** — ต่างกันคนละโครงงาน
