## 1. Deploy demo — ทำตอนนี้

### 1.1 🔴 สามข้อที่ต้องรู้ก่อน ไม่งั้นพังทันที

**(1) `tsx` อยู่ใน `devDependencies` แต่ production ต้องใช้**

`pnpm migrate` และ `pnpm realtime` เรียก `tsx` ทั้งคู่ · ถ้าติดตั้งบนเซิร์ฟเวอร์ด้วย
`pnpm install --prod` **ทั้ง migration runner และ WebSocket server จะพังทันที**

- ทางแก้ตอนนี้: **ติดตั้งเต็ม** (`pnpm install --frozen-lockfile` ไม่ใส่ `--prod`)
- ทางแก้ถาวร (ควรทำก่อนเปิดร้าน): ย้าย `tsx` ไป `dependencies` หรือ compile ตัว
  realtime server เป็น JS ตอน build

**(2) ยังไม่มี health endpoint**

ไม่มี `/api/health` หรืออะไรเทียบเท่า · **monitoring จึงยังไม่มีอะไรให้เช็ค** —
เป็นงานของส่วนที่ 3 ไม่ใช่ตัวขวาง demo

**(3) มีสองโปรเซสยาว ไม่ใช่หนึ่ง**

| โปรเซส | คำสั่ง | พอร์ต | ถ้าไม่รัน |
|---|---|---|---|
| เว็บ | `pnpm start` (หลัง `pnpm build`) | 3000 | ระบบไม่ขึ้นเลย |
| realtime | `pnpm realtime` | `WS_PORT` (3001) | **ระบบยังใช้ได้** — ตกไปใช้ polling 5 วินาที และขึ้นป้าย "โหมดสำรอง" |

🔴 **realtime ไม่ใช่ของบังคับสำหรับ demo** — architecture §3.3 ออกแบบ polling fallback ไว้
ตั้งแต่ต้น · ถ้า demo มีเวลาจำกัด ให้เว็บขึ้นก่อนแล้วค่อยต่อ WS ได้

### 1.2 ตัวแปรสภาพแวดล้อม

```
DATABASE_URL=postgres://<user>:<pass>@localhost:5432/<db>
PUBLIC_BASE_URL=https://thyna.tnmlab.dev
NEXT_PUBLIC_WS_URL=wss://thyna.tnmlab.dev
WS_PORT=3001
```

🔴 **ห้ามใส่ `SEED_*` บนเครื่องจริง** — ดูส่วนที่ 2

### 1.3 ลำดับขั้น

```bash
# 1. เอาโค้ดขึ้น
git clone <repo> && cd qr-order-app && git checkout main

# 2. ติดตั้ง — ห้ามใส่ --prod (ดู 1.1 ข้อ 1)
pnpm install --frozen-lockfile

# 3. เตรียมฐาน — ครั้งแรกเท่านั้น
createdb <db>          # Postgres อยู่บน VPS เครื่องเดียวกัน (§9.2)
pnpm migrate

# 4. build แล้วรัน
pnpm build
pnpm start &           # เว็บ 3000
pnpm realtime &        # WS 3001 — ข้ามได้ถ้ายังไม่พร้อม
```

**หน้าบ้าน** — Cloudflare (DNS · CDN · WAF · **Tunnel**) ชี้ `thyna.tnmlab.dev` เข้าพอร์ต 3000
· Tunnel ทำให้**ไม่ต้องเปิดพอร์ตขาเข้าที่ VPS เลย** (§9.2 · ลด R13 ส่วนหนึ่ง)

### 1.4 ตรวจว่าขึ้นจริง — ไม่ใช่แค่ไม่ error

| ตรวจอะไร | ทำยังไง | ผลที่ถูก |
|---|---|---|
| เว็บขึ้น | เปิด `https://thyna.tnmlab.dev/login` | เห็นหน้าเข้าสู่ระบบ |
| ฐานต่อติด | เข้าสู่ระบบด้วยบัญชีแอดมิน | เข้าได้ ไม่ค้าง |
| migration ครบ | `pnpm migrate` ซ้ำ | ขึ้นว่า "ไม่มี migration ใหม่" |
| ข้อมูลไม่ขัดกันเอง | `pnpm check:invariants` | "สอดคล้องครบทุกข้อ" |
| 🔴 **QR ใช้ได้จริง** | สร้างโต๊ะ → ดาวน์โหลดป้าย → **สแกนด้วยมือถือจริง** | เข้าหน้าเมนูของโต๊ะนั้น |
| realtime | เปิดจอพนักงาน ดูมุมขวาบน | ถ้าไม่ขึ้น "โหมดสำรอง" = WS ต่อติด |

🔴 **ข้อ QR ต้องสแกนด้วยมือถือจริง ไม่ใช่กดลิงก์บนคอม** — เป็นข้อเดียวที่พิสูจน์ว่า
`PUBLIC_BASE_URL` ถูกตั้งถูก · ตั้งผิดแล้ว QR จะพาไป `localhost` โดยหน้าเว็บยังดูปกติทุกอย่าง

## 2. ระหว่าง demo — สามอย่างที่ห้ามทำ

ทั้งสามข้อนี้**สร้างความเสียหายที่ย้อนกลับไม่ได้ด้วยการแก้โค้ด**

### 2.1 🔴 ห้ามรัน `pnpm seed` บนเครื่องที่มีข้อมูลจริง

`seed` **สร้างจุดบริการใหม่ทั้งชุด → รหัส QR เปลี่ยนหมด** · ป้ายที่พิมพ์ไปแล้วสแกนไม่ติดทุกใบ

> เกิดขึ้นจริงแล้วระหว่างพัฒนา (2026-08-23) — QR ที่เปิดได้ตอนเช้าใช้ไม่ได้ตอนบ่าย
> และมันยัง**ล้างค่าที่ตั้งไว้เองด้วย** (ธีมป้าย QR · ข้อจำกัดระดับคั่วของเมล็ด)

`seed` มีไว้สำหรับเครื่อง dev ที่ยอมให้ข้อมูลหายเท่านั้น

### 2.2 🔴 ห้ามพิมพ์ป้าย QR ติดโต๊ะจริงด้วยโดเมนนี้

`thyna.tnmlab.dev` เป็น**โดเมนตัวอย่าง ไม่ใช่โดเมนถาวร** —
`architecture-v1` §5.3 ระบุว่าโดเมนบน QR ต้องเป็น **"โดเมนเดียวของบริการสำหรับทุกร้าน"**
แต่ `thyna.` คือชื่อร้าน (ดู decision log 2026-08-23)

- **พิมพ์ทดสอบ / ถือโชว์ / วางบนโต๊ะชั่วคราวตอน demo** — ได้
- **ติดสติกเกอร์ถาวร** — **ห้าม** จนกว่าจะเคาะโดเมนบริการถาวร

**เส้นแบ่งคือ "สติกเกอร์ใบแรกที่ติดแล้วไม่ตั้งใจจะลอก"** ไม่ใช่ "เปิดร้านหรือยัง"

### 2.3 ⚠️ ไฟล์ที่อัปโหลดไม่รอด deploy

`public/signage/` (โลโก้ · ภาพพื้นหลังป้าย QR) ถูก gitignore และ**อยู่บนดิสก์ ไม่ได้อยู่ในฐาน**
· deploy ใหม่แบบ clone ใหม่ = **รูปหาย ต้องอัปโหลดซ้ำ**

ยังไม่มีทางออกถาวร — ต้องตัดสินในส่วนที่ 3 (เก็บนอกโฟลเดอร์ deploy / object storage / เก็บลงฐาน)

### 2.4 🔴 demo ที่เปิดให้คนนอกสแกนสั่งเล่น — สี่อย่างที่ต้องตั้งก่อน

Touch ยืนยัน (2026-08-23): *"QR เรายังไม่ปริ้นจริงอยู่แล้ว แต่ให้คนสแกนเข้ามาลองสั่งเล่นได้"*
— คนที่สั่งคือ**คนนอกที่ไม่รู้ว่านี่คือ demo** สิ่งที่ต้องกันจึงต่างจาก demo ที่เราคลิกเอง

**(1) 🔴 ห้ามใส่เบอร์พร้อมเพย์จริง**

ปุ่ม "พร้อมเพย์" สร้าง **QR ตามมาตรฐาน EMVCo ที่ฝังยอดเงินมาแล้ว** — มัน**โอนเงินได้จริง**
ถ้าเบอร์ในระบบเป็นเบอร์จริง · คนที่มาลองสั่งเล่นอาจสแกนแล้ว**โอนเงินจริงให้ร้านโดยไม่ตั้งใจ**
และระบบ**ไม่มีทางคืนเงินให้อัตโนมัติ** (ดู decision log 2026-08-23 — พร้อมเพย์ไม่มี refund ผ่าน API)

- ✅ **สถานะตอนนี้ถูกแล้ว: ยังไม่ได้ตั้งเบอร์** → ปุ่มพร้อมเพย์ใช้ไม่ได้ ซึ่งคือสิ่งที่ต้องการ
- ระหว่าง demo ให้รับเงิน **"เงินสด"** อย่างเดียว (เป็นการกดบันทึกเฉย ๆ ไม่มีเงินจริง)

**(2) ปิด VAT ไว้**

ถ้าเปิด ตัวเลขภาษีของออเดอร์ทดลองจะปนกับของจริงตั้งแต่วันแรกที่เปิดร้าน · A-08 เปิดทีหลังได้

**(3) ออเดอร์ทดลองจะค้างในคิวและทำให้ `check:invariants` แดง**

ด่าน OPS จับ "ออเดอร์ที่ค้างสถานะเดิมเกิน 2 ชั่วโมง" · คนลองสั่งแล้วไม่มีใครกดปิด =
คิวจะพอกขึ้นเรื่อย ๆ

> เกิดขึ้นจริงแล้ว (2026-08-23) — ออเดอร์ทดลอง 2 ใบค้าง 4 ชั่วโมงจน `check:invariants` แดง

- ระหว่าง demo ให้**กดปิดออเดอร์เป็นระยะ** — ปุ่ม "เสร็จแล้ว" หรือ "ยกเลิก" ในกระดานออเดอร์
- 🔴 ออเดอร์เคาน์เตอร์ที่บันทึกว่ารับเงินแล้ว ให้ปิดด้วย **"เสร็จแล้ว" ไม่ใช่ "ยกเลิก"** —
  ยกเลิกแปลว่าต้องคืนเงิน ซึ่งจะทิ้งร่องรอยผิดไว้ในบัญชี

**(4) วางแผนล้างข้อมูล demo ไว้ตั้งแต่ตอนนี้**

🔴 **`pnpm seed` ล้างให้ไม่ได้** — มันสร้างจุดบริการใหม่ทั้งชุด **รหัส QR เปลี่ยนหมด** (ดู 2.1)

ทางที่ปลอดภัยที่สุดคือ **ใช้ฐานข้อมูลคนละตัวสำหรับ demo กับของจริง** แล้วเปิดร้านจริง
ด้วยฐานสะอาด — ตัดสินให้จบก่อนวันเปิด ไม่ใช่ตอนที่มีบิลจริงปนอยู่แล้ว

## 3. ก่อนเปิดร้านจริง — ยังไม่ต้องทำวันนี้ แต่ห้ามลืม

> ทั้งหมดนี้คือมาตรการที่ตารางความเสี่ยง §9.5 ระบุไว้เอง
> **วันที่ลูกค้าจริงคนแรกสแกน QR = วันที่รายการนี้ต้องติ๊กครบ**

### 3.1 R13 — ภาระ ops

- [ ] ย้าย `tsx` ไป `dependencies` หรือ compile realtime server (ดู 1.1 ข้อ 1)
- [ ] เพิ่ม **health endpoint** ที่ตรวจ **การต่อฐานข้อมูลจริง** ไม่ใช่แค่ตอบ 200
- [ ] ให้สองโปรเซสอยู่ใต้ **systemd** (หรือ process manager อื่น) — restart เองเมื่อตาย
- [ ] monitoring + **alert ที่ดังถึงคนจริง** เมื่อเว็บล่มหรือฐานต่อไม่ได้
- [ ] SSL ต่ออายุอัตโนมัติ (Cloudflare จัดการให้ ถ้าใช้ Tunnel) — ยืนยันว่าจริง
- [ ] แผน patch OS

### 3.2 R14 — backup ที่กู้ได้จริง 🔴 ข้อที่แพงที่สุดถ้าพลาด

- [ ] `pg_dump` อัตโนมัติรายวัน เก็บ**นอก VPS เครื่องนั้น**
- [ ] 🔴 **ทดสอบ restore จริงลงฐานเปล่า** แล้วเปิดระบบขึ้นมาดู — ไม่ใช่แค่ดูว่าไฟล์ถูกสร้าง
- [ ] **alert เมื่อ backup ไม่ผ่าน**

> 🔴 เอกสารบันทึกไว้ว่า **เคยเกิดจริงที่ระบบอื่นของ TNM — สคริปต์ backup เงียบไป 10 คืน
> โดยไม่มีใครรู้** · "ตั้งไว้แล้ว" กับ "กู้ได้จริง" เป็นคนละเรื่องกัน

### 3.3 R15 — VPS เครื่องเดียว

- [ ] **ถ่าย snapshot ก่อน deploy ทุกครั้ง**
- [ ] SOP กระดาษเมื่อระบบล่ม + คีย์ออเดอร์ย้อนหลังผ่าน US-30 (ยอมรับความเสี่ยงนี้ใน Phase 0)

### 3.4 โดเมนถาวร (C8)

- [ ] เคาะโดเมนบริการที่**ไม่มีชื่อร้านอยู่ในนั้น**
- [ ] ตั้ง `PUBLIC_BASE_URL` เป็นโดเมนนั้น **แล้วสร้าง QR ใหม่ทั้งหมดก่อนพิมพ์**
- [ ] คง `/t/` `/c/` บนโดเมนเดิมเป็น **redirect ถาวร**

### 3.5 ไฟล์อัปโหลด

- [ ] ตัดสินที่เก็บของ `public/signage/` ให้อยู่ข้ามการ deploy

## 4. Deploy รอบถัดไป

```bash
git pull
pnpm install --frozen-lockfile
pnpm migrate            # 🔴 ก่อน build เสมอ — โค้ดใหม่คาดหวัง schema ใหม่
pnpm build
# restart ทั้งสองโปรเซส
pnpm check:invariants   # ตรวจว่าข้อมูลยังไม่ขัดกันเอง
```

🔴 **`pnpm migrate` ต้องมาก่อน `pnpm build`/restart เสมอ** — โค้ดใหม่คาดหวังตารางใหม่
ถ้ารันสลับลำดับ ระบบจะขึ้นแล้วพังตอนมีคนเปิดหน้าที่ใช้ตารางนั้น ซึ่งแปลว่า**พังตอนมีคนใช้จริง
ไม่ใช่ตอน deploy**

**ก่อนเปิดร้านจริง** ให้เพิ่ม `snapshot ก่อน` ไว้หัวลำดับนี้ (R15)
