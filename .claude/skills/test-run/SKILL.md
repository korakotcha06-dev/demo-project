# Test Run (Test Case → ผลจริง → Bug Log → Go/No-Go)

รันเคสที่ `/test-design` เขียนไว้ กับ **ระบบจริงที่ทำงานได้** แล้วบันทึกผลลง `docs/03-testing/02-test-result`

**เจ้าของงาน:** OKOYE

## 🔴 เงื่อนไขก่อนเริ่ม — ถ้าข้อใดไม่ผ่าน ให้หยุดและรายงาน

1. **มีระบบให้ทดสอบจริง** — ถ้ายังไม่มีโค้ดที่รันได้ skill นี้ใช้ไม่ได้ ให้กลับไป `/test-design`
2. **test data ครบตามเช็กลิสต์ใน `test-data-v1.md`** — seed ผิดทำให้เคสบางตัว **pass แบบผิด ๆ** ซึ่งอันตรายกว่า fail
3. **อุปกรณ์ครบตามที่ test plan §1.3 ระบุ** — โดยเฉพาะเคส `C` (≥2 เครื่องพร้อมกัน) และ NFR-06 (4 เครื่อง)
4. **รู้ว่ากำลังทดสอบ build ไหน** — บันทึก commit/version ไว้ ผลทดสอบที่ไม่รู้ว่าทดสอบอะไรอยู่ ไม่มีค่า

---

## Workflow

### 1. เปิดรอบทดสอบ
บันทึกหัวรอบใน `02-test-result/test-result-v1.md`: วันที่ · ผู้ทดสอบ · build/commit · สภาพแวดล้อม · ชุด test data ที่ใช้

### 2. รันตามลำดับความเสี่ยงใน test plan §6
ไม่ใช่เรียงตามเลข TC — เงินผิด และ architecture ที่แก้ทีหลังแพง มาก่อน

### 3. บันทึกผลทีละเคส — มี 4 สถานะเท่านั้น

| สถานะ | ใช้เมื่อ |
|---|---|
| **PASS** | รันครบทุกขั้นตอน และผลตรงกับ "ผลที่คาดหวัง" **ทุกข้อ** |
| **FAIL** | รันได้ แต่ผลไม่ตรง → **ต้องมี BUG-xxx ผูกทันที** |
| **BLOCKED** | รันไม่ได้เพราะของยังไม่มี/อุปกรณ์ไม่ครบ → ระบุว่าติดอะไรและใครปลดล็อก |
| **DEGRADED** | รันได้แต่ไม่ครบเงื่อนไขจริง → **ห้ามนับเป็น PASS** และต้องเขียนว่าขาดอะไร |

🔴 **กฎที่ห้ามละเมิด:**
- **BLOCKED ไม่ใช่ pass และไม่ใช่ fail** — เป็นหมวดที่สาม ต้องรายงานแยกเสมอ
- **ผลบางส่วนตรงไม่นับเป็น PASS** — "ผลที่คาดหวัง" มีหลายข้อ ต้องครบทุกข้อ
- **ห้ามกรอกผลเคสที่ยังไม่ได้ลงมือรัน** ไม่ว่าจะมั่นใจแค่ไหน
- **DEGRADED ห้ามใช้เป็นหลักฐานว่า NFR ที่เกี่ยวข้องผ่าน** (เช่น รันด้วย 4 บัญชีแยกไม่พิสูจน์ NFR-06 ที่ต้องใช้บัญชีเดียว 4 เครื่อง)

### 4. เจอ FAIL → ก่อนเขียนเป็นบั๊ก ให้เรียก `/debug-mantra`
ทำซ้ำให้ได้ก่อน แล้วค่อยเขียน ไม่ใช่รายงานอาการลอย ๆ

ลง `02-test-result/bug-log-v1.md`:

```
| BUG | TC ที่เจอ | Req ID | ความรุนแรง | อาการ | ขั้นตอนทำซ้ำ | สภาพแวดล้อม | เจ้าของ | สถานะ |
```

**ความรุนแรง:**

| ระดับ | นิยาม |
|---|---|
| **S1 Critical** | เงินผิด · ข้อมูลหาย · เปิดร้านไม่ได้ · กฎ prepay รั่ว |
| **S2 Major** | ฟีเจอร์หลักใช้ไม่ได้ แต่มีทางเลี่ยง |
| **S3 Minor** | ใช้ได้แต่ผิดจากที่ออกแบบ |
| **S4 Cosmetic** | ไม่กระทบการใช้งาน |

**สถานะ:** `เปิด` → `กำลังแก้` → `แก้แล้วรอ verify` → `ปิด (verify แล้ว)`
🔴 **ห้ามปิดบั๊กด้วยคำว่า "แก้แล้ว" อย่างเดียว** — ต้องรัน TC เดิมซ้ำแล้ว PASS จริงถึงปิดได้ และบันทึกว่ารันซ้ำเมื่อไหร่

### 5. บั๊กที่ปิดแล้ว → `/post-mortem`
เฉพาะ S1/S2 หรือบั๊กที่หลุดมาได้ทั้งที่ควรถูกจับตั้งแต่ design — บันทึกว่ามันหลุดมาได้อย่างไร เพื่อให้ `04-retrospectives` หยิบไปใช้

### 6. ตัดสิน Go / No-Go
ลง `02-test-result/test-summary-report-v1.md` เทียบกับ **เกณฑ์ผ่าน-ไม่ผ่านใน test plan §7** ตรง ๆ:

- P0 ต้อง PASS **100%** — ไม่มีข้อยกเว้น
- P1 PASS ≥90% · ที่ fail ต้องมี ticket และเจ้าของ
- invariant (suite `I`) ต้อง PASS **100%** — ถ้า DB ไม่ปฏิเสธ แปลว่ากฎธุรกิจไม่มีผลบังคับจริง ไม่ว่า UI จะกันดีแค่ไหน
- **เคสที่ BLOCKED อยู่ใน exit criteria = ยังตัดสินว่าผ่านไม่ได้**

🔴 **ห้ามรายงานว่า Phase ผ่านการทดสอบ ถ้ายังมีเคสใน exit criteria ที่ยังไม่ได้รัน** — ผลทดสอบที่ไม่ครอบสิ่งที่อยู่ใน exit criteria ไม่ใช่หลักฐานว่าพร้อมเปิดร้าน

### 7. ปิดรอบ
- อัปเดต `02-test-result/index.md` (wikilink + สถานะรอบล่าสุด)
- ลง `docs/05-log/changelog.md`
- รายงาน Touch ด้วย `/management-talk`

## รูปแบบการรายงานขึ้น Touch

เรียงแบบนี้เสมอ — ตัวเลขก่อน ความเห็นทีหลัง:

1. **ตัดสินได้หรือยัง** — Go / No-Go / ยังตัดสินไม่ได้เพราะอะไร
2. **ตัวเลข** — PASS / FAIL / BLOCKED / DEGRADED (รวมต้องเท่ากับจำนวนเคสทั้งหมด)
3. **บั๊ก S1/S2 ที่ยังเปิดอยู่** — พร้อมผลกระทบเป็นภาษาธุรกิจ ไม่ใช่ศัพท์เทคนิค
4. **สิ่งที่ต้องการจากคนอื่น** — ใคร ทำอะไร แล้วปลดล็อกกี่เคส

## กฎเหล็ก

1. **ตัวเลขทุกตัวต้องนับจากตารางผลจริง** — ห้ามประมาณ ห้ามปัดให้สวย
2. **PASS / FAIL / BLOCKED / DEGRADED รวมกันต้องเท่ากับจำนวนเคสทั้งหมดเป๊ะ** ถ้าไม่เท่าแปลว่ามีเคสหาย
3. **ห้ามแก้ test case ให้เข้ากับพฤติกรรมของระบบที่ผิด** — เคสผิดให้กลับไป `/test-design` พร้อมเหตุผล
4. **ห้ามแก้โค้ดเอง** — คุณเป็นด่านตรวจ ไม่ใช่คนแก้ ส่งกลับ COULSON/BANNER/SHURI
